# 第 4 章 静态批处理之弊与连续批处理（大项目 v1→v2）

> **最小背景栏**：本章只需要第 1-2 章的账本（两阶段画像、launch 开销、带宽下限）与第 3 章的 KV 账本概念（$2Lh_{kv}d_k$ 元素/token）。GQA 的投影形状（Book3 第 6 章）会在手写执行层复现——权重键位 `q/k/v/o_proj` 你已认识。排队论不需要：本章的账全是算术。

## 4.1 开始造引擎：第一版引擎的唯一使命

第 2 章收尾时立了还账路线表，现在开始第一笔。造引擎之前先把「为什么需要引擎」的两册欠条再读一遍：Book2 第 10 章与 Book3 第 6 章都登记过「全量重算口径」的欠账框——当时训练侧只需要一次前向，如今服务侧每生成一个 token 都要重走整段序列，这笔账再拖不下去了（Book2 第 12 章那句「那是推理册的开场白」说的正是此刻）。

但第一版引擎（v1）不是来解决这些问题的——**它的唯一使命是当反面教材**：把「没有引擎」的三宗罪原样代码化，让每一宗罪都变成可测量的数字。三宗罪：静态批（一批算到全批完成为止，先完成的请求空转陪跑）；无 KV cache（每步全量重算，$O(n^2)$ 的账原样保留）；逐批串行（批间无重叠）。v1 的每一行代码都在为 v2 的偿还做对照基线。

先看 workload 的设计——这是教学引擎与玩具 demo 的分界。v1 的负载从真实语料切出：8 条请求、prompt 各 128 token（等长——把 prefill 的拼批干扰摘干净，教学焦点集中在 decode 期的浪费）、输出长度 16 到 64 token 不齐（制造静态批的经典困境）。测量口径与第 1 章一致：wall-clock、有效 token 数（扣除空转）、显存峰值。

## 4.2 静态批处理的时隙账

把静态批的时间线画出来最直观（图 4.1 占位：八条横条、各自从 prefill 块后伸出长短不一的 decode 尾巴、全部对齐到最长的右端——先完成的尾巴上打叉的格子就是浪费位）。静态批的做法朴素到不需要解释：把 8 条请求拼成一个批张量，prefill 一次算完，然后逐步 decode——直到**最后一条**请求完成。浪费的结构值得再看一眼：它不是均匀散布的，而是**集中在批尾**——前 16 步人人有活干（最短的还没完成），第 17 步起最短的请求开始空转，空转的批位随步数单调增加，到最后几步可能只剩一条请求在干活、其他七条全程陪跑。**浪费随时间累积**这个形状很重要：它意味着输出长度的**方差**（而不只是均值）决定浪费——长短越悬殊、批越大，批尾的空转越惨。这为 workload 的画像法（服务运营里统计输出长度分布）埋下伏笔。

问题出在「不齐」：输出最短的请求 16 步就完了，最长的要 64 步——静态批没有退出机制，先完成的请求只能继续陪跑，每一步都白白为它们计算一个「根本不会被读走的 token」。

**例 4.1（构造例：3 条请求的静态批时隙账）**：设 3 条请求输出长度分别为 2、3、5。静态批跑到第 5 步：第 1 条在第 2 步就已完成的 2 个有效 token 之后，**又陪跑了 3 步×1 个空位 = 3 个浪费位**；第 2 条浪费 2 位；总计算位 3×5=15，有效位 2+3+5=10，浪费 $\frac{5}{15} = 33\%$。直觉读法：**浪费率由「最长请求与平均长度之差」决定**——输出越不齐、批越大，浪费越可观。这个 toy 数字与下面实测的 22.8% 同源。

v1 的实测把这笔画在真实负载上（`engine_v1_base.json`，Atlas 910B3）：

**实物 4.1（v1 静态批读数，出处：本机实测，`engine_v1.py`）**

```text
[v1] 8 条请求 × p_len 128 | decode 62 步 | wall 2.76s
     吞吐 138.99 tok/s | 浪费位 113/496（22.8%） | 峰值 665.7 MiB
```

读法导引：decode 62 步=最长请求的输出长（它锁定全批节奏）；496 个批位（8×62）里只有 383 个有效——**113 个批位在为已经完成的请求空转**，占 22.8%。这就是静态批的时隙账，Orca 论文（OSDI 2022）图 2/3 画的就是这幅时间线（依据其机制自绘的版本见本章图 4.1）。

## 4.3 Orca 的答案：调度粒度从「批」降到「步」

2022 年，OSDI 会刊上的一篇论文把这个问题连根拔起。Orca（Yu et al., OSDI 2022——该文**没有 arXiv 版本**，引用挂 USENIX 官方页，我们的调研底单里存了官方 PDF）提出 **iteration-level scheduling**（迭代级调度）：调度的粒度不再是一批，而是**一个 decode 步**。每步过后：完成的请求即刻退出批（它的 KV 与批位即刻释放）、等待的请求即刻填入空位（新批随时重组）。静态批里「先到的等后到的、先完的陪没完的」两笔冤枉账同时清零。

iteration 级调度还有一个容易被低估的副产品：**准入的即时性**。静态批世界里一条新请求要么等当前批整体结束（TTFT 以秒计）、要么被塞进「下一批」的等待队列；iteration 级世界里它等的是**一步**——最坏几百毫秒、通常几十毫秒内就能进批。对交互式产品（聊天、代码补全），这个差别是「能用」与「不能用」的分界——TTFT 的 SLO（第 1 章那把尺子）在这里第一次被工程机制直接保卫。

但同一个批里混着「刚 prefill 完的长请求」和「decode 到一半的短请求」，张量形状怎么对齐？Orca 的第二件武器是 **selective batching**（选择性批处理）：**能拼批的段拼批，不能拼批的段各自算**。具体说：线性投影与 FFN 段——每个 token 独立过自己的参数，拼成 $(B, 1, d)$ 的批毫无障碍；注意力段——每条请求要读**自己的 KV 历史**，天然各是各的，就按请求各自算（或等长对齐后向量化）。拼批的红利（权重摊薄）拿到手，注意力的事实（历史不可共享）也尊重——**selective 的意思是「按算子的性质选择批的边界」**。

Orca 论文报的数字：与 FasterTransformer 相比最高 36.9×（GPT-3 175B 场景，摘要口径【官方论文】）——这个乘数是「调度收益×批利用率提升×它那个 baseline 的浪费」的复合，读的时候要知道它对照的是完全静态的世界。真正被业界继承的是机制本身：今天一切主流引擎的调度循环都是 iteration 级的。

> **【考据框】「continuous batching」这个名字是谁起的？** 有趣的是，Orca 论文全文**一次也没有出现** continuous batching 这个词——它用的是 iteration-level scheduling。vLLM 的 SOSP 论文也不用这个词。这个名字是 Anyscale 的博客（2023 年 9 月）流行起来的——机制是 Orca 的、名字是博客圈的；NVIDIA 的 TensorRT-LLM 文档则叫 in-flight batching（同一机制的第三个名字）。本册正文用业界通名「连续批处理（continuous batching）」，考据框里把三个名字的出身钉死——读文献时不至于以为是三个东西。

## 4.4 v1 的代码走读：三宗罪的现场

`engine_v1.py` 只有一百多行，因为笨得很诚实。主循环是它的全部（形状标注在注释里）：

```python
while not done.all():
    logits = model(gen)[0][:, -1]        # (B, n, V) 全量重算——罪②：无 KV cache
    nxt = multinomial(softmax(logits))   # (B, 1) 采样
    gen = cat([gen, nxt], 1)             # (B, n+1) 序列只增不减
    done |= (n_steps >= max_new)         # 完成的请求置位——但没有退出批：罪①
```

三宗罪在代码里一眼可辨：`model(gen)` 每步对整个 $(B, n)$ 重算（无 KV）；`done` 只置位不摘除（静态批）；批间没有重叠（串行）。值得停留一秒的是 `gen` 张量的形状演化：$(8, 128) \to (8, 129) \to \cdots \to (8, 190)$——**它每一步都在变大**，这就是无 KV 的 O(n²) 账在张量形状上的直接可视化：第 $t$ 步的计算量正比于 $128+t$。

## 4.5 v2 的两把刀：连续批处理与 KV cache

`engine_v2.py` 把两把刀同时落下。

**第一把刀：iteration 级调度**。主循环的形状彻底变了：不再是「一个批张量跑到底」，而是维护一个**活跃集**——每步先做出批（完成的摘除、等待的填入），再对活跃集走一步。v1 的 `done` 置位变成了 `del active[rid]`：请求完成的瞬间，它的 KV 缓存与批位即刻回收。浪费位的账从此不存在——不是被优化掉了，是**这笔账的记账科目被取消了**。

**第二把刀：KV cache**。先把机制账算清：decode 第 $t$ 步的 naive 前向要把 $n_0+t$ 个 token 全部过一遍模型——其中 $n_0+t-1$ 个的 K/V 昨步就算过、今天原样不变；只有新 token 的 K/V 是新的。KV cache 把「算过的」存下来：每层每请求一个 $(h_{kv}, n, d_k)$ 的两张表（K 表与 V 表），每步只前向新 token——计算量从 $O(n)$ 每步降到 $O(1)$ 每步（每 token 常数次投影），代价是显存里多了这张随长度生长的表（第 3 章的 KV 账本——24 KiB/token）。**空间换时间的最古典形态**，省的正是第 2 章算过的那笔 $O(n^2)$ 总账。v2 手写了带缓存的步进执行层（这是本册大项目最重的一块代码）：prefill 段一次前向把整段 prompt 的 K/V 存入该请求的缓存——每层形状 $(h_{kv}, n_0, d_k)$；decode 段每步只前向**新 token 的一个位置**——$q$ 是 $(h, 1, d_k)$、打分是 $(h, 1, n)$ 对全部历史，但「算过的历史」再也不重算，只读取。与 llama215 原版 forward 的数值对拍（CPU fp32）逐位一致：prefill 与两步 decode 的 max|Δ| 均为 0.00e+00——步进执行层与全量重算在数学上等价，这是后面一切改造的地基。

批化的关键在**异长共存**：活跃集里「decode 到第 40 步的老请求」和「刚 prefill 完的新请求」的缓存长度不同，attention 段用 pad+mask 向量化处理（把各请求的 K 拼到 $n_{max}$、把 pad 位在 softmax 里掩掉）——这就是 selective batching 在张量操作层的真身：**投影段真拼批、注意力段 pad+mask 拼批**。

## 4.6 实测对照：一个必须诚实面对的反直觉

v2 的实测（同 workload、同种子）：

**实物 4.2（v2 连续批读数 + v1 对照，出处：本机实测）**

```text
[v2] 8 条 | wall 4.50s | 吞吐 85.09 tok/s | TPOT 均 58.98 ms | 峰值 498.2 MiB | 浪费位 0
[v1] 8 条 | wall 2.76s | 吞吐 138.99 tok/s | （全批锁定节奏）  | 峰值 665.7 MiB | 浪费位 113
```

浪费位 113→0 达成、显存峰值降 25%（KV 缓存替代了不断膨胀的 gen 张量）——但**吞吐反而更低**（85 对 139）。并发扫描（第 7 章的收官数据先借一角）把这层账摊得更开：$B{=}1$ 时 v1 28.2 对 v2 20.1 tok/s、$B{=}8$ 时 168.7 对 88.3——全档 v1 占优，且差距随 B 扩大（v1 的整图前向把批维摊得更好、v2 的 python 逐层税随批内请求数线性涨）。这不是连续批处理的失败，是第 1 章那个发现的回归：**瓶颈还没搬到「正确的位置」上**。拆开看：v1 每步是一次 $(8, n)$ 的整图前向（torch 计算图、大 kernel 链）；v2 每步是手写层循环（12 层 × 逐请求缓存读写 + python 循环开销）——省掉的 FLOPs 在 NPU 上本来就不值钱（207M 全量重算的计算只占峰值的百分之几，launch 才是主导），而 python 循环的每层开销是新增的。**省计算不省时间的条件是「计算在瓶颈上」**——roofline 的教训在引擎上原样重演。第 12 章的图执行与真实的工程优化（kernel 融合、C++ 调度循环）才是让 v2 的机制红利兑现成时延红利的最后一公里；也正是这个原因，工业引擎从不这样做对比——它们的前提（融合 kernel、图执行）早已铺好。

v2 真正的胜利在语义层：**TTFT 不再等凑批**（新请求即刻入批——静态批世界里它要等整批结束）、**TPOT 不再被最长请求锁定**、**浪费位的记账科目取消**。吞吐的绝对值是执行层工程的问题，机制的账要这样读才公平。

## 4.7 本章小结

回扣开篇：v1 把三宗罪代码化，每宗都拿到了实测数字——静态批浪费 22.8%、无 KV 的张量形状逐步膨胀、批间串行。v2 两把刀落下：iteration 级调度（Orca 的机制，名字的考据已钉死）取消浪费位科目、KV cache 步进执行层（对拍逐位一致）把 O(n²) 清偿。反直觉的吞吐对照不是失败，是「优化必须先在正确瓶颈上」的一课——这堂课第 7 章收官时还会再上一遍。

带走的心智：**调度粒度从批到步，是引擎与循环的第一个分水岭——它改变的不是一个数字，是账目的结构（浪费位科目被取消、TTFT 获得即时性）**；而机制红利与工程红利是两层账，教学引擎拿到前者、工业引擎补齐后者。下一章把「同池共处」推到底：多条请求的 KV 不再各占一段连续显存，而是分页共居一个物理块池——碎片，这个 v2 还藏着的最后一笔浪费，将被操作系统的老智慧消解。
