# 第 5 章 PagedAttention：分页 KV 与碎片消解（大项目 v3）

> **最小背景栏**：本章用到 v2 的块状世界观（第 4 章的活跃集与 KV 缓存）与操作系统「虚拟内存分页」的常识——不熟悉操作系统的读者不用慌：5.2 节把分页的来龙去脉从零讲到可画出，不假设任何 OS 前置。B5-1 的「分类型账本」公式（Book5 第 1 章）在 5.6 节回收。

## 5.1 一笔从 Book5 带来的正账

Book5 第 2 章的章末欠账框里写着：「滑窗层要『滚动淘汰』……逐块记账与淘汰给 prefill/decode 带来的不对称是推理系统的正菜。→ Book6 第 5 章（第 3 章架构侧串联）」。现在到期了。这本账说的是：混合架构的机器上，不同层的 KV 有不同的**生命周期**——全局层的 KV 活到请求结束、滑窗层的 KV 滚动作废（窗口滑出即弃）、线性层压根没有 KV 只有固定状态。一个引擎要伺候这样的机器，它的 KV 管理就必须支持「同一池子里住着不同寿命的住客」。而现行的连续显存管理方式，连「不同大小的住客」都伺候不好——先从这笔更基本的账算起。

## 5.2 分页：操作系统的一堂旧课

v2 的 KV 管理有个我们当时没细看的隐患：每请求一段**连续**缓存，按上限预分配（`n_cap` 一次买断）。两个问题随之而来。**其一，买断浪费**：请求实际用多长事先不知道，只能按最坏情况分配——输出 16 token 的请求也占着 256 token 的仓位。**例 5.0（构造例：外部碎片的诞生）**：显存里先后住过三段连续 KV（各 40 MiB），中间的请求先走了——留下一个 40 MiB 的洞。新来的请求要 60 MiB 连续段：洞太小、剩余空间也散——**明明总空闲超过 60 MiB，却分配失败**。连续分配的失败不是「空间不够」而是「形状不对」——这就是外部碎片：空间是标量、需求是形状。

**其二，外部碎片**：连续段必须整段找到空闲显存才能分配；请求进出几个回合后，显存里散布着大小不一的空洞——每个空洞都不够放下新请求的整段，加起来却很大（这就是「外部碎片」：空间没少，形状不对）。

两笔浪费的量级感先立住。买断浪费的教学实测：v2 按 n_cap=192 买断，8 条实际长度 130-190 的请求共占 8×192×24 KiB = 37 MiB，实际只需 34 MiB——**教学负载里 7%**；但把 n_cap 拉到服务真实上限（2048），浪费率立刻到 80% 以上（论文 Fig 2 那个 20.4%-38.2% 利用率的由来——预留与碎片在真实部署里是常态而非病态）。这两个问题计算机科学在六十年前就解过一遍。操作系统的解法叫**分页（paging）**：把物理内存切成固定大小的小块（页框），把程序的地址空间也切成同样大小的页；程序看到的「连续地址」由**页表**翻译到散布各处的页框。买断浪费消失（最后一页之外的页都实打实用着），外部碎片消失（任何页框都一样大，哪里有空用哪里）——代价是最后一页的**内部碎片**（页内用不满的部分）与查页表的开销。**判据自查**：拿 7 个 token 的请求配 4 token 一页——逻辑页 0（token 0-3）落页框 5、逻辑页 1（token 4-6，占 3 格空 1 格）落页框 9。你能画出这张映射，分页就懂了。

页的大小本身也是一堂权衡课：操作系统选 4 KiB 是「浪费 vs 表项开销」的折中；KV 管理的块选 16-128 token 是同类折中加一层「注意力收集的段数」——块越小碎片越少，但一次注意力读取要拼的段越多（第 5.7 节实测这笔税）。vLLM 团队把这套思想搬进 KV 管理（SOSP 2023 论文，arXiv:2309.06180），名字起作 PagedAttention。原文的自陈是「inspired by the classical virtual memory and paging techniques in operating systems」——**借的是分页、页表与写时复制三件，不是完整虚存**（没有按需调页、没有换出到磁盘）；借来的精确边界，引用时要说清楚。

## 5.3 block table：KV 的页表

v3 引擎（`engine_v3.py`）把 v2 的连续缓存换成三件套：

**物理块池**（`BlockFreeList`，自有类名与任何引擎源码类名刻意区分——本册「论文概念可用、实现类名不碰」纪律的操作面）：一个大张量堆 $(N_{blocks}, L, 2, h_{kv}, b, d_k)$——$b$ 是块大小（每块装 $b$ 个 token 的 KV）、$N_{blocks}$ 是池里的总块数，配一个空闲块号栈。**块表**（`BlockTable`，论文概念身份）：每请求一张，逻辑 token 位置 $p$ 查表得物理块号与槽位——$(p \div b, p \bmod b)$。**分配与回收**：请求每长满 $b$ 个 token 申请一块，请求结束（或滑窗滚出）即刻还块。

**例 5.1（构造例：块大小 4、两条请求的块表走查）**：请求 A 长 7（prompt 5 + 已生成 2）、请求 B 长 5。A 的逻辑页 0（token 0-3）与页 1（token 4-6，实占 3 槽）——池里空块是 3、7、8：A 拿块 3 与 7；B 随后进来拿块 8（一页装 4）再拿一块装第 5 个 token——拿块 3？不行，块 3 被 A 占着——拿下一个空块。此刻池的占用图：块 3（A 满）、块 7（A 半满——**内部碎片 1 槽**）、块 8（B）——任何未来请求都能拿到整块，**外部碎片为零**。把例 5.0 的困境在分页世界重演：那个 40 MiB 的洞=十个空块，新请求要 15 块——池里任何 15 个空块都行（形状需求消失了，只剩数量需求）。**分页把「形状问题」降解成「数量问题」**——这就是它能终结外部碎片的全部秘密。A 结束：块 3、7 归还池栈顶，B 的第 5 个 token 照常住块 8 的下一页（新块）。两张表、一个池、按页借还——这就是全部机制。

块表还有一个实现层的小账值得一提：**收集（gather）**。注意力每步要读全部历史的 K/V——连续缓存是一次切片（$[:n]$ 一刀），分页后历史散在多个物理块里，要按表逐块拼回逻辑序（`gather_layer` 的逐块 cat）。这就是分页的访存税：逻辑连续变物理离散，读取从一次访存变成多次。块越大税越轻（块少拼接少）但内部碎片越重；块越小反之——**权衡的旋钮就是块大小**（vLLM 论文 Fig 18-19 的消融正为此）：块太小——页表条目多、块操作碎、注意力收集要拼更多段；块太大——内部碎片回潮（最坏 $b-1$ 槽/请求）。v3 默认块大小 32（实验档可调）——第 5.7 节实测它的账。

## 5.4 论文的账：碎片从六成降到近零

vLLM 论文给出的动机数字（Fig 2【官方论文】）：现有系统的 KV 显存**有效利用率只有 20.4%-38.2%**——六到八成的 KV 显存被预留浪费与碎片吃掉，而这直接折算成并发容量损失。PagedAttention 之后浪费「限于一块以内」——注意这句「waste of under 4%」**出自 vLLM 官方博客（2023-06-20）而非论文**，论文口径是 near-zero（摘要）与上述利用率对照——引用时两个出处分列（本册引用纪律：引擎博客数字一律标厂商自报）。

## 5.5 写时复制：前缀共享的伏笔

分页还送了一件将来有用的事：**写时复制**（copy-on-write）。两条请求若共享同一段前缀（同一个系统提示、同一段对话历史），它们的 KV 块可以**指向同一批物理块**——只要都只读。哪条请求要先写新 token，新 token 落在新块里，共享块不动（「写时才复制」的语义在块粒度自然成立）。这是第 6 章前缀缓存的物理基础——分页不只是省显存，它把「共享」变成了可能。此伏笔先记下。

## 5.6 分类型生命周期的块管理（B5-1 兑现）

现在接 5.1 的正账。分类型账本（Book5 第 1 章立的公式）说混合架构有三类 KV/状态：全局层无界增长、滑窗层有界（$\min(n, W)$）、线性层固定状态。在块管理眼里它们是**三类住客**：

- **全局层的块**：随请求增长逐块申请，活到请求结束——「全保」。
- **滑窗层的块**：窗口滑过 $W$ 之后，最老的块**整体作废**——还块入池。滚动淘汰在块粒度是 $O(1)$ 的记账（还一块、进一块），在连续缓存上却要搬运整个窗口（memmove 掉最老的一格、其余前移）——**分页让「淘汰」从搬运降级为记账**，这正是 B5-1 那句「逐块记账与淘汰」的账本面。「滚动淘汰」在块粒度是 $O(1)$ 的操作（还一块、进一块），在连续缓存上却要搬运整个窗口（memmove 几 MB）——**分页让「淘汰」从搬运降级为记账**。滑窗层的占用量恒定在 $\lceil W/b \rceil$ 块——Book4 第 10 章那个「gpt-oss 滑窗层 KV 需求是否被窗口 128 封顶」的问题，块账一口答出：封顶在 $W$，且以块为单位取整。
三类住客的画像在容量规划上合出一张「分类型并发账」：全局层决定并发上限的弹性部分（每条请求线性吃满 $2L_g h_{kv} d_k$）、滑窗层贡献封顶部分（$\lceil W/b \rceil$ 块/请求，与长度无关）、线性层只付常数——**一台混合架构机器能同时伺候多少条 100 万 token 的请求，取决于全局层那本无界账**；这把 Book5 第 1 章的账本公式从「描述模型」推进到了「规划容量」。
- **线性层**：没有 KV 块——它的状态是固定张量，随请求激活/销毁，根本不进 KV 池（统一分页池如何同时容纳 KV 与状态张量，是 Book8 第 1 章的终局课题——本册只立问题）。

**例 5.2（构造例：滑窗 W=8 的环形块账）**：块大小 4、滑窗层的第 9 个 token 到来。此刻窗口覆盖 token 1-8（块 A=1-4、块 B=5-8）。新 token 9 进块 C；同时 token 1 滑出窗口——块 A 里 token 1 作废但 token 2-4 还在窗内，**块 A 不能整块还**。到 token 12 到来时：窗口 5-12，块 A（token 1-4）整块出窗——还块。看到机制了吗：**滚动淘汰的粒度是块、节奏是「整块出窗才还」**——块大小决定了淘汰的响应延迟（最坏多留 $b-1$ 个过期 token 的 KV）。这就是「逐块记账与淘汰给 prefill/decode 带来的不对称」的账本面——B5-1 的欠账在此兑现，混合架构机器的块管理画像完成。

## 5.7 v3 实测：碎片账与代价账

`engine_v3.py` 在与 v2 相同的 workload 上跑分页版（数值对拍：分页路径 vs 全量重算 CPU fp32，max|Δ|=0.00e+00——分页只改存放不改数学）：

**实物 5.1（v3 分页读数 + v2 对照，出处：本机实测）**

```text
[v3] 8 条 | wall 9.45s | 吞吐 40.52 tok/s | KV 账 v2 连续 37 MiB -> v3 分页 34 MiB（省 7.1%）
```

值得再深看一眼「省 7.1%」的构成：它是「买断浪费的消除」减「内部碎片的引入」的净额——8 条请求各留最多 31 个空槽（块大小 32），最坏情形内部碎片反而比买断浪费大！教学负载里净额为正靠的是「长度分布离上限不远」；生产负载里（长度分布长尾、上限保守）净收益会大得多。**分页不是无条件的赢——它赢在「不确定」上：请求长度越不可预测，买断越浪费、分页越划算**。两笔账分开读。**省的账**：v2 按 $n_{cap}$ 买断（8 条 × 192 上限 × 24 KiB = 37 MiB），v3 只占实际长度取整到块（34 MiB）——省 7.1%。这个数字温和，因为教学 workload 的 $n_{cap}$（192）只是实际长度的两三倍；生产环境里「不知道请求会多长」的不确定性越大（聊天对 32k 上限）、请求越短，买断浪费的比例越可观——论文那 60-80% 的利用率数字正是这么来的。**付的账**：吞吐从 85 降到 40.5 tok/s——块收集（`gather_layer` 逐块拼接）与逐 token 入块的 python 开销，与 v2 一样的手写层税。另有一笔池的固定开销：块池预分配 4096 块 ≈ 3.2 GiB（峰值显存 3.5 GiB 的主因）——生产引擎的池按需增长，教学版一步到位。

## 5.8 本章小结

三笔旧账在此合销：**F4 的账本**（Book1 起的 KV 读取语义，经 Book3 第 6 章开立）、**B3-1 的第三股**（存放方式的省法——分页不压 KV 一个字节，只消灭「放不下」的浪费）、**B5-1 的两类生命周期**（全保与滚动淘汰在块粒度的统一管理）。带走的心智：**分页把 KV 管理从「找房」变成「登记」——连续分配时代你要找一整段合适的显存（找不到就碎片死），分页时代你只需要记账（哪页在哪个块）；而记账，正是引擎比操作系统更擅长的事**。代价也如实记下：块粒度的收集与访存模式改变，是第 8 章 kernel 章的常客。下一章兑现 5.5 埋的伏笔：既然块可以被两条请求共享，前缀缓存就只剩一个问题——怎么知道「这个块我算过了」。
