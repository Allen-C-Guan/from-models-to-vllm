# 第 6 章 Prefix caching：前缀复用的经济学（大项目 v4）

> **最小背景栏**：本章站在 v3 的块池与块表上（第 5 章），前置只有一样新东西——哈希函数（把任意数据映射成短指纹的常识级理解即可）。Book2 第 11 章 few-shot 探针的账（K 条示范前缀被一遍遍重算）在 6.1 回收。

## 6.1 三本旧账：few-shot 的、多轮的、上下文的

第 5 章收尾说：块可以被共享，剩下的问题是「怎么知道这个块我算过了」。这个问题值多少钱，先算三本旧账。

**第一本：few-shot 的账（N6）**。Book2 第 11 章做过 in-context learning 探针：给模型 K 条示范再提问。示范部分动辄几百上千 token——而对话服务里，同一组示范会被**成千上万个请求原样重复**。Book2 第 11 章的章末欠账框写着：「它的长 prompt 在服务侧的经济学（前缀缓存）见 Book6 第 6 章」——每个请求都从头 prefill 一遍同样的示范，是纯粹的重复劳动。

**第二本：多轮对话的账**。聊到第 5 轮时，请求的 prompt = 系统提示 + 前 4 轮全部历史 + 新问题——历史部分**逐轮原样重发**。第 $r$ 轮的 prefill 里，前 $r-1$ 轮的 KV 昨天就算过、今天还在缓存里躺着（如果没被丢掉的话）。

**第三本：上下文主线的终点账（F10/N7）**。Book1 的「容量→上下文长度」主线经 Book2 第 12 章、Book5 第 4 章一路接力，到服务端汇成一句话：**长上下文的账单大部分是重复前缀的账单**——前缀缓存的命中率，就是这份账单的折扣率。

三本账指向同一个机制：**把「算过的前缀」认出来、复用它**。

## 6.2 两派设计：认块的两条路

先给收益立一个上限直觉：命中率的理论上限=负载里重复前缀占总 prefill 的比例。多轮对话里这个比例随轮数增长（第 5 轮的请求里 80% 以上是历史重发）；few-shot 服务里示范前缀全局复用（比例=示范长度占比）；一次性分析负载里它趋近零。**前缀缓存不创造任何新计算——它只是不再重复旧计算**；所以它的收益天花板由负载形状封顶，机制的好坏只决定你离天花板多近。带着这个上限观，看两派怎么「认块」。

**哈希前缀派**（vLLM 路线）：每个块的指纹 = **块内 token id 序列的哈希**。为什么合法？因果模型的确定性——同样的 token 序列、同样的权重，算出的 K/V 逐位相同（第 4 章 v2 对拍的 0.00e+00 就是确定性的实证）。所以拿 token 序列当指纹不损失任何信息：指纹相同 ⟹ KV 相同。查询是 $O(1)$ 的哈希表查找；粒度是块（块对齐的前缀才能命中）。代价：键管理碎（海量块键的分配与驱逐）、只在「块边界」命中。

**RadixAttention 派**（SGLang 论文，arXiv:2312.07104 的运行时组件）。基数树值得三十秒讲透：一棵每个节点存「一段 token 序列」的多叉树，**从根到任何节点的路径拼起来就是一个历史前缀**。两条对话共享系统提示=它们在系统提示节点之前走同一条路；在哪岔开，前缀就共享到哪。查询=沿 token 序列逐字符下行，走不动的那一点就是最长匹配（LCA）——匹配段的 KV 全在树上挂着，直接取用。新算的部分完成后挂成新枝——**树自己就是缓存的全部元数据**（不需要独立的哈希表）。驱逐时剪枝（按 LRU 或效用剪叶子——叶子是最少被复用的前缀尾）。把全部历史前缀组织成一棵**基数树**（radix tree）——从根到任一节点的路径就是一个历史前缀，公共前缀天然共享树干。新请求到来，沿树下行到**最长匹配节点**（LCA）——匹配段即命中段，分歧点之后才需要新算。树的优点：前缀关系一目了然、任意长度命中（不受块边界约束的树形变体）；代价：树的锁与并发管理更重。

哈希键的细节还有一个工程暗礁：**前缀绑定**。裸的「块内容哈希」有碰撞风险——同一个 16-token 序列出现在不同前缀位置，其 KV 其实相同（因果模型只看内容与位置——位置在 RoPE 里已乘进 K），所以裸内容键是安全的；但如果实现引入了位置相关成分（某些优化按位置重排 KV），键就必须带上前缀哈希链（每块键=父块键+本块内容的哈希——键链天然编码了前缀树）。vLLM 的实现正是哈希链式：**块的键 = hash(父块键 ‖ 本块 token)**——哈希派悄悄长成了树。两派在实现层已经合流，这是读源码时的惊喜之一。

**例 6.1（构造例：3 轮对话的哈希命中走查）**：块大小 4；系统提示 8 token（块 0、1），第 1 轮新增 4（块 2）、第 2 轮新增 4（块 3）。第 1 轮：块 0、1、2 全 miss——全算并入表（三个指纹）。第 2 轮：prompt 16 token，块 0 查表——指纹命中（挂共享块）；块 1 命中；块 2 命中；块 3（新问题）miss——只算这 4 个 token。**第 2 轮的 prefill 从 16 token 缩到 4 token，命中 75%**。第 3 轮照此办理——命中部分逐轮变长。这就是多轮对话的复利。

工程现实里两派还在合流：哈希派的块粒度在变细（可变长块、跨块对齐的尝试），radix 派也在吸收块化存储（树叶挂块而不是裸张量）——本册教学件 v4 取哈希派（块对齐简单、与 v3 块池天然衔接）。两派谁对？都对，各付各的代价。vLLM 的答案（16-token 块哈希、默认开——**平台口径注：16 是 CUDA 阵营的块大小，NPU 侧默认 128，本机观测实验按 128 报**）——这句点名留给下一册（B6-3）：它落在引擎配置层，机制本册已经教完。

## 6.3 收益的形状：什么负载吃多少

前缀缓存的收益强依赖**负载形状**，三种典型场景的画像：

- **多轮对话**：命中部分随轮数增长（第 $r$ 轮约 $\frac{历史}{历史+新问题}$）——轮数越深折扣越大。缺点：不同用户的对话之间无共享（各 hit 各的树）。v4 的实测正属此型（66.7%）：3 条对话各 4 轮、系统前缀 128 对每轮新增 16——到第 4 轮时命中段已占八成以上。缺点：不同用户的对话之间无共享（各 hit 各的树）。
- **few-shot/Agent 服务**：示范或系统提示全局共享——命中率可以极高（提示占总长比例），且**跨用户命中**。这里有一笔多轮对话没有的账：共享块的 refcount 可以到几百（几百个用户同时挂同一个系统提示块）——驱逐决策的效用账从「一条请求的 LRU」变成「全局热度」；热门提示像热门网页，值得常驻。Agent 场景的系统提示+工具表动辄几千 token，全在同一棵共享树下。
- **一次性长文分析**：无重复前缀——命中率零，纯付哈希开销。负载画像里没有重复，就不要开前缀缓存。还有第四型（负向）：**敏感场景的缓存穿透**——多租户服务里用户 A 的前缀不该被用户 B「撞键命中」（信息泄露面）——生产实现给键加租户隔离前缀。缓存不是纯性能问题，它把「谁能看到什么」变成了新问题。负载画像里没有重复，就不要开前缀缓存。

命中率还有一个隐形敌人：**驱逐时机**。缓存块不能无限驻留（显存有限），驱逐策略（LRU/TTL/效用分）决定「下一条请求来的时候它的前缀还在不在」。前缀感知调度因此有双重目标：把相似前缀的请求聚到相近时刻处理（提升命中时的驻留概率），并给高频前缀（热门系统提示）更高的驻留优先级。缓存容量-命中率-驱逐策略的三角，与第 5 章的块池管理合起来就是完整的缓存经济学。还有一个调度侧的联动：**前缀感知调度**（prefix-aware scheduling）——把相似前缀的请求聚到一起处理，既提升命中率（共享块还在缓存里没被驱逐），又让批内前缀对齐（拼批友好）。引擎的调度器把「哪些请求的前缀在缓存里」纳入决策——这是第 7 章调度折中的新维度。

## 6.4 v4 实测：命中率与 TTFT 的折扣率

`engine_v4.py` 在 v3 块池之上加哈希表与引用计数，跑多轮对话负载（3 条对话 × 4 轮，系统前缀 128 + 每轮增量 16，每轮生成 8 token）：

**实物 6.1（v4 前缀缓存读数，出处：本机实测）**

```text
[v4] 3 对话 × 4 轮 | prefill 2016 tok（免算 1344 = 66.7%）| TTFT 首轮 878.8 ms → 末轮 101.9 ms
```

两笔读数分开消化。**命中率 66.7%**：全部 prefill token 中三分之二免算——负载形状的直接兑现（系统前缀+逐轮历史占大头）。**TTFT 折扣 8.6×**：首轮（全算）878.8 ms 对末轮（几乎全命中）101.9 ms——TTFT 从「prefill 长度决定」变成「新增部分决定」。增量前向值得多讲三句——它是命中免算的数学保障。新段第 $i$ 个 token 的注意力要读「全部历史+新段前 $i$ 个」：历史段的 K/V 已经躺在共享块里（gather 即得），新段的边算边入块。mask 因此是梯形而非三角（新 token $i$ 可见 $[0, \text{hit}+i]$）——一个 mask 形状的变化背后是「历史读取」与「新段计算」的分离。**命中段零前向、新段一次前向、attention 全量读取**——三个短语就是增量 prefill 的全部。v4 的实现细节如实交代：命中块的挂载（refcount+1）与未命中段的**增量前向**是代码的核心段；尾块不共享（简化）、跨对话的块回收略（教学版对话内保持存活）。

诚实账：收益再大也只作用于 prefill 段——TPOT 一分不省（decode 每 token 还是全量权重搬运）；显存反而多付一点（哈希表+共享块驻留）。前缀缓存是 TTFT 与 prefill 算力的折扣券，不是全能券。

## 6.5 本章小结

三本旧账在此合销——F10 的上下文主线到服务端以「折扣率」收尾、N6 的 few-shot 经济学兑现成跨用户命中、N7 的账半句落定。带走的心智：**前缀缓存把「历史的计算」变成「历史的登记」——哈希派按块认指纹（简单、块对齐），radix 派按树认亲缘（优雅、任意长）；命中率的本质是负载里重复前缀的占比，TTFT 的折扣率就是命中率**。批处理五部曲至此四部完成，只剩长 prefill 与 decode 同池的干扰账——那是调度章的收官戏。
