# 第 2 章 仓库地形图与阅读路径

## 2.1 拿到一座十七万行的城

上一章收尾说：「兑现它的第一步是拿地图：下一章把这座十七万行的城画成一张可复核的地形图——十五个子包各守什么、一条请求从 HTTP 到 token 要穿过哪十七个文件。」而这张地图背后是 Book6 收束时的整句许诺——「本册每个算法，在那里有一个**点名到类**的模块等着……沿一条请求的生命周期把源码读穿」【Book6 ch13-收束.md#L68，「Book7 主链路门」段原文；模块名经 repos/vllm v0.30.0 核对】。本章兑现第一步。

先掂量这座城的体量。`vllm/` 全包 **2,479 个 .py、972,641 行**——近百万行；但本册的主叙事线住在 `vllm/v1/`：**390 个 .py、169,658 行**，只占全仓行数的 17.4%【证据等级：本仓 wc 实测（阅读锚 v0.30.0，复现命令见 2.2）】。剩下的八成多是什么？`model_executor/`（模型实现库）、`config/`、`distributed/` 等周边——第 10 章讲权重与注册时会进去一小角。单文件之最也在城里等着我们：`vllm/v1/worker/gpu_model_runner.py` **7,664 行**，全仓最大——它是 MRV1 单体，第 7 章的主角之一（也是它被拆到千行级（博文口径 <1,300 行，{厂商自报}，第 1 章）的那段历史的反面主角）。这个体量值得与 Book6 的交付物对一眼：mini 引擎四版，每版单文件数百行；工业引擎同一功能面，十五子包十七万行——**差的两三个数量级里装的不是算法（算法你在 Book6 都推过），是工程**：进程隔离、消息协议、容错、可观测、多后端适配。本册要读的正是这部分「算法之外」的东西。

不拿地图就进城的代价可以算出来：近百万行里与本册主线无关的占八成以上，逐文件读是注意力预算的破产。本章产出四样：**两张图**（地形分层图 2.1、请求穿越图 2.2）、**一张表**（设计文档索引表 2.1）、**一把 grep**（读者的第一个动手件）——它们合起来回答一个问题：**这本书剩下的十二章，每次说「第 N 站」时到底在说什么地方。**

> **最小背景栏**：本章直接使用第 1 章立的双轨口径（源码引用看阅读锚 v0.30.0、实验观察看运行栈 0.27.1+vllm-ascend）；不重教。Book6 的算法账本（调度/分页/前缀缓存/图执行）在第 13 章收束时逐项对账，本章只在图上预留对应关系。

三条带里最值得驻足的是六个**主线大包**——本册每个都能对回一章以上的正文：`attention/`（97 文件 56,336 行，第 9 章）、`worker/`（115 文件 41,919 行，第 7/8 章）、`core/`（15 文件 13,266 行，第 5/6 章的调度器与块池都在这）、`engine/`（15 文件 11,061 行，第 3/4/11 章的前端与进程）、`executor/`（9 文件 3,902 行，第 7 章）、`sample/`（15 文件 5,642 行，第 11 章）。八顶层模块是横切件（余几件的正身见上段）——其中 `request.py`（406 行）里的 `Request` 类是第 5 章调度器的台账对象，顶层不等于边缘。

六包之间还有一条**调用方向线**，先立个粗框（细节逐章拆）：`engine/` 的前端对象收请求 → 跨进程交给 `engine/` 的 EngineCore → 它调 `core/` 的调度器做决策、调 `executor/` 把活派下去 → `executor/` 落到 `worker/` 的 model runner 执行 → 前向里最贵的一段进 `attention/` 的后端 → 采样在 `sample/` 完成、token 沿原路返回。**数据从 engine 进、从 sample 出，中间每包各管一段**——这条线就是图 2.2 十七站的数据流骨架，也是「一条请求的生命周期」这条主叙事线在目录结构上的投影。

## 2.3 生命周期视图：一条请求的十七站

地形是静态的；本册的主线是动态的——一条请求从进门到出门的文件穿越链。图 2.2 把它画成十七个站，在线链与离线链在站 4 前分岔、在站 7 汇入同一个 EngineCore（这棵分岔树的逐跳解剖是第 3 章正菜，本章只立骨架）。每章开篇的「请求现在在哪」都指这张图。

![图 2.2](figures/fig-2-2-lifecycle.png)

图 2.2 一条请求的生命周期十七站（按 v0.30.0 源码自绘，示意级）：上泳道在线链（HTTP→API server→OpenAI serving→AsyncLLM）、下泳道离线链（LLM 类→LLMEngine），站 7 汇入 EngineCore；站 8-9 调度与 KV、站 10-12 执行三层、站 13 采样回身、站 15-17 输出链。站号-章对应色带：ch3=站 1-6、ch4=站 6-8（兼收站 14）、ch5=站 8-9、ch6=站 9、ch7=站 10-12、ch8/ch9=站 12 内、ch10=启动期、ch11=站 13+15-17。

先立一条全书制度：**十七站是本册的坐标系**。后面每一章的开篇都会说「请求现在在第几站」——这不是装饰性导航，是「读者任一时刻都知道我们在引擎的哪里」这条硬要求的落点（三条贯穿线之首的生命周期坐标线）。站号先在此总登记：ch3=站 1-6（入口）、ch4=站 6-8（进程与引擎核，兼收站 14 的消息出）、ch5=站 8-9（调度）、ch6=站 9（KV 配块）、ch7=站 10-12（执行三层）、ch8/ch9=站 12 内（编译图执行与 attention 后端）、ch10=启动相（不在请求时间线上）、ch11=站 13+15-17（采样回身与输出链）、ch12=元层（观测整条线）。

十七站本身值得逐段走一遍（锚全在图 2.2，这里只给段意）。**站 1-6 是前端段**：CLI 与 API server（站 1-2）把 HTTP 变成引擎调用，OpenAI 兼容层（站 3）把协议对象变成引擎输入，`AsyncLLM`/`LLMEngine`（站 4）是前端引擎对象，InputProcessor（站 5）做 tokenize 与线协议封装，core_client（站 6）是跨进程客户端——离线链在这段走的是同一串站的不同变体（第 3 章的两条泳道）。**站 7-9 是引擎核段**：EngineCore 进程收消息（站 7）、调度器每步决策（站 8）、KV 管理器配块（站 9）。**站 10-12 是执行段**：executor 派发（站 10）、worker 进程（站 11）、model runner 组织前向与图执行（站 12，attention 后端嵌在这一站里——第 9 章「站 12 内」的由来）。**站 13-17 是回程段**：采样（站 13——注意它在生命周期上属于执行、在本书叙事上归第 11 章「回身」讲，因为采样出口与 detokenizer 同链）、EngineCoreOutputs 出账（站 14，归第 4 章收）、OutputProcessor（站 15）、增量 detokenize（站 16）、SSE/HTTP 返回（站 17）。站序有个容易读错的地方先钉死：**站 13 的采样在 GPU 侧紧跟前向发生，但「token 变回文本」的最后三站在前端进程**——一条请求要跨一次进程边界才算真正回家，这是第 4 章进程拓扑（process topology，进程间的形状与通道）要解释的第一件事。

站图之外还有一张官方的**进程账**——十七站是文件视角，进程视角的问题是「这些文件跑在几个进程里」。官方设计文档给了一张五行表：

```markdown
| Process Type | Count | Notes |
| - | - | - |
| API Server | `A` (default `DP`) | Handles HTTP requests and input processing |
| Engine Core | `DP` (default 1) | Scheduler and KV cache management |
| GPU Worker | `N` (= `DP x PP x TP`) | One per GPU, executes model forward passes |
| DP Coordinator | 1 if `DP > 1`, else 0 | Load balancing across DP ranks |
| **Total** | **`A + DP + N` (+ 1 if `DP > 1`)** | |
```

【源码：`docs/design/arch_overview.md`#L107-113（表格原文直引），阅读锚 v0.30.0——证据等级：官方设计文档】看什么：Total 那行的公式 `A + DP + N`（DP>1 再加一个协调器）；A 的默认值就是 DP（API server 通常每 DP 秩一个）。文档自己配了两个算例：「1 API server + 1 engine core + 4 GPU workers = **6 processes**」（`-tp=4` 单机四卡）与「4 API servers + 4 engine cores + 8 GPU workers + 1 DP coordinator = **17 processes**」（`-tp=2 -dp=4` 八卡）【arch_overview.md#L117/#L125】。

**例 2.1（toy：进程公式的三步算法）** 构造：给任意一组并行参数，算进程数。三步（输入：TP/DP/PP；输出：进程总数）：

1. 读 DP、定 A：$A$ 默认 $=\mathrm{DP}$（每个数据并行秩一个 API server）；
2. 算 N：$N=\mathrm{DP}\times\mathrm{PP}\times\mathrm{TP}$（每卡一个 worker 进程）；
3. 判协调器：$\mathrm{DP}>1$ 则总数 $+1$，否则 $+0$；合计 $A+\mathrm{DP}+N(+1)$。

两例代入：tp4 → A=1、DP=1、N=1×1×4=4、无协调器 → **6** ✓（与官方算例一致）；tp2dp4 → A=4、DP=4、N=4×1×2=8、+1 → **17** ✓。效果读法：**公式数的是逻辑角色，不是物理进程**——单卡时 worker 角色会被「吸收」进 EngineCore 进程（`vllm/config/parallel.py`#L1010-1011：`world_size == 1` 即用 uniproc executor，driver_worker 进程内直挂），ps 里数出来的是 2 不是 3。这个「角色 vs 进程」的差，第 4 章用一次真 ps 对拍收账。留一道给读者的第三算：`tp2 dp2`（四卡）——按三步走，答案是几？（9。）

图 2.2 是本册被引用最多的一张图——但要让它从「示意图」变成「可复核的账」，还得把每站钉到文件。这就是例 2.2 的任务。

**例 2.2（toy：一条离线请求的文件路径串走查）** 构造：`LLM.generate("The capital of France is", SamplingParams(temperature=0.0, max_tokens=8))`（hf207m，本册大项目的自训模型）。沿图 2.2 走七跳，每跳标输入与输出：

| 跳 | 文件::符号（阅读锚 v0.30.0 实测锚） | 输入 → 输出 |
|---|---|---|
| 1 | `vllm/entrypoints/llm.py::LLM.generate`#L418 | str+SamplingParams → 委托 _run_completion |

## 2.4 设计文档=代码的投影：一张表的两种命运

地形图的第三个产出与「读什么」有关。`repos/vllm/docs/design/` 下有 **30 篇设计文档**（实测清点），是官方写给贡献者的机制说明——比代码好读、比博客准确，本册大量直引都出自这里。但 30 篇里有两种命运截然不同的文档，先看正面的那种：

```markdown
# Attention Backend Feature Support

The priority and feature tables on this page are auto-generated from the
attention backend registry by
`docs/mkdocs/gen_files/generate_attention_backends.py`, based on the checks in
`AttentionBackend.validate_configuration()`.
```

【源码：`docs/design/attention_backends.md`#L1-6（直引），阅读锚 v0.30.0】看什么：这张特性表**不是人写的，是脚本读着注册表生成的**——代码变表就变，永不撒谎。三支柱齐在：①L1-6 自我声明；②生成脚本 `docs/mkdocs/gen_files/generate_attention_backends.py` 在位；③表的源头是 `vllm/v1/attention/backends/registry.py`（一手源码，证据等级高于文档——第 9 章进门）。

反面的那种是**手写文档**——同一目录的 `arch_overview.md` 是全册最好的一篇总览，但它的行级锚已经烂了两处：L157 说 LLMEngine 的代码在 `vllm/engine/llm_engine.py`、L169 说 AsyncLLMEngine 在 `vllm/engine/async_llm_engine.py`（第 1 章敲过：两张都是 7 行别名门牌）；L202 外链 `vllm/config.py#L2036`（config 早已成包，34 个 .py 文件）。两处腐烂不是作者马虎，是手写文档的宿命——代码动、文档不动。教学结论只有一句：**docs/design 里生成式文档可信、手写式文档的行号一律回源码复核——这正是本书行级锚制度（引文档先验是不是投影）的由来。**

## 2.5 姊妹城：vllm-ascend 的地形与三级链接管链

NPU 读者此刻该问的问题：**运行栈里的 vllm-ascend 这座平台插件（platform plugin，经 vLLM 插件体系接入的硬件后端包）是什么形状？**答案有点惊人：`vllm_ascend/` 全包 **587 个 .py、170,346 行**——与 `vllm/v1/` 子树（169,658 行）几乎同量级【证据等级：本仓 wc 实测（repos/vllm-ascend@3b31886）】。平台插件不是薄壳，是一座与主城同体量的姊妹城。分包前列：`distributed/` 65 文件 27,320 行、`ops/` 110 文件 25,290 行、`worker/` 44 文件 15,371 行、`attention/` 18 文件 14,597 行、`_cann_ops_custom/` 47 文件 12,955 行。特别值得记的一个数字是 `patch/`：**60 文件 10,071 行**——全部是对上游代码的运行时补丁（谁在改什么、为什么改、等上游哪个 PR，第 11 章给抽样索引）。这个包的存在本身就是一条机制事实：**NPU 后端对上游的跟随不是「适配层」而是「持续维护税」**——上游每重构一次，这 60 个补丁就要重新对齐一次（第 5 章会见到这类「维护条件写在门口」的活样本——一个调度器副本的英文自注，原文见彼处直引）。

这座城怎么接管主城的？一条**三级链**，每一环都有源码正身。第一环在打包清单里——`setup.py` 的 entry_points：

```python
    entry_points={
        "vllm.platform_plugins": ["ascend = vllm_ascend:register"],
        "vllm.general_plugins": [
            "ascend_kv_connector = vllm_ascend:register_connector",
            "ascend_model_loader = vllm_ascend:register_model_loader",
            "ascend_service_profiling = vllm_ascend:register_service_profiling",
            "ascend_model = vllm_ascend:register_model",
        ],
        "ms_service_metric.providers": [
            "vllm-ascend = vllm_ascend.observability:get_metric_provider",
        ],
    },
```

【源码：`repos/vllm-ascend/setup.py`#L518-529（节选自打包配置段），运行栈 vllm-ascend 0.27.1rc1——安装包≡构建源，无需版本框注】看什么：核心行是 `"vllm.platform_plugins": ["ascend = vllm_ascend:register"]`——pip 安装的那一刻，「世界上有个叫 ascend 的平台插件」就写进了发行版元数据。vllm-ascend 接管 vLLM 的第一句话不在任何 .py 里，而在打包清单里。顺带数一数：除平台插件外还注册了四个 general_plugins（connector/model_loader/service_profiling/model）与一个指标 provider——**vLLM 侧五把插件钥匙，外加一个指标体系的锚点**（第 10 章大项目与第 11 章 patch 叙事的伏线）。

第二环是平台类的自报家门——`NPUPlatform` 的类属性：


【源码：`vllm_ascend/platform.py`#L87-97，运行栈 vllm-ascend 0.27.1rc1】看什么：这是一张平台身份卡，五个属性各答一问——`device_type="npu"`（我是谁：torch dispatch 靠它把张量运算路由到 NPU 后端）；`dispatch_key="PrivateUse1"`（走哪条路：torch 为第三方后端预留的私有调度键，torch-npu 的挂载点）；`device_control_env_var="ASCEND_RT_VISIBLE_DEVICES"`（怎么选卡：与全书 NPU 选卡纪律**同一个环境变量的源码正身**——你在每个实验件里写的 `ASCEND_RT_VISIBLE_DEVICES=<卡>` 就是从这行读出来的）；`simple_compile_backend="eager"`（编译怎么退：行内注释即官方原文 `# Disable torch.compile()`——第 8 章的门牌，本章只指门）；`_enum=PlatformEnum.OOT`（什么身份：out-of-tree，不在上游树内的官方扩展位）。

## 2.6 阅读方法：三层法的第一层

地图、站表、文档索引都齐了，收束成本章的方法论。读引擎源码的三层法是一组侦探三问：**它在哪**（静态地形——不跑引擎就能回答）→ **它在动吗**（动态跟跑——日志/断点/单进程模式）→ **我理解对了吗**（对拍验证——读数与推演互证）。本章交出第一层的全部家当：三张图、一张表、一把 grep。后两层是第 12 章的正菜——到那时我们会给引擎接上仪表，把地图上的每条路跑亮、并用读数证明你没看错（那里才会出现具体的观测开关与变量名，本章不提前泄露）。

三层法的对立面值得点名：**按目录字母序读源码**——`git clone` 之后从 `attention/` 开始逐目录扫，这是大多数读者本能的读法，也是大多数「读不下去」的原因：字母序与重要性无关、与调用链无关，读到第三个包时你已经忘了前两个包为什么存在。本册的读法主张只有一条：**按数据流读**——先问「一条请求路过哪些文件」（图 2.2），再按站进包；目录结构用来「住」，不用来「走」。

第一层还有一条私房手艺值得现在就立：进任何子系统前先读「**0 号文件**」——`vllm/envs.py`（全部 `VLLM_*` 环境开关的名录）与 `logger.py`（日志从哪来）。开关面是引擎的「可调旋钮总表」，后面章节每次出现一个新开关，都能在这份名录里找到默认值与出处。

第一层的收尾检验是一个能当场做的练习——「我要看的代码住在哪个进程」。

**例 2.3（toy：三个符号的进程落籍）** 构造：给你三个符号，凭图 2.2 判断它们各住在哪个进程。输入：`AsyncLLM.generate`（`vllm/v1/engine/async_llm.py`#L638）、`EngineCore.step`（`vllm/v1/engine/core.py`#L589）、`Sampler.sample`（`vllm/v1/sample/sampler.py`#L244）。三步：①先看包——engine 包的前端段还是执行段？sample 包挂在谁的调用链下？②再对图 2.2 的三段（前端段站 1-6/引擎核段站 7-9/执行段站 10-12）；③落籍。答案：`AsyncLLM.generate` 在**前端进程**（API server 或你的离线脚本里）；`EngineCore.step` 在**引擎核进程**（独立的 EngineCoreProc）；`Sampler.sample` 在 **worker 侧**——uniproc 时与 EngineCore 同进程、multiproc 时在独立 worker 进程（第 4 章的 ps 实测正是这三种落籍的物理印证）。效果读法：**符号的包名就是它的户籍区**——断点打不打得中、日志前缀对不对得上，第一道判断都靠这张落籍表；第 12 章断点三法的「先问代码在哪个进程」，问的就是这道题。

欠一笔边界声明：本章的 wc/grep 实测全部落在**阅读锚 v0.30.0**；运行栈 0.27.1 侧的对应数字（如 v1/ 为 331 个 .py）有差异但结构同构——两轨差异的正式清单在卷首，逐章遇到才框注，不提前背包袱。
