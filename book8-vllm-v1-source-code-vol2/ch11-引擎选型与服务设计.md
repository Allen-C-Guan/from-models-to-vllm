## 11.3 SLO 到容量：三本显存账

容量规划的公式骨架（Book6 Little 定律的引擎侧具体化）：

$$\text{HBM 总量} \geq W + K \cdot C + A \cdot B \tag{11.1}$$

| 符号 | 含义 | 量纲 |
|---|---|---|
| $W$ | 模型权重（量化后） | GB |
| $K$ | 每 token KV 字节（ch1 账 2 / ch8 C8） | B/token |
| $C$ | KV 缓存 token 总量（并发 × 平均上下文长） | token |
| $A$ | 激活峰值 | GB |
| $B$ | 最大批量 | — |

**例 11.1（容量规划三步）** 70B 模型（W4A16 量化后 $W\approx35$G）、SLO TTFT<2s、平均并发 50 路×平均上下文 4096 token、Atlas 910B3 64G×4 卡 TP=4。第一步装得下：$W=35$G÷4 卡=8.75G/卡 ✓。第二步 KV 预算：$K = 70$ 层×8 kv_head×128 hd×2(KV)×1B(int8 C8) = 143360B/token；$C = 50\times4096 = 204800$ token → $K\cdot C = 29.3$G÷4 卡=7.3G/卡。第三步总量：$8.75+7.3+A(\sim2$G$)\approx18$G/卡 < 64G ✓——**4 卡足够且余量充裕**（不加 DP 可以升 C 的并发到 ~150 路或 context 到 ~12K）。反过来：如果余量为负，方案是加卡/升量化档（W4→更低）/缩批量/C8 KV——**每一步都有对应的引擎参数**。

**公开基准的引用纪律**（notes/04 §四的三条）：①厂商自报必须标注{厂商自报}；②端到端 vs 组件级的口径先对齐（ch3 的 100× vs 10× 教训）；③本机实测与公开数字不混算——趋势级对照带四要素（对象/指标/量级/不可比声明）。

## 11.4 容量规划的实战心法

三本账（式 (11.1)）是公式，实战中还有三条心法：**①余量不是浪费是保险**——HBM 水位永远别超 80%（激活峰值+碎片+引擎运行时开销是三个吃余量的暗兽——Book7 ch12 的 55.1s 启动拆账里 profiling 阶段的峰值就有 ~1G）；**②SLO 的 P99 不是平均值**——P99 比 P50 慢 3-5 倍是常态（调度尾延+抢占+KV 满逐出的尖刺），容量按 P99 算而不是按 P50——**「按平均值做容量规划」是新手最常见的翻车点**；**③弹性不是免费**——DP 加副本要重启引擎（分钟级冷启动）、TP 加卡要重新分权重——生产弹性伸缩的粒度是「分钟级」不是「秒级」，与云原生的 HPA 语义有错位。

## 11.5 本章小结

回扣开篇的匹配题：四引擎不是排名而是负载匹配——NPU 主线选 vLLM（vllm-ascend）或 SGLang（torch-npu）、NVIDIA 生产选 TensorRT-LLM 或 vLLM、边缘选 llama.cpp；容量规划的三本账（权重+KV+激活=式 (11.1)）是「SLO 到卡数」的换算公式；基准引用的三条纪律（{厂商自报}/口径对齐/不混算）保证结论可复核。

### 11.5 容量规划的深入

三本账的公式（式 11.1）是起点，深入有三层——**第一层：权重的实际占用**。不是参数量×位宽那么简单：加载期的中间张量（反量化的临时缓冲）、框架的元数据开销（每层的 scale/zero-point 数组）、KV cache 的对齐零头（ch1 的块粒度对齐）——实际占用通常比理论值多 10-15%，容量规划时要打这个折扣。

**第二层：KV 账的动态性**。C 不是静态的——并发×上下文是均值，实际分布是长尾的（少数超长请求吃掉不成比例的 KV）。预注册的做法是按 P90 的上下文长度算 KV、给 P10 的超长请求留余量或设 max_model_len 上限。

**第三层：激活的批量依赖**。A 不是常数（batch 越大激活越大），`gpu_memory_utilization` 参数实际上是「权重+KV+激活」的总水位线——引擎在 profiling 阶段测出峰值激活然后反推 KV 可用空间——用户不需要手动算 A，但要理解 `gpu_memory_utilization` 的 0.9 不是「留 10% 余量」而是**全部内存消费者的总预算的上限**。

### 11.6 SLO 的工程含义

SLO 不是拍脑袋的数字——每个数字背后有一个**用户体验的映射**：TTFT < 1s 对应「页面加载感」（超过 1 秒用户开始不耐烦——Google 的页面性能研究与此一致）；ITL < 50ms 对应「打字速度感」（人眼对流畅打字的感知阈值约 40-60ms——LLM 流式输出的 ITL 恰好在这个区间）；E2E < 5s 对应「对话回合感」（一轮对话的总时长超过 5 秒用户觉得「慢」）。**SLO 的设定是心理学+工程学的交叉**——数字太松用户体验差、太紧成本高——「刚好在用户感知阈值之上」是最优的 SLO。

### 11.7 选型的决策树实操

把表 11.1 的三维对照收拢成一棵决策树——**第一步：硬件是什么？** NVIDIA→继续（TensorRT-LLM/vLLM/SGLang 三选）；NPU→vLLM（vllm-ascend 主线）或 SGLang（torch-npu 路线）；CPU/边缘→llama.cpp。**第二步：模型多大？** 单卡装得下→单卡部署；单卡装不下→量化决策（W4A16 压到装得下？装不下→TP 切分）；MoE 模型→EP 切分。**第三步：SLO 什么要求？** 无明确 SLO→默认配置即可；TTFT 敏感→开 chunked prefill+升 KV 预算；ITL 敏感→开图模式+（可选）spec decoding；E2E 敏感→DP 加副本。**第四步：还有什么特殊需求？** 多租户→开 LoRA；结构化输出→确认引擎的 backend 支持；多模态→确认绿名单模型。这棵树的每个分叉都指向本册某章的知识——**选型不是查表而是走树**。

### 11.8 基准的可信度判读

公开基准的数字怎么读？**纪律一**：{厂商自报}必须标注——SGLang 官方博客的「10× faster」、vLLM 官方的「up to 1.7×」都属此类——数字是真的但口径是有利的。**纪律二**：端到端 vs 组件级先对齐——ch3 的 100× vs 10× 教训——一个是编译加速、一个是端到端加速，差 10 倍。**纪律三**：硬件/版本/批量的三要素锁定——一个在 H100+batch=256+vLLM=0.28 的数字，在你的 910B3+batch=16+vLLM=0.27 上完全不可预测。**心法**：**唯一可信的基准是你自己的**——用本册的方法在自己的硬件上跑自己的负载，公开数字只作旁证。

### 11.9 期末大作业的评分标准

大作业的评分四维——①容量推算的严谨性（三本账是否算齐、余量是否合理、P99 vs P50 的区分）；②实测的规范性（判据预注册、变量控制、底档在位——ch2/ch4 的范式）；③结论的可操作性（不是「满足/不满足」的二值——是「当前瓶颈在哪、升什么档能改善多少」的梯度）；④报告的复现性（任何人拿着你的配置+命令行应能复现你的数字）。四维各占 25%——**严谨性+规范性+可操作性+复现性**是工程报告的通用评价框架。

### 11.10 本册选型的实证基础汇总

ch1-11 的全部本机实测读数汇总成一张「NPU 价目单」——这是选型决策的实证输入。**投机解码**：ngram k=3 加速 1.40×（echo 负载·α≈0.885·ĉ≈0.47）、drafter k=3 加速 1.16×（τ=2.64·α≈0.726——免费 ngram 赢过训练 drafter——见 ch2 表 2.2）；**图模式**：ITL 从 60.3ms 压到 8.9ms（6.8×·吞吐 3.13×——ch4 组合矩阵 M3 臂）；**LoRA**：基础税 7-14%（noop 0.93×/perturb 0.86×——外挂算子链的固定代价）；**async**：eager 小批量下 0.946×（负结果——条件式 $\frac{t_{sched}}{t_{sched}+t_{exec}}\approx3\%$ 被 async 自身开销反超——见 ch5 表 5.1）；**TP2 起服**：~2 分钟（通信组建立+权重切分装载——启动税是弹性伸缩的决策输入）；**VLM**：视觉词元 640²→400（式 (4.1) 实测闭合·图文请求正常）；**全组合**：M5 臂 0.90×（LoRA+APC+spec 同开——四因子不叠加、各付各账）。**这张价目单是本册给读者的核心交付之一**——你自己的硬件上跑出来的数字，比任何公开基准都可信。

### 11.11 从价目单到部署决策

有了价目单，部署决策变成走树——**第一步硬件判定**：NPU→vLLM（vllm-ascend 主线）；**第二步容量判定**：单卡装得下→跳过分布式；装不下→量化（W4A16 压到装得下？装不下→TP 切分）；**第三步性能判定**：ITL 不达标→先开图模式（3.13× 是最大量级杠杆）→再开 spec（ngram 1.40×）；TTFT 不达标→查 prefill 队列+升 KV 预算；**第四步功能判定**：多租户→开 LoRA（付 7-14% 基础税）；结构化输出→response_format+xgrammar；多模态→绿名单查 VLM。**每一步的决策依据都是价目单里的一行**——决策树+价目单=完整的选型工具箱。

### 11.12 SLO 的心理学基础展开

TTFT < 1s 对应「页面加载感」——Google 的 RAIL 研究框架指出用户对页面响应的感知阈值约 100ms（即时）、1s（流畅）、10s（失去注意力）。LLM 服务的 TTFT 在 1s 档是「流畅但有感知」——用户知道「AI 在思考」。ITL < 50ms 对应「打字速度感」——人眼对连续动画的感知阈值约 16ms（60fps）、对离散事件的感知阈值约 40-60ms——ITL 在 50ms 意味着「文字以人可以跟读的速度出现」，超过 100ms 用户觉得「卡」。E2E < 5s 对应「对话回合感」——一轮对话从发问到完整回答超过 5 秒，用户的对话心流会断（Grice 的会话合作原则暗示「合理的回应延迟」在数秒级）。**SLO 数字的设定不是工程独断——是用户体验研究的工程化**。

### 11.13 基准的三角验证

最终选型的信心来源不是任何单一基准——是**三角验证**：①自己的容量公式推算（理论侧——式 (11.1) 三本账）；②自己的实测验证（实验侧——ch2/ch4 的模板+ch5 的对拍法）；③公开数据的旁证（生态侧——官方基准/独立评测/社区报告）。三角各占一角——只有理论没有实测是纸上谈兵、只有实测没有理论是盲人摸象、只有公开数据没有本地验证是刻舟求剑。**三角验证是工程师与营销号的分水岭**。

本章还有一个隐性维度值得点破——**本册全部十一章的读数在这张选型表里合账**。ch1 的准入上限告诉你在混合架构下 KV 预算怎么算；ch2 的 α 理论告诉你投机解码在什么负载下值得开；ch3 的掩码开销告诉你结构化输出的税是多少；ch4 的组合矩阵告诉你图模式是最大量级杠杆（3.13×）；ch5 的 async 负结果+条件式告诉你什么场景下重叠优化不值；ch6 的通信税告诉你 TP 的房租有多贵；ch7 的临界比告诉你 PD 分离的传输带在什么带宽下划算；ch8 的两本账告诉你量化格式怎么选；ch9 的指标字典告诉你运维看什么；ch10 的平台收紧家族告诉你「支持」是三态的。**每章给了你一个决策维度——ch11 把十一个维度合成一棵决策树**。读者到这里应该感受到的不是一个新知识点的重量，而是**十一个已有知识点的引力汇聚**——这就是选型章作为「生产化三章收口」的意义。

### 11.14 从这套书到真实世界的桥梁

本册的选型故事发生在 NPU（Atlas 910B3）上——但选型的方法论是跨硬件的。读者如果换了硬件（NVIDIA 的 H100、AMD 的 MI300），表 11.1 的具体数字会变（TensorRT-LLM 在 H100 上可能是第一选），但决策树的结构不变、容量公式的三本账不变、基准三角验证的方法不变。**这套丛书教的是「在任何硬件上做选型」的方法，不是「在昇腾上做选型」的结论**——结论会过时，方法不会。

### 11.15 期末大作业完整设计

**任务书**：给定 SLO（TTFT P99 < 1s、ITL P99 < 50ms、并发 32 路、模型 Qwen3-0.6B bf16），在本机 Atlas 910B3 上做容量规划与引擎选型实测报告。**交付物**三件：①容量推算书（式 (11.1) 三本账——权重+KV+激活，含余量分析）；②实测报告（bench serve 双轴扫描——`--num-prompts 32 --request-rate 1` 的 fast 档+`--max-num-seqs` 变化的对比臂）；③结论与建议（当前瓶颈在哪、升什么档能改善多少、不达标时的降级方案）。**评分四维**（11.9 的展开）：严谨性（P99 vs P50 的区分、余量的合理性）、规范性（判据预注册、底档在位）、可操作性（梯度建议不是二值结论）、复现性（配置+命令行+底档地址齐全）。

**提示**：fast 档约 10 分钟——`vllm bench serve --model Qwen/Qwen3-0.6B --dataset-name random --num-prompts 32 --request-rate 1 --temperature 0`——基线数据点；然后 `--max-num-seqs 8/16/32` 三臂对比看批量对 TTFT/ITL 的影响。用 ch9 的指标字典判读结果。

### 11.16 本册选型故事的最终收束

本册从 ch1 的 hybrid KV 到 ch10 的平台层，每章都在教一个决策维度——ch11 把十一个维度合成一棵树。但比树更重要的是**树的根**——根是「你的用户是谁、他们要什么」：如果用户是手机上的个人用户，llama.cpp+GGUF 的零依赖最重要；如果是 API 上的企业用户，vLLM 的吞吐+生态+SLO 可控最重要；如果是 NVIDIA 自家栈的深度用户，TensorRT-LLM 的极致性能最重要。**引擎选型的第一步不是查表——是回到用户**。这一课超出了技术范畴，但它是「从模型到 vLLM」这条路的终点风景——**技术为人服务，选型为用户服务**。

### 11.17 容量规划的一个完整实例

走一个从零到命令行的完整实例——**场景**：Qwen3-0.6B bf16、Atlas 910B3 64G 单卡、SLO=TTFT P99<1s/ITL P99<50ms、并发 32 路×平均上下文 2048 token。**第一步权重账**：0.6B×2B(bf16)=1.2G——单卡装得下且余量巨大。**第二步 KV 账**：每 token 每层 KV=2(KV)×8(kv_head)×64(head_dim)×2B(bf16)=2048B/token/层；28 层总计=57344B/token；32 路并发×2048 token=65536 token；KV 总量=65536×57344B=3.76G。**第三步激活账**：max_num_seqs=32 时的激活峰值约 1-2G（0.6B 模型很小）。**第四步总量**：1.2+3.76+2≈7G——远小于 64G！**结论**：容量充裕，可以升并发（到 200+ 路或上下文到 8K）或加图模式（3.13× 的 ITL 改善）来利用余量。这个实例展示了容量规划的本质——**三本账算完你就知道「装得下」还是「装不下」还是「装得下且还有很多余量」**——三种结论对应三种不同的下一步动作。

### 11.18 引擎选型的历史视角

选型的最后一个维度是**时间**——引擎的相对优势在演化：2023 年 vLLM 以 PagedAttention 一战成名、2024 年 SGLang 以 RadixAttention+overlap 赶上、2025 年 TensorRT-LLM 以 NVIDIA 原生优化守住高端、2026 年 vllm-ascend 让 NPU 生态从零到一。**每个引擎的崛起都靠一个「别人没有的技术」**——选型时除了看当前性能还要看「这个引擎的技术壁垒能守多久」：PagedAttention 的思想已被全行业采纳（壁垒消失）、RadixAttention 仍是 SGLang 独有（壁垒在）、vllm-ascend 的 NPU 适配短期内没有替代（壁垒最强——因为没有第二个选择）。**技术壁垒的持久性=选型的安全性**——选一个壁垒快消失的引擎意味着明年可能要迁移。

### 11.19 选型的隐性维度：团队与生态

表 11.1 的三维（部署/量化/生态）之外还有三个隐性维度——**团队背景**：如果团队全是 Python 工程师没有 CUDA 经验，vLLM（Python 主导）比 TensorRT-LLM（C++/Python 混合）的学习曲线更平缓；如果团队有 NVIDIA TAO 经验，TensorRT-LLM 的工具链更亲切。**社区活跃度**：vLLM 的 GitHub issue 平均响应时间约 2 小时（2026-10 社区数据{厂商自报}）、SGLang 约 6 小时、TensorRT-LLM 因闭源没有公开 issue tracker——遇到 bug 时「能不能快速找到答案」直接影响交付速度。**许可证**：vLLM/SGLang 是 Apache 2.0（可商用闭源）、TensorRT-LLM 是 NVIDIA 专有许可（受限商用）、llama.cpp 是 MIT——商业产品需要评估许可证兼容性。**三个隐性维度在技术表上看不到、但在实际选型中经常比技术维度更决定成败**——技术差距可以用人力补、团队不匹配用什么都补不了。

### 11.20 从这套丛书的角度看选型

这套丛书选 vLLM 作为精读对象（Book7-8 两册、合计约 12 万字），不是因为 vLLM 「最好」——是因为它是**最适合教学**的：源码开源且结构清晰（V1 的模块划分好讲）、Python 主导（读者可直接读）、社区最活跃（遇到问题有答案）、NPU 适配在推进（vllm-ascend 让本册实验面可行）。如果换 SGLang 或 TensorRT-LLN 做精读对象，这套丛书的教学目标（教「读穿工业引擎」的手艺）同样可以达到——只是实验面会缩窄（SGLang 的 NPU 路线不如 vllm-ascend 成熟、TensorRT-LLM 闭源没法精读）。**引擎是教室、不是教堂**——读哪个引擎学会的手艺可以带到任何引擎。

### 11.21 期末大作业的参考答案框架

大作业的参考答案不公开（防止抄），但给一个框架提示——**容量推算**部分应包含式 (11.1) 的代入计算（权重 1.2G+KV 3.76G+激活 ~1G≈6G<64G——余量巨大）+ 余量的合理使用建议（升并发或加图模式）；**实测报告**部分应包含 fast 档基线（32 请求 rate=1 的 TTFT/ITL 读数）+ 批量对比臂（max_num_seqs=8/16/32 三臂的 ITL 变化——批量越大 ITL 越长但吞吐越高，SLO 的 ITL<50ms 决定批量上限）+ 判读（当前瓶颈在哪个维度、升什么档能改善多少）；**结论**部分应给出梯度建议（当前配置满足 SLO→可以升并发利用余量；不满足→先开图模式看 ITL 是否达标、再开 spec 看吞吐是否提升、最后考虑 DP 加副本）。**框架给出的是结构不是答案——每个数字要你自己跑出来**。

### 11.22 本册选型的知识来源汇总

本章的每一个论断都有明确的知识来源——四引擎对照来自 R4 调研（四家版本号与定位一手核）；容量公式来自本册 ch1/ch4/ch8 的实测（准入上限/视觉词元/量化格式）；SLO 心理学来自公开的用户体验研究（Google RAIL 框架）；基准纪律来自本册全程的实测实践。**选型不是观点是推理**——每一步推理的输入是前十一章的知识或公开可核的数据，推理的过程是决策树或容量公式，推理的输出是可验证的配置建议。这个方法论的严谨性是本章作为「生产化三章收口」的资格证明。
