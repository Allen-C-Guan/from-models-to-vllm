## 11.1 开篇：敢承诺什么

生产化三步到终点：可观测（ch9——知道发生了什么）→平台边界（ch10——知道站在什么地基上）→**选型与容量（本章——知道敢承诺什么）**。Book5 收束章的决算表把这笔账挂到这里（B5-7 引擎选型→Book8 第 11 章——Book5 ch12-收束 表 12.2 行）；Book6 ch07 的容量规划句同款到期（「容量规划……→ Book8 第 11 章」）。给服务定 SLO（TTFT 上界/ITL 上界）是销售的承诺、给运维的红线——本章的问题：**给定一批硬件与一类负载，怎么选出引擎、配上量化、算出并发、签下 SLO？** 这是全书的总应用题：前面所有章节的账本（容量公式/部署矩阵/指标面/平台约束）在此汇成一张决策表。值得点破的是本章与前十章的视角差：前十章是「引擎内部怎么工作」（显微镜），本章是「引擎之间怎么选、服务整体怎么设计」（望远镜）——两镜共用同一套账本语言（字节/毫秒/块数），这也是丛书把源码剖析与生产化放进同一册的用意：**懂内部的人做选型，账算得比只看 benchmark 的人深一层**（知道数字是哪来的、口径是什么、什么时候会翻）。

给「选型」这个词先卸掉一个误解：它不是一次性的采购决策，而是**随负载演进的持续决策**——今天 32 并发的最优配置在流量涨十倍后可能全面失衡（KV 账最先爆）、模型换代后量化路线也要重选（新架构常有新的量化友好位）。所以本章教的与其是「怎么选」不如是「怎么重选」——把选型做成可重复的流程（画像→对表→算账→反推→验证），每次流量/模型/硬件任一变化就重跑一遍。三段定位：专题=引擎选型与服务设计；站段=横览全站（选型是元层决策）；模块=前十章的全部表格（表 8.1 部署矩阵/表 3.1 后端面/表 10.1 平台面/表 9.1 指标面——本章是表格的汇流处）。产出：四引擎对照（表 11.1）、容量公式与算例（例 11.1）、本机价目单（表 11.2）、八维决策表、期末大作业。

> **最小背景栏**：Book6 ch07 的容量规划三本账（权重/KV/激活）已立公式；SLO 两参数（TTFT/ITL）的语义=Book6 ch02；本章只做「前账新用」——把散在各章的表汇成决策流程。

选型时间线的实用建议一句：这四家都在快速迭代（本书写作期内 vLLM 出了 v0.31/v0.32rc、SGLang 到 v0.5.21、TRT-LLM 在 rc 线上滚动）——**对照表有半衰期**，用它做初筛后必须回官方渠道核当期版本（表头的版本号就是这张表的「保质期戳」）。四家之外的引擎（MNN/MLC-LLM/原生 transformers serve 等）在特定生态位也有价值，但超出本书的对照范围——选型方法论（查表→算账→反推）是通用的，表本身不是。

SGLang 的 Ascend 双路线值得半段（ch10 等价路径的又一实例）：**torch-npu 路线**（现行——与 vllm-ascend 同样骑在 torch-npu 上）与 **MindSpore 路线**（华为自家框架为底）——同一引擎两套地基，「选 SGLang on NPU」其实是两个选择。这种「同引擎多地基」的分裂在 CUDA 世界不存在（NVIDIA 是唯一地基），是 NPU 生态的常态景观——选型时必须问清走的是哪条路线（版本/特性/支持面都不同）。

## 11.3 容量公式与算例：先算装不装得下

选型的第一道硬门槛是容量——Book6 ch07 的三本账在此立成式：

$$M_{\text{deploy}} \approx \underbrace{P_{\text{act}} \cdot b_w}_{\text{权重}} + \underbrace{C \cdot n \cdot b_{kv}}_{\text{KV}} + \underbrace{A_{\text{act}}}_{\text{激活}} \tag{11.1}$$

| 符号 | 含义 | 取值例（Qwen3-30B-A3B） |
|---|---|---|
| $P_{\text{act}}$ | 参数量 | 30B（激活 3B——MoE 只算装载不按激活折） |
| $b_w$ | 每参数字节 | bf16=2 / W8A8=1 / W4A16=0.5 |
| $C$ | 并发路数 | 16 |
| $n$ | 每路上下文长 | 4,096 |
| $b_{kv}$ | 每 token KV 字节 | 98,304B（48 层×4 KV 头×128×2×2B——ch8 判断题的数字） |
| $A_{\text{act}}$ | 激活/缓冲 | 经验值 ~2-4G（graph 池/工作区） |

用人话说：**权重磅（装不装得下）+ KV 棒（装下之后能伺候几路）+ 激活零头**——三棒里权重磅由量化档决定（表 8.1 换档）、KV 棒由模型架构与并发决定、激活零头由引擎配置决定——三棒加起来不超过卡数×每卡显存，才谈得上服务。三个容易算错的细节先点破：其一，MoE 的 $P_{\text{act}}$ 按**总参**不按激活参算（权重是全装载的——ch8 例 8.2 的教训：专家权重占总参 87%但一个不能少装）；其二，$b_{kv}$ 按模型 config 直算（层数×KV 头数×head_dim×2×dtype 字节——ch8 例 8.1 与判断题各算过一遍的正身公式）；其三，激活零头别省（图模式池/工作区/通信缓冲在实际部署里 2-4G 起步——省了它会在 burst 时翻车）。

**例 11.1（Qwen3-30B-A3B 四卡三步账）** 构造：4×Atlas 910B3（4×64G=256G）、并发 16 路×4,096 上下文、要求 ITL<50ms。输入三步：
①权重三档：bf16=60G（4 卡各 15G——已占每卡 23%）；W8A8=30G；W4A16=15G（compressed-tensors 路线，表 8.1 查得）；
②KV 账：$16\times4096\times98{,}304\text{B}=6.4\text{G}$ 总量（bf16），**C8 减半=3.2G**（但 C8 需 ModelSlim 产制检查点——ch8 阅读面，如实注：本机无法自产，选它=接受外购检查点的供应链）；分摊 4 卡每卡 1.6G/0.8G——注意 MoE 的 KV 按**全部注意力层**算（48 层层层有 KV——只有 FFN 被专家化了，「按激活层数算 KV」是常见手误）；
③合计（W4A16+bf16 KV，总量口径）：15G+6.4G+激活≈4G=25.4G 总 → 每卡 ~6.4G——**装得下且余量巨大**；若 bf16 权重：60G+6.4G+4G=70.4G 总 → 每卡 ~17.6G——也装得下但余量薄（burst 并发会触逐出）。
输出读数再细一步（ITL 的账）：decode 单步访存量≈权重字节（30B×b_w）；带宽取本机 microbench 实测口径（910B3 D2D 稳态 ~1.19TB/s【Book6 ch01 表 1.2 定谳——官方无带宽规格，以实测为准】）——bf16 档单步下界 ≈60G/1190GB/s≈50ms（**贴线偏险**）；W8A8≈25ms；W4A16≈12.6ms（达标余量大）——**ITL<50ms 的 SLO 在这个模型上直接排除了 bf16**，容量够不够之外又多了一层带宽账。输出读法：这个负载下三档量化「能跑」的分野在余量与 ITL——W4A16 的 15G 权重把带宽压力也降了 4 倍（decode 是带宽受限型——ch8 的账），ITL<50ms 的 SLO 最稳；**容量公式回答「装不装得下」，性能面（下一节的价目单）回答「跑多快」**——两问都要过才算选型完成。（位置：数字=ch8 判断题的正式化——跨章联动账。）
容量公式的三种「不够」各有药方（回前章查表）：权重超了→量化（表 8.1——W4A16 把磅压到 1/4）；KV 超了→三选（C8 压字节/ch1 混合钉层/ch9 offload 搬走——KV 四省法全部可用）；激活超了→降图模式档位或 batch 上限。**「不够」的诊断本身就是选型信息**——权重型不够是量化问题、KV 型不够是架构问题（该换滑动窗/混合架构的模型了——ch1 的 0.941× 负结果说明这条路要挑模型）、激活型不够是配置问题。

读法两句话：正向读——每个数字都是「加了什么特性、付/赚了什么」的单因子读数（表因此可当「特性价目字典」用）（图模式 3× 是最大杠杆、spec 的收益看 workload、结构化是百分之十几的税）；反向读——**价目单的口径极其严格**（同模型/同卡/同 seed/贪心/eager 除特别注明），跨行比较只能看趋势不能算合成（「图+spec+结构化」的合成账要像 ch4 的 M5 那样单独跑）。

三个消费场景示范这张表的正确用法。**场景一（预算选型）**：「ITL 要压到 10ms 内」——查表见 eager 档 ITL 59ms 起、图模式 8.9ms 达标——结论：图模式是必选项不是可选项，预算里要把图捕获的启动时间（Book7 的 84s→159s 账）算进去。**场景二（特性决策）**：「要不要开 spec？」——查表见 ngram 加速 1.40×（echo workload@207M）、ch2 的 random 臂翻车记则警告「猜得准是联合属性」（弱训练模型分布平→什么都好猜，正反而失真）——结论：先做 workload 分析（重复率）再决策，别拿别人的加速比自己 的负载。**场景三（容量核算）**：「VL 服务的 TTFT 预算」——查表见图文首 token 含 402 视觉词元（约等于 400 token 的 prefill 量）——结论：VL 的 TTFT SLO 要按「文本+图片入场费」双口径定，纯文本的 SLO 直接套会违约。三个场景的共同点：**价目单给的是锚点，决策要回负载形态**——这也是本册「判据预注册+负结果如实」的方法论在选型层的投影。

这张表也是**评估任何新引擎的方法模板**：拿同样的负载族打同样的单因子臂——价目单可比的唯一前提是口径对齐（模型/卡/seed/温度/图档全对齐——差一项就只能趋势级对照）。

一个常见的选型陷阱在此立牌：**「benchmark 最高的引擎」不等于「你的负载下最高的引擎」**——公开 benchmark 多用高并发吞吐负载（照顾大集群买家），而你的负载可能是低并发延迟型（在线助手）或突发混合型（办公高峰）——三类的最优引擎可以完全不同。正确做法是把 ch9 的指标字典当成你的负载画像工具（生产上先采一周 `/metrics`：并发分布/prompt 长度分布/命中率的真实形状），再拿画像去对表 11.1 的引擎生态位——**负载画像在先、引擎对照在后**，顺序反了就是拿别人的尺子量自己的脚。

## 11.5 SLO 反推：从承诺倒推配置

容量公式正向算（配置→能不能），SLO 反向算（承诺→该什么配置）。用人话说：先问「客户能忍受多慢」，再倒着推出「该买几张卡、开什么量化」——而不是先买卡再看看能多快。先立一个反例立感：拍脑袋承诺「平均 50ms」的服务，在长尾上会 Double（平均值 50 的分布 P99 可以到 500——重尾是 LLM 服务的常态：批大小波动/逐出重排/前缀 miss 三源叠加）。所以方法的第一步就是戒掉均值思维。三步：**①定 SLO**——TTFT P99 与 ITL P99（两参数定约，百分位不定均值——尾部才是用户感受）；**②反推瓶颈**——ITL SLO ÷ 模型单步时延=可容忍的每步开销预算（图模式的开销、spec 的验证批放大、结构化的掩码税都从这个预算里扣）；TTFT SLO 减去排队时间的预算给 prefill（chunked 的步长选择、并发上限由此定）；**③反推容量**——并发上限×每路 KV=KV 总量，代入式 (11.1) 验算显存——不够则降并发/开 C8/开 offload（三选一或组合，各自的代价回 ch8/ch9 查）。把三步再压成一张随身卡（运维可以贴在工位上的那种）：**承诺（P99 两参数）→预算（毫秒/显存两本）→配置（五旋钮：量化档/图模式/spec/并发/卡数）→验证（三直方图：TTFT/ITL/水位）**——四行字之间全是一一映射，任何一行出问题都能顺着查回上一行。这个「SLO→预算→配置」的链条是服务设计的完整闭环——**承诺不是拍脑袋，是算出来的**；而上线后的验证回 ch9（指标字典的 P99 直方图就是 SLO 的成绩单——`time_per_output_token_seconds` 的 bucket 边界要按 SLO 值配置，否则直方图的粒度看不见违约）。三步里最容易被跳过的是第②步的反推（很多人直接从 SLO 跳到「加卡」）——反推告诉你的是**瓶颈在哪一侧**：计算侧超预算该开图模式/减批；访存侧超预算该量化/减 KV；排队侧超预算该限流/扩容——三种超法三种药，跳过诊断直接加卡是把三种病都用钱治。

这张汇流表的用法是**完形填空**：把自己的需求逐行填进「本章动作」列——填得出的直接查表定案、填不出的就是待调研项（回到对应章读机制）。八个维度有优先级：硬件地基与容量是硬约束（一票否决），其余六维是软权衡（可折衷）——**先过硬约束再谈软权衡**，顺序反了会在不存在的选项里浪费时间。

最后一个选型心理战提示（给要向老板汇报的读者）：账本齐了还要会讲——汇报的顺序是「约束→选项→推荐→代价」四段（先说地基与 SLO 排除了什么、再说剩什么可选、给推荐、最后诚实说代价），**把代价放最后不是藏它，是让决策者在完整信息下签收它**——这也是「敢承诺」的另一半：承诺的勇气来自代价的透明。

## 11.7 期末大作业

题面：给定 SLO（ITL P99<50ms、TTFT P99<1s、并发 16 路×4,096 上下文）与硬件（4×Atlas 910B3），模型待选（Qwen3-30B-A3B 或 Qwen3-0.6B——两档都算，比较结论）。交付四件：**①选型备忘**（引擎+版本+理由——表 11.1 查起、平台面核地基）；**②容量账**（式 (11.1) 逐项列数——两档模型×三档量化=六列对比表，指出唯一可行组合或全部不可行的原因）；**③参数清单**（量化档/图模式/spec 开关/并发上限——每项附「为什么」与「代价」两栏）；**④验证方案**（上线后看哪些指标、P99 bucket 怎么配、违约时的三步排查路径——ch9 的三元组）。判据=容量账逐位闭合+每个选择有代价表+验证方案可执行（写出具体 PromQL 或日志行）。

评分量表公开（对答案用）：容量账 30%（逐位闭合+三档对比完整）、代价表 25%（每个选择两栏齐）、验证方案 25%（PromQL 具体到指标名）、风险登记 10%、整体一致性 10%（设计内部不打架——比如「图模式必开」与「启动预算 60s」的矛盾要自己发现）。这道题没有唯一解——**判分的是账本质量不是答案对错**（同样的 SLO 可以有「W4A16+大余量」和「bf16+限流」两个都对的设计，差别在代价表的诚实度）。这是八章知识的合卷考试——也是从「读引擎」到「做服务」的毕业证：读书时每个账本是给定的，做题时账本要自己立。

## 11.8 本章小结

回扣开篇：「敢承诺什么」的答案=式 (11.1) 的容量账（例 11.1 三步账——W4A16 给 SLO 最大余量）+表 11.2 价目单（图模式 3.126× 是最大杠杆）+SLO 反推三步（承诺→预算→配置）+八维决策表（前十章表格的汇流）；四引擎对照给市场全景（NPU 上 vLLM 插件与 SGLang 双路线两强）。

**带走的心智**：两幅画。**其一，选型是查表不是信仰**——表 11.3 八维决策表+价目单+容量公式三件套把「我喜欢 X」翻译成可审计的账目；八维决策表把「我喜欢 X 引擎」翻译成「我的八个维度各自查表的结果」；每个格子的证据等级（官方/第三方/本机）决定了它的可信半径——本机实测一格顶官方白皮书三格。**其二，SLO 是算出来的承诺**——容量公式正向、SLO 反向、指标验证闭环；三步里没有任何一步需要信仰，全需要账本。两幅画之外再送一句毕业赠言（选型层的）：**最贵的错误不是选错引擎，是不做画像就选**——选错引擎损失一次迁移（天级），不做画像损失的是每一次都选错（每次都在别人的尺子上量自己的脚）；画像能力（ch9 的指标面）因此是比任何引擎知识都保值的投资。

镜头拉回全书：生产化三步走完（知道发生什么/站在哪/敢承诺什么）——三步与专题九章的关系至此清晰：专题章是「引擎的器官」（每章一个），生产化三步是「体检的流程」（观测→地基→承诺），两者正交；下一章毕业设计把两条线拧成一股——一条请求穿越八册知识的全链走查，走查的每一步都同时是器官（专题知识）与体检（生产化判断）。
