## 1.2 先算一笔账：混合不是免费午餐

机制之前先算钱。两种层型的准入公式先立正身（本章反复回指）：

$$N_{\text{blk}}^{\text{FA}} = \left\lceil \frac{n}{b} \right\rceil, \qquad N_{\text{blk}}^{\text{SWA}} = \left\lceil \frac{W-1+e}{b} \right\rceil + 1 \tag{1.1}$$

| 符号 | 含义 | 取值例 |
|---|---|---|
| $n$ | 序列当前长度 | token（512/4096 两档） |
| $b$ | 块大小 | 128（NPU APC 档锁定） |
| $W$ | 滑窗宽 | 512 |
| $e$ | 保留尾 token 数（投机预留） | 0（本章无 spec） |

用人话说：FA 的账随长度线性涨、SWA 的账封顶在窗宽附近还多付一块「+1 舍入块」——混合机器的总账就是两类层的直加。构造一台最小的混合机器：8 层=2 层满注意力（FA）+6 层滑窗（SWA）、块大小 b=128、窗宽 W=512、每 token 每层 KV 2,048B（与 Book7 大项目 207M 的账逐位同源）。

**例 1.1（双组最小混合的块账）** 输入两档序列长度，逐组套准入公式（SWA 每层准入 $\lceil (W-1)/b\rceil+1$ 块、FA 每层 $\lceil n/b\rceil$ 块）：
①n=512：FA 组每层 4 块×2 层=8 块；SWA 组每层 $\lceil 511/128\rceil+1=$**5 块**×6 层=30 块；合计 **38 块当量**（块当量=各层块数直加的合计口径——本章各层同 b，块数可直比字节）——纯 FA 机器 8 层只要 32 块，**混合反亏 6 块**（n≤W 时窗口盖住全序列，SWA 每层多付的那块「+1 舍入块」×6 层全是白付的）；
②n=4096：FA 组每层 32 块×2=64 块；SWA 组每层**仍 5 块**×6=30 块；合计 **94 块**——纯 FA 要 256 块，**省 63.3%**（SWA 组的账本封顶在 W 附近，不再随 n 长）；
③滚动释放轨迹：decode 每前进 128 token，SWA 组释放一块再占一块（`remove_skipped_blocks` 语义）、FA 组只增不减——两类住客的账本性格全在这条轨迹里。
效果读法：38/32（亏）与 94/256（省 63.3%）一正一负，**混合省显存的前提是 n≫W**——短序列混合是亏本生意。（位置：+1 舍入块的正身=`kv_cache_interface.py#L834-840` 注释原文——block size 4、num_token 4 时，6-token 窗口 [CDEF] 要占 [XXCD][EF] 两块（窗口含 2 个保留位）；同一套公式在 workload 档 n=1232 的复算见 `exp_ch01_sim.py` 账 1，1.8 节。）

![图 1.1](figures/fig-1-1-hybrid-blocks.png)

图 1.1 混合组块布局（自绘，示意级；出处：`code/Book8-vLLM源码剖析下/ch01/fig_ch01.py`）：同一块池里 FA 组的无界账本随 n 增长、SWA 组的账本封顶在 W 附近；两线交叉即盈亏反转点——Book5 大项目的 3:1 整机账给出交叉 $n^*\approx1{,}373$（MLA 3 层 960 元素/token 无界 vs GDN 9 层固定 1,317,888，文档锚 `DESIGN-3TO1.md` 原值 1,372.8）——与例 1.1 的两点互证：n* 两侧，混合从亏变赚。

由此立机制图像：**一个池子、一套账本、两种集装箱**——大件行李（定长状态）整块入箱、散装小件（逐 token KV）按件装箱，箱子的尺寸全池统一。用人话说：混合 KV 管理器不发明新内存，它做的是**让两种生命周期不同的东西共用同一套分配、引用计数与逐出**——省的不是池子本身，是「各建各的池」的碎片化。接下来的三节把这张图像落到代码：谁分类（1.3）、谁记账（1.4）、K3 这样的工业正身怎么用（1.5）。

## 1.3 谁决定这是台混合机器：判定链与 spec 全谱

混合不是用户声明的，是**模型自己长出来的**。判定链五步行锚：模型 config 的 `layer_types`/`sliding_window`/mamba 层混排 → 每层在注意力层基类自报缓存规格（`get_kv_cache_spec`，`model_executor/layers/attention_layer_base.py#L40`；mamba 系在 `layers/mamba/abstract.py#L67`）→ GPUModelRunner 收集全部 spec（`v1/worker/gpu_model_runner.py#L7558`）→ 同型层分组成 `KVCacheGroup`（`kv_cache_spec_registry.py#L191` 的挂载注册表）→ 工厂按组数分派协调器（`v1/core/kv_cache_coordinator.py#L1014`：不缓存→NoPrefixCache#L477、单组→Unitary#L529、多组→Hybrid#L615）【源码：阅读锚 v0.30.0（ced6857），下同】。这条链上每层交出的那张「自报单」就是本章的主角之一——**缓存规格**（KVCacheSpec，spec）。

读法：manager 表与 spec 表**不是一一对应**——同一 spec 家族可能共用记账逻辑（如 Full 系三个 spec 共享向下封闭语义），而 HiSparse 一个子系统拆三个 manager。反向读：12 对 15——manager 数少于 spec 数，正说明记账语义按组复用（同族 spec 共享一个记账者）。真正的行为差异集中在**命中规则**：FA 组「命中就全要」、SWA 组「只要尾部窗内那几块」、Mamba 组「要 checkpoint 在场才认」。

跨组归并是协调器的活，也是混合 KV 的**核心难题**：一个请求同时住 12 层 FA 与 12 层 SWA，命中到底算多少？正身是 `find_longest_cache_hit`（`kv_cache_coordinator.py#L841`）：

```python

        self,
        block_hashes: list[BlockHash],
        max_cache_hit_length: int,

        """
        Find the longest cache hit using an iterative fixed-point algorithm.

        Each attention type either accepts the current candidate length or
        reduces it. If any type reduces the length, restart checks over all
        types. This converges because length monotonically decreases and is
        bounded below by 0.
        …
```

用人话说：**定点迭代归并**——先拿一个候选命中长度，逐类型问「这个长度你要不要」；任何类型说「太长了我只认到更短」，全体降到新长度重查一轮；长度只降不升、有下界，所以必然收敛。两个加速特例：满注意力「向下封闭」（只要候选不超过它的命中就永远同意，查一次后续只裁剪，#L894-901）；simple hybrid（1 FA+1 其他）一轮即收敛（#L872-876）。返回值里有一个 hybrid 特有的读数 `num_uncached_common_prefix_tokens`（#L970-973）——「FA 组已缓存、其他组没跟上的那段公共前缀」，它是 1.8 节命中率语义账的主角伏笔。

三面主镜各走一遍（其余 12 类表内点到）：**FA 镜**——无界账本、向下封闭、容量=每层 $\lceil n/b\rceil$ 块；**SWA 镜**——准入公式带 +1 舍入块、命中取尾部 $\lceil (W-1)/b\rceil$ 连续块、滚动释放；**Mamba 镜**——固定状态进池要回答「存几个快照」：

**例 1.2（Mamba 三态账：显存↔可命中性三角）** 构造：单层状态页 64 KiB、b_mamba=64、max_len=2048、无投机 checkpoint（`MambaSpec.max_memory_usage_bytes` 公式 toy 化：align 态=page×(2+spec+ckpt)，正身 `kv_cache_interface.py#L1034-1045`）。输入三档 `mamba_cache_mode`：
①none=1 页 64 KiB——请求退出即弃，零命中；
②align=2 页 128 KiB——只在**调度步末的对齐位置**存 checkpoint，哈希可部分命中（`enable_partial_hash_hits` 的语义正身）；
③all=⌈2048/64⌉=32 页 2 MiB——全序列可命中。
输出读法：三态是「显存↔可命中性」的三角权衡——align 是 K3 的生产档（1.5 节），none 是无前缀缓存档，all 最贵也最好命中；块表按全序列位置索引、但仅 2+spec 块常驻（#L1050-1058 注释——「索引宽、常驻窄」是 align 态的形状签名）。（位置：公式锚 `kv_cache_interface.py#L1034-1045`；仿真实现在 `exp_ch01_sim.py` 账 4。）

最后一块拼图是**钱**：单页统一与预算入口。`unify_kv_cache_spec_page_size`（`kv_cache_utils.py#L1365`）把所有组的页字节数对齐（不同 kv_hidden_size 的组靠增大注意力块到 ≥状态尺寸、mamba 按页 padding——设计文档 Case4 的推演；该文档写于 458e74 自注 early stage，其「只支持恰好两种注意力型」的表述已滞后于 v0.30.0 的不动点多组——成书以代码为准）；`get_kv_cache_config_from_groups`（#L1648）算出 num_blocks=可用内存//每块字节——**可用内存单点测量、块数统一换算**，这就是「一个池子」的落笔处。

## 1.5 K3 的正身：同一池子怎么装下两种状态

vLLM 的机制图谱之上，看一遍工业正身。K3 官方报告 §5.4.1（KDA-Aware Prefix Cache Management，p22-24）给了与上述图谱惊人同构的方案——三件套逐项对：

**(a) 统一分页布局**（p23）：KDA 递归状态定长每请求单份、MLA KV 逐 token 分页——**打进同一 block pool、页统一到相同字节数**，共享同一套分配/引用计数/逐出；页内按头连续存放=跨节点传输的最小单元（ch7 PD 的伏笔）。报告还留了个工程趣闻：类型混淆的访问得到的是垃圾而非「看似合理的数据」——池化布局自带零开销 sanity check。

**(b) 双粒度解耦与两段式查找**（p23-24，Fig.12）：block-hash 前缀缓存天然逼所有层共享一个 block size——共享块被逼到 1024-6144 token 的粗粒度，粗到缓存近乎无用。解耦方案：**hash 在 MLA 页内跑细块（512），物理块仍粗分配**；KDA checkpoint 只存 hash 端点。

**例 1.3（K3 Fig.12 两段式查找：在物理块内部命中）** 构造：物理块=6144 token=12×512 hash 块；请求前 2800 token 与缓存前缀匹配。输入三步：
①MLA 段按链式 hash 匹配整物理块、第一个缺失处回退到页内 hash 端点→最长 hash 命中 **B=2560=5×512**（落在物理块内部深处）；
②KDA 段逐组验证候选边界 2560 处**每组都有 checkpoint**→通过；
③恢复 B 处 checkpoint+对部分 MLA 块写时复制（CoW），从 token 2560 续 prefill——[0,2560) 零重算。
输出读法：命中 2560 是 hash 块的倍数、**不是**物理块的倍数（6144 的倍数只有 0 与 6144——粗粒度下这个请求只能命中 0）；代码形态=MambaManager 细粒度扫描的 `block_idx=fine_idx//scale_factor`（#L1517-1537，前面各位补 null_block）。（标 {官方技术报告 Fig.12 p23-24——1024-6144/512 为「通用机制+示例数字」口径}。）

**(c) 并发一致性三规则**（p24）：同一 free list 取块→分配前跨组 pin 所有命中块；拷贝落地前把（本调度步内新分配/新注册的）块排除出匹配；checkpoint 每组都有才可恢复、一组逐出则原子失效——「联合管理」的并发面就这三句话。

## 1.6 NPU 这条腿：vllm-ascend 的重写与边界

机制层（协调器/align/checkpoint）是平台无关的 Python 层，NPU 同享；器件层各走各路。vllm-ascend 对本章主题的重写集中在两个 patch 文件，能力限界开门见山：

```python
# vllm_ascend/patch/platform/patch_kv_cache_coordinator.py#L70-78（docstring 原文）
# 【源码：运行栈 vllm-ascend 0.27.1rc1】
    """KV cache coordinator for hybrid models with multiple KV cache types, and
    thus multiple kv cache groups.
    To simplify `find_longest_cache_hit`, it only supports the combination of
    two types of KV cache groups, and one of them must be full attention.
    May extend to more general cases in the future.
    """
```

指名看什么：**只支持两类组、且其一必须满注意力**——这是运行栈的能力自述。直接推论：1.8 节的变身体（FA+SWA 两组）恰在界内；三组以上混合在 NPU 运行栈不可实测（功能矩阵里 Qwen3-Next 标 🔵 与此限界的关系未逐行核——疑靠分组归并绕过，如实标注）。协调器本体的 `find_longest_cache_hit`（#L377 起）与上游同构（定点迭代/simple hybrid 一轮收敛/FA 向下封闭俱在）；另有一处本地增强：写读粒度对齐（#L180-185，SWA manager 的 scheduler_block_size 改挂 lcm_block_size——把写路径掩码粒度对齐读路径命中粒度，上游无）。

第二件是**块大小协商补丁**（`patch_kv_cache_utils.py`）：`_ascend_resolve_kv_cache_block_sizes`#L51——上游 PR #40860 限制「多块大小 hybrid 组不支持 DCP」，其注释明言该限制对 CUDA 正确、**对 Ascend 不正确**（Ascend 为 MLA 与 SWA-MLA 独立实现了 CP——上下文并行，dcp 则是 KV 数据并发副本数）——ascend 版按 LCM×dcp 算调度块、前缀缓存时 hash 块取 GCD 分支（#L73-82）；上游正身=`vllm/v1/core/kv_cache_utils.py#L717`。同文件还有 K3-DSpark 特判分组（`_get_kimi_k3_dspark_mixed_kv_cache_groups`#L87——target 与 draft 注意力层合入一个 UniformType 组共享调度块表、递归层切均衡组）——「为一家模型写一个分组特判」是 NPU 生态的现状写法。

第三件是归并策略补丁，它直接连到 1.8 节的命中率语义账。`patch/__init__.py#L193-201` 的 Why 原句：「Upstream's min-reduction across all KV groups collapses the FullAttention hit length to 0」——PD+hybrid Mamba 场景下，上游对全组取 min 会把 FA 组的命中压到 0，ascend 改取 FA 命中长（等上游 PR #42524/#44243）。**归并策略影响命中率**——这句话在 1.8 节会变成两个具体数字。

边界两头说清。能做的一头：滑窗不是 NPU 二等公民——`attention_v1.py` 的 prefill/decode 都原生按 `sparse_mode=4` 走滑窗（#L676-677/#L917-918）。不能做的一头：`vllm_ascend/attention/` 下**没有任何通用 mamba/linear/gdn backend**——通用线性架构族（Falcon-H1/Jamba/Bamba）在 NPU 无注意力后端；NPU 上能跑的 hybrid 走逐模型定制路（K3 的自定义 CANN 算子 `ops/kimi_kda.py`+专用注册）。「mamba backend 缺位→模型定制」本身，就是 NPU 生态的教学案例。

## 1.7 第二主题：sparse/indexer 族与组合后端（B7-11）

从「状态异构怎么共管」换到「**后端异构怎么组合**」——KV 池之外，attention 后端族也有自己的谱系与组合问题（Book7 ch09 章末欠账框后半句在此兑现）。谱系在 `vllm/v1/attention/backends/mla/indexer.py`（1,670 行）：`DeepseekV32IndexerBackend`#L184（**DSA 正身**）→`DeepseekV4IndexerBackend`#L239→`DeepseekV41IndexerBackend`#L256→`KpoolTailBackend`#L215（GLM-5.3-Flash 的 kpool 尾）；registry 侧 `registry.py#L93-132` 列 FLASHMLA_SPARSE/DSV4/DSV41/MINIMAX_M3_SPARSE/CUTLASS_MSA/TRITON_MSA，另有 `MambaAttentionBackendEnum`#L197 管线性/SSM 族（K3 KDA 经 `MambaSpec.mamba_type` 选中）【源码：阅读锚 v0.30.0】。

这一族有一个与量化章遥相呼应的设计——**indexer K cache 强制量化**：

```python
# vllm/v1/attention/backends/mla/indexer.py#L55-58【源码：阅读锚 v0.30.0（ced6857）】
DSA_INDEXER_KV_DTYPES = ("fp8", "mxfp4")
```

指名看什么：DSA 的 indexer K cache **总是量化**——"auto" 落 fp8（V3.2 布局）、mxfp4 是 Blackwell 专属 opt-in（`dsa_indexer_uses_fp4` 校验 sm_10x）。稀疏化省的是访问账，存储侧靠强制量化再砍一刀——架构账指回 Book5 ch03 的原句「省下的只记在访问账上、全量 KV 存储账原封未动」与 ch04 的 CSA/HCA 压缩条目。

第二个教学点是**进池 vs 不进池的对照**：DSA 的 indexer K cache 不单独成组——与 MLA 压缩 KV **同页混布**（`mla.py#L431-432` 的 656 字节自定义 layout+compressor_utils 管压缩槽位映射）；GLM-5.3-Flash 的 kpool 尾巴**单独成组**（KpoolTailSpec，`prefix_cacheable=False`）。同一类「indexer 内存」的两种池化决策，代价结构不同（前者共享逐出、后者隔离但不可缓存）。第三个是**跨层共享组**（`index_group.py#L35` SparseMLAIndexGroup）：一次索引、多层共用——indexer 算完 top-k 放进组、同组各 sparse MLA 层来取、event/流做生产者-消费者同步（`set_logical_topk_ready`#L53 的注释还顺手讲了 cudagraph 下 event 语义——Book8 ch5 的图模式话题在此预埋半句）。

hisparse 三件套（`vllm/v1/hisparse/`：块池系统/Coordinator/Connector）是 ch9 的地界，本章只立「spec 层已为其留位」（表 1.1 的 HiSparse 双 spec+`KVCacheGroupRole`）。最后登记一笔实测边界：MLA/DSA/SFA 的实测需要 DeepSeek 系/K3 权重——**作者已裁定（2026-10-12）：云 GPU 选做不做**（无云环境）；按 Book7 ch10 fp8/ModelSlim 先例显式登记入 ch13 台账，Book7 ch09:162 欠账前半句以此销项。本章这一节的口径=源码阅读面。

## 1.9 本章小结

回扣开篇：一台机器两类住客的问题，答案是一张三层图谱——spec 自报（15 类性格，表 1.1）、manager 记账（12 类命中规则，表 1.2）、协调器定点迭代归并（find_longest_cache_hit）；K3 正身与之逐项映射（表 1.3：统一分页/双粒度解耦/两段式查找）。账目三笔各有读数：例 1.1 的 38/94 块（n≫W 才省）、例 1.3 的 2560=5×512（hash 块倍数命中物理块内部）、例 1.4 的 **0.941×（启动容量按准入上限定池——负结果逐位咬合）**与例 1.5 的双天花板 32.0%/56.0%；命中率语义账两臂 56.0% 对手算 32.0%/56.0% 双天花板——计数者是谁，ch9 回账。

**带走的心智**：两幅画。**其一，一个池子、两种集装箱、一轮定点迭代**——混合 KV 管理器不发明新内存，它让无界账本与定长记忆共用分配/引用/逐出，命中长度是各类型「讨价还价」收敛出的不动点；读任何混合模型的部署行为，先找它的组、再找每组的记账者。**其二，启动容量 ≠ 运行时节省**——池子按准入上限一次定死（0.941× 的来源），窗宽的收益在滚动释放的运行时才兑现（63.3% 的来源）；同一指标在两个时间尺度上读，方向可以相反——这是读一切容量数字的坐标系。

镜头拉回全书：本章把 KV 的「省」走到了**层型**粒度（哪些层钉死窗宽）；下一章换一个维度——时间的「省」（投机解码：一步多算几个 token）。而 KV 的第三、四种省法（offload 搬走、传输换机）分别在 ch9 与 ch7——四种省法共享的临界比经济学，到 ch8 会统一收账。
