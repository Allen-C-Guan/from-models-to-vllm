# 第 8 章 量化生产化：两本账与部署矩阵

> 站段坐标：站 11（权重加载/量化识别）+站 12（算子执行层）。B4-3（推理侧量化）与 F18 后半句双钩并门；B7-9（MoE 量化与 expert 权重加载）的装载链在 ch6 预热、本章长出量化形态。

## 8.1 量化的生产问题：进门一本账、出门一本账

Book4-6 已把量化的数学与算法教完（四法四档，式与图指回）。本章的问题不是「怎么量化」而是「量化模型进了引擎之后发生什么」——一本**进门账**（检查点白名单：什么格式的量化权重引擎认）加一本**出门账**（执行格式：认了之后用什么算子跑）。两本账是不同的：进门看「格式声明」（config 的 quantization_config 字段）、出门看「执行路径」（算子+算子链）。**一本账在元数据、一本在算子**——量化的生产化难点恰好住在这两本账的换算里。三段定位：专题=量化生产化；站段=11+12；模块=`vllm/config/quantization.py`（白名单与格式解析）+vllm-ascend 的 `quantization/` 子包（NPU 算子接入）+Book6 的量化理论账（指回）。

> **最小背景栏**：量化四法（GPTQ/AWQ/FP8/训练侧量化）的数学是 Book4 ch09 已教；KV 量化的三线（KIVI/H2O/SnapKV）是 Book6 ch03 已教。本章只讲引擎侧怎么伺候量化模型。

## 8.2 进门账：检查点白名单六法

引擎认什么量化模型？答案在平台层的检查点白名单里——这是量化部署的第一道门，也是最常被踩的一道（用错格式直接起不了服务）。`vllm_ascend/platform.py#L99-106` 的白名单**六法**：`ascend`（ModelSlim——华为自家量化工具的输出格式）、`compressed-tensors`（llmcompressor 生态的开放格式）、`fp8`（浮点 8 位——社区通用）、`deepseek_v4_fp8`（DeepSeek-V4 专属）、`modelopt_mxfp8`（NVIDIA ModelOpt）、`mxfp8`（微缩浮点——Blackwell 世代主打）。**gptq 与 awq 不在列**——这两家社区最流行的量化格式在 NPU 白名单**进门即拒**。初次接触 NPU 部署的工程师最常见的困惑就在这里：「vLLM 明明支持 gptq，为什么我的模型起不了？」——答案是：vLLM 上游支持（有 marlin 还原算子），**vllm-ascend 平台层不认**（没有 NPU 版 marlin）。先看白名单的源码正身——

```python
# vllm_ascend/platform.py#L99-106（骨架摘录）【源码：运行栈 vllm-ascend 0.27.1rc1】
    # The checkpoint quantization methods that are supported by the platform.
    supported_quantization = [
        "ascend",              # ModelSlim
        "compressed-tensors",  # llmcompressor ecosystem
        "fp8",                 # OCP floating point 8
        "deepseek_v4_fp8",     # DeepSeek-V4 specific
        "modelopt_mxfp8",      # NVIDIA ModelOpt
        "mxfp8",               # Microscaling FP8 (Blackwell+)
    ]
```

指名看什么：六法的字符串列表——这就是「进门」的全部审判（`quantization_config.quant_method` 字段的值不在此列即拒）；注释标了每法的来源生态——源码注释即生态地图。

六法逐个过一眼——**ascend**（ModelSlim）：华为自家量化工具链的输出——从检查点产制到算子执行的全链华为生态、NPU 原生支持最深（C8 KV 也是这条路独有——只有 ModelSlim 产制的检查点才能激活 KV 量化路径）；**compressed-tensors**：llmcompressor 生态的开放标准（vLLM 社区的量化权重大本营）——本机可实测面最大（ch6 的 MoE w4a16 检查点就是此格式）；**fp8**：OCP 标准浮点 8 位——在 910B3 上进门但走 bf16 反量化服务（无 FP8 计算单元）；**deepseek_v4_fp8**：DeepSeek-V4 专属的 FP8 变体（有专门的权重布局）；**modelopt_mxfp8/mxfp8**：Blackwell 世代的新微缩浮点——面向 A5 能力位（下一代 NPU 的主打，本机降级跑）。**六法的排序暗含生态优先级**：自家格式第一、开放格式第二、社区格式第三、未来格式预留——这个排序不是 vLLM 的排序，是**华为生态战略在引擎层的投影**。六法的来源与优先级也值得看：`ascend` 是华为自家 ModelSlim 工具的输出格式（原生支持最深——从检查点产制到算子执行的全链华为生态）；`compressed-tensors` 是 llmcompressor 生态的开放标准（社区权重最多的入口）；`fp8` 是 OCP（Open Compute Project）推动的社区标准；`mxfp8` 系是 Blackwell 世代的新格式（A5 上主打——本机 910B3 上降级跑）。**白名单的排序暗含生态优先级**：自家格式第一、开放格式第二、社区格式第三、未来格式预留。

> **【实现对照框】** 为什么 gptq/awq 被拒？不是「NPU 不能跑量化」——是这两家的**还原算子**（gptq 的 marlin 系、awq 的反量化核）是 CUDA 专属。NPU 的替代路径是：模型先经 ModelSlim/llmcompressor 重产为白名单格式（`ascend` 或 `compressed-tensors`），执行走 NPU 算子。**「不支持格式」≠「不支持量化」——不支持的是那份格式的解码器**，与 ch7 的 OffloadingConnector CUDA-only 是同构的平台边界。

## 8.3 出门账：执行格式八种

过了门之后的执行路径由 `vllm_ascend/quantization/quant_type.py#L25-37` 的 QuantType 枚举定义**八种非 NONE 执行格式**：W8A8（权重 8 位/激活 8 位）、W4A8（4/8）、W8A8MXFP、**W4A16**（4 位权重/16 位激活——weight-only）、W4A4MXFP、W4A8MXFP、W8A8FP、W4A16MXFP。关键认知：**检查点白名单 ≠ 执行格式**。举例：同一个 `fp8` 检查点在 910B3 上走「反量化为 bf16 服务」的路径——该卡**没有 FP8 计算单元**（H 卡的 FP8 是 910B4/A5 世代的能力），引擎在加载期把 fp8 权重反量化回 bf16 再服务；**量化的收益只剩传输与存储（权重文件小一半）**，运行时算力与 bf16 无异。再举例：`compressed-tensors` 的 W4A16 子集进了门就直接走 NPU 的 int4pack 路径——**4 位权重在运行时也被保持**（不是加载期解压到 bf16），每步前向用 `npu_weight_quant_batchmatmul` 边解压边算。两种命运的分野在于**算子有没有到位**——算子在，格式就能「进门即出门」直达计算；算子不在，格式只是元数据标签，实际跑的是翻译后的替代品。

**引擎把进门格式翻译成该硬件最优的出门格式**——翻译表是部署矩阵的隐藏维度。这张表是 vllm-ascend 平台层的核心知识之一，也是选型时的查询表（表 8.1）。翻译的具体路径举例：一个 `compressed-tensors` 的 W4A16 检查点进门后——`quant_type.py` 解析 config 的 quantization_config 字段 → 识别为 W4A16 子集 → 分派到 `AscendW4A16` 算子族 → 加载期调用 `npu_convert_weight_to_int4pack` 把 safetensors 里的 int4 数组重新打包为 NPU 硬件解压格式 → 执行期 `npu_weight_quant_batchmatmul` 边解压边乘。**六步翻译链**（格式识别→格式解析→算子分派→权重重打包→算子调用→反量化输出）中的每一步都是平台层的代码——**用户看到的只是「模型能跑了」，引擎做的翻译全在暗处**。

翻译之所以必要，是因为**量化格式的碎片化**：同一个 W4A16 的概念，GPTQ 用 marlin 布局、AWQ 用等效缩放、llmcompressor 用 compressed-tensors 布局、ModelSlim 用自家布局——**权重位的排列方式各不相同**，NPU 算子只认自家布局，翻译层就是「各家方言→NPU 普通话」的转换器。

**表 8.1 部署矩阵**（进门格式 × 出门格式 × 硬件能力的三维对照——Book6 量化章的引擎侧续）

| 检查点格式 | 910B3 出门格式 | 说明 |
|---|---|---|
| ascend（ModelSlim） | W8A8/W4A16/C8 | NPU 原生算子链 |
| compressed-tensors | W4A16（w4a16 子集） | NPU 装载链 `AscendW4A16FusedMoEMethod` |
| fp8 | **bf16 反量化** | 910B3 无 FP8 单元 |
| mxfp8/modelopt_mxfp8 | MX 族（A5 主打） | 910B3 上前代格式降级 |
| gptq/awq | **进门即拒** | 还原算子 CUDA 专属 |

## 8.4 算子地图：从权重到计算

出门格式的算子链在 `vllm_ascend/quantization/` 子包。先看执行格式的枚举正身——

```python
# vllm_ascend/quantization/quant_type.py#L25-37（骨架摘录）【源码：运行栈】
class QuantType(Enum):
    """Quantization execution format."""
    W8A8 = auto()       # weight 8-bit, activation 8-bit
    W4A8 = auto()       # weight 4-bit, activation 8-bit
    W8A8MXFP = auto()   # microscaling FP
    W4A16 = auto()      # weight-only 4-bit (weight-only)
    W4A4MXFP = auto()   # ...
    W4A8MXFP = auto()
    W8A8FP = auto()
    W4A16MXFP = auto()  # MoE expert specific
```

指名看什么：`auto()` 赋值的枚举——**每种是一个独立的执行路径**（不是同一路径的参数变体，是八条不同的算子链）；W 后跟的数字=权重的位宽、A 后跟的=激活的位宽、MXFP 后缀=用微缩浮点而非整数量化。**这张枚举表就是出门账的全部合法值**。

三条主力路径：

**W8A8 dynamic**（动态量化——最主力路径）：加载期权重存 int8（每层一个 scale/zero-point 对）→ 执行期每步先 `npu_dynamic_quant` 现量激活（bf16→int8 的逐通道量化）→ `npu_quant_matmul` 融合乘加（int8×int8 累加到 int32 再反量化回 bf16）→ `w8a8_dynamic.py#L92/#L98` 的两调用是算子链正身。**每步前向都要现量激活**——因为激活的分布是动态的（不能像权重一样离线校准），所以叫 dynamic。收益的账：省的是**权重带宽**（int8 的 1B/token vs bf16 的 2B/token——权重加载是 decode 的主要访存，省一半带宽≈ITL 降一半）；付的是**量化算子开销**（每步多一个 dynamic_quant 调用）。收益条件=模型够大（权重带宽占比够高）且批量够小（小批的算术强度低、带宽主导）。

**W4A16**（weight-only 4 位——精度保全型路径）：加载期 `npu_convert_weight_to_int4pack`（`w4a16.py#L101`）把权重预压为 int4pack（NPU 专用的 4 位压缩布局——不是简单的 int4 数组而是适配硬件解压单元的打包格式）→ 执行期 `npu_weight_quant_batchmatmul`（`w8a16.py#L65`）边反量化边乘（每输出元素的计算流程：int4 权重→反量化 bf16→乘 bf16 激活→累加）——**激活全程 bf16 不量化**（weight-only 的含义：只压权重的存储，不动计算的数值形态）。代价是每步多一层反量化（int4→bf16 的解压开销），收益是**权重存储压到 1/4**（同卡可驻留 4 倍大的模型）。适用于：模型太大装不下（W4A16 是「装得下」的量化解法）或精度敏感不能动激活。与 W8A8 的选择是**容量 vs 速度**的经典权衡：W4A16 省显存、W8A8 省带宽——「装不下选 W4、跑不快选 W8」是部署的一线口诀。

**C8 int8 KV**（KV 缓存量化——B6-2 的第四种省法引擎侧正身）：五步链（`vllm_ascend/quantization/` 与 `npu_fused_infer_attention_score` 的 antiquant 通道）逐步走——**①进门识别**：检查点 config 带 `quantization_config.quant_method="ascend"` 且 `kv_quant=True` 标记，平台层识别为 C8 路径并设 `kv_cache_dtype="int8"`；**②布局分配**：KV 块的 dtype 从 bf16（2B/值）改为 int8（1B/值）+ 尾随的 scale 数组（per-channel 或 per-block 的浮点缩放因子）——同块大小下容量翻倍；**③写入侧量化**：每步 attention 输出的 K/V 新值在写入块前量化为 int8（`npu_quantize_kv` 调用）——量化公式 $x_{int8} = \text{clip}(\frac{x_{bf16}}{s}, -128, 127)$，$s$ 为该通道的 scale；**④读取侧反量化**：attention 前向读取 KV 时，`npu_fused_infer_attention_score` 算子的 antiquant 通道在**算子内部**边反量化边计算（$x_{bf16} \approx x_{int8} \times s$——反量化不是独立步骤而是融合进 attention 核的 prologue）；**⑤精度校准**：scale 的选择决定精度——per-tensor（一个全张量共用 scale，最快但精度最差）/per-channel（每通道一个 scale，平衡）/per-block（每块一个 scale，KV 场景最准）——ModelSlim 产制时的离线校准选档。五步串成一条「**量化→存储→反量化→计算**」的完整路径，Book6 ch03 的 C8 机制半句从理论侧长出了引擎侧的全息图。Book6 ch03 的 C8 机制半句在此长出完整引擎侧五步。

**W4A16MXFP**（MoE 专家专属 MXFP4 路径）：`w4a16_mxfp4.py#L142/#L147`——MoE 的 w13/w2 权重走 MXFP4 格式（微缩浮点——用共享指数的 4 位尾数块，比纯 int4 的精度更好），执行走 NPU 的 MXFP 解压算子——**这条路径只对 MoE 层生效**（attention 权重仍走其他路径），因为 MoE 的 expert 权重有「大量稀疏访问」的特征（每次只用少数几个 expert），压缩收益最大化。

**表 8.2 三条主力算子链的选择**（各链的适用面与代价——表 8.1 的出门侧展开）

| 链 | 压什么 | 精度损失 | 适用面 | 代价 |
|---|---|---|---|---|
| W8A8 dynamic | 权重+激活（8 位） | 中（激活动态量化） | 在线服务/大模型 | 每步量化算子开销 |
| W4A16 | 仅权重（4 位） | 低（激活保 bf16） | 装不下/精度敏感 | 解压开销+4 倍容量 |
| C8 int8 KV | 仅 KV 缓存 | 低-中 | KV 瓶颈场景 | antiquant 开销 |

读法：第一列决定你选哪条路、第二三列是选路的代价表——**三条不是互斥的**（W4A16+C8 可叠：权重压 4 位+KV 压 8 位，容量收益乘法）。

给读者一个量化选型的历史背景一句话：量化的「代际」由硬件的计算单元决定——910B3 是 INT8/INT4 世代（MXFP 是下一代 A5 的主打），所以本册实测面集中在 W8A8/W4A16/C8 三条路；FP8 硬件计算是 910B4 的事（本册按进门格式可验但出门走 bf16 反量化）。**硬件代际×量化格式=部署矩阵的第三维**——这张三维表是 ch11 容量规划的隐藏输入。

**例 8.1（C8 的容量账与两条路的叠加）** Qwen3-0.6B（24 层、GQA 8 头、head_dim 64）：每 token KV 字节 = 24 层 × 8 头 × 64 × 2(KV) × 2B(bf16) = 49152B → **C8 后减半为 24576B/token**（int8=1B/值）——同预算下 KV 容量翻倍（ch1 的混合变身是「部分层窗钉死」省一半层、C8 是「全部层的 KV 压半」省一半字节——**两条路可叠**：混合组 + C8 → 理论上 4× 容量——这正是 gpt-oss 级模型能在边缘 NPU 上跑的根本原因：三种省法（层数钉死+字节压半+C8）叠加把 1TB 级的 KV 需求压到单卡 64G 内。代价：antiquant 在每次 attention 里的精度损失（per-channel scale 缓解）与反量化开销——**量化 KV 的临界比与 ch7 的传输临界比同构**：省的容量 > 付的精度+延迟。**这个临界比的判断力比记住任何具体格式都重要**——KV 的四种省法（混合/C8/offload/传输）共享同一个经济学框架，理解了临界比就理解了 KV 管理的全部设计空间。

## 8.5 MoE 量化与 expert 权重加载（B7-9 正身）

MoE 模型的量化有自己的形状。回忆 Book4 ch07 的参数账：MoE 的总参数是激活参数的 10-20 倍（DeepSeek-V3 总 671B、激活 37B）——**expert 权重占模型体积的 95% 以上**。量化 MoE 的最大收益在压 expert 权重（压 attention 的那点收益在 MoE 里是零头）；反过来，MoE 量化的精度风险也集中在 expert（量化误差影响路由决策的稳定性——被量化扰动的 expert 输出可能改变 top-k 路由的选择）。装载链的特殊性也在此：expert 权重不是顺序加载的（每卡各装自己那份——ch6 EP 的分卡装载+量化解压在同一管道）。这条复合管道的具体流程：检查点的 expert 权重按「层→专家编号」组织（`model.layers.0.mlp.experts.0.gate_proj.weight` 等）→ EP 分卡映射决定每卡拿哪些专家 → 每卡装载时对分到的专家做量化解压（int4pack 打包）→ 装载完成的专家权重在卡上等待路由命中——**「分卡+量化」的复合意味着装载错误可能出现在两个层面**：分错卡（路由找不到专家）或量化解压错（数值错但形状对——更难查），生产部署时的冒烟测试应覆盖两个层面（一次 forward 确认路由命中正确+输出非 NaN）。装载链：MoE 检查点的 w13/w2 权重走 W4A16MXFP 路径（`w4a16_mxfp4.py#L142/#L147`——MoE 专家专属的 MXFP4 算子）→ expert 权重的**分布式装载**（ch6 的 EP 分卡 + 量化解压在同一管道——每卡装载自己那份 expert 的 int4pack）。

ch6 预热的 w4a16 MoE 检查点（7.76G compressed-tensors 格式——nm-testing 的 Qwen1.5-MoE-A2.7B-Chat）装载链有源码级正面信号（`AscendW4A16FusedMoEMethod` 的张量名与检查点逐字匹配——notes/16 §六 R3 登记的对照实验），但下载遇 hf-mirror 大文件断流（多次重试、blob 仅有 header 无权重的已知问题）未完成实测——**本章按源码走查口径写**（装载类、张量名映射、算子路径三面全核），实测留作批三开工的补验首跑项；**「下载受阻+源码走查先行」本身是 NPU 量化的部署现实**——社区量化权重多在 HF 上、镜像质量是最后一公里的卡点（本册实验期间 hf-mirror 大文件多次断流，7.76G 的 safetensors 两片均只获 79B 的 header 就中断）——**生产部署的权重分发策略（自建镜像/预热到本地盘/多源 fallback）不是附属问题，是部署矩阵的隐藏维度**。

## 8.6 精度-吞吐-SLO 三维权衡

量化部署的最终决策是三维的：**精度**（量化误差的下游影响——按任务敏感度分级：分类>生成>代码>数学）、**吞吐**（weight-only 的带宽省→ITL 降、dynamic 的融合→整体提速）、**SLO**（TTFT 是否被加载时间主导——大模型的 int4 装载可能比 bf16 慢 2-3 倍）。三轴的权衡不是自由组合——**部署矩阵的每个格子有自己的最优档**：在线服务（低延迟敏感）→W8A8 dynamic 稳态最优（带宽省→ITL 降）；离线批处理（吞吐优先）→W4A16 吞吐最优（权重省→同卡塞更多并发）；精度敏感（医疗/法律/数学）→bf16 全精度或 C8 只压 KV 不压权重（KV 量化对输出的影响比权重量化小——因为 KV 是中间态不是知识载体）；离线大模型（70B+ 单卡装不下）→W4A16 是唯一选项（先解决「有没有」再谈「好不好」）。**这张决策表是 ch11 容量规划的核心输入之一**——量化的选择不是独立的，是容量规划的约束变量。给一个定量直觉：70B 模型部署在 4×64G 卡上——bf16 需 140G（装不下）、W8A8 需 70G（刚好 4 卡×17.5G 但 KV 余量小）、W4A16 需 35G（4 卡余 221G 给 KV——充裕）——**量化从「选不选」变成「选哪个才能装下+跑多快」**，每个量化档位对应一张不同的容量规划表。

## 8.7 本章小结

回扣开篇的两本账：进门账（白名单六法——格式声明识别、gptq/awg 进门即拒的机制=算子 CUDA 专属）与出门账（执行格式八种——引擎把进门格式翻译成硬件最优路径）；三条主力算子链（W8A8 dynamic/W4A16 weight-only/C8 KV 五步）各有收益条件；MoE 量化把 expert 权重压到 4 位是 MoE 部署的关键账。

**带走的心智**：其一，**白名单 ≠ 支持面**——白名单只管进门（格式识别），出门的算子链才是实际支持面——「模型能不能跑」看两本账的换算表而非单看白名单有这个格式；其二，**量化是三维决策不是一维**——精度/吞吐/SLO 三轴各有最优档，不存在全局最优量化（「我该用什么量化」的答案永远是「看你最在乎哪一轴」）；其三，**C8 的临界比与传输临界比同构**——「省的东西 > 付的东西」这个公式在 KV 的一切变换（混合/C8/offload/传输）里反复出现，是 KV 管理的统一经济学——本册读完后读者应该能对任何一种新的 KV 优化方案（将来可能出现的新技术）用这个框架预判它的收益条件；其四，**翻译是平台层的暗工作**——用户看到的是「模型能跑了」，引擎做的格式翻译（六步链）全在暗处——理解翻译链才能 debug「为什么这个格式跑不通」的问题。

**例 8.2（精度-吞吐的直觉对照）** 用 Book6 的量化四法直觉做引擎侧续账：W8A8 dynamic 对应「整量化」（权+激全压）——精度损失最大（激活动态量化引入每步噪声）但带宽省最多；W4A16 对应「仅权量化」（激活保 bf16）——精度最保但解压开销吃掉部分收益；C8 对应「仅 KV 压」——不影响权重计算精度（KV 是中间态，量化对最终输出的影响是间接的）。三者的精度排序：**C8 > W4A16 > W8A8**（从最保到最压）；吞吐排序看场景：**W8A8 > W4A16 > C8**（纯 KV 压不省权重带宽）。**没有全能冠军——每种量化在自己的维度上最优**，三维决策（精度/吞吐/SLO）由此有了具体的映射表。

**量化部署的工程检查单**（从两本账到命令行的五步）：
①查白名单（模型的 quantization_config 在六法内？）→ ②查出门表（该格式在本硬件走什么路径？——表 8.1）→ ③算容量（式 (11.1) 的三本账——权重+KV+激活）→ ④设参数（`--quantization`/`--kv-cache-dtype`）→ ⑤冒烟验证（一次 forward 确认输出合法+一次 bench 确认性能达标）——**五步走完，量化部署的决策链闭合**。

量化的历史脉络一句话收束：从 GPTQ/AWQ 的「后训练权重量化」（社区生态最大但 NPU 不认）到 FP8 的「训练时原生量化」（OCP 标准化但需要硬件 FP8 单元）到 MXFP 的「微缩块量化」（下一代硬件的主打）——**量化格式与硬件代际是锁死的一对**：每代硬件推自己的量化格式、每种格式只在自己那代硬件上最优。选型时的第一问不是「什么量化最好」而是「我的硬件是哪代、它原生的量化格式是什么」——本册的 910B3 答案是 W8A8/W4A16/C8 三条主力，与六法白名单的映射已收入表 8.1。

本章的实测面值得总结一句：本机栈能直接跑的量化检查点=Qwen3 系的 bf16 原生版（反量化路径=无操作）+Qwen1.5-MoE 的 w4a16 compressed-tensors 版（下载受阻但装载链源码核齐）；能开的 KV 量化=C8（需 ModelSlim 产制的检查点——本机无产制工具，阅读面）；能验的配置面=白名单六法的进门判定（`--quantization` 参数设不认识的值直接报错——**报错消息里列的就是白名单**，一行命令即可验证）。三个「能」各对应一个知识层：**跑得动的是结果、读得懂的是机制、验得了的是边界**——本章在三层的交汇处写完了量化的引擎侧故事——读者离开本章时应该能对任何一个量化检查点文件说出三件事：它能不能进门（白名单判定）、进门后走什么算子链（出门表的换算）、这条链在我的硬件上值不值（三维权衡的判断）——三问三答的判断力是本章的核心交付。

下一章进入生产化的核心：可观测——metrics 指标字典、OTel 追踪、fault tolerance，把引擎变成「自己会说话的对象」。本章的量化与下一章的可观测在生产部署里配对：量化改了引擎的行为（延迟/精度/显存），可观测是**验证改动是否达到预期的唯一手段**——「量化后到底快了多少」的答案不在量化章，在可观测章的指标里。
