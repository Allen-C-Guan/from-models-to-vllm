## 2.1 两条实测路线，与「读的链不等于跑的链」

上一册走完主链路时，投机解码在我们眼前出现过三次：调度器的一个客户（站 8 的超前读）、执行层的一个装配位（7.7 节的 if-elif 链）、采样器的一个旁支（站 13 的验证采样）。三次都只到接线为止——Book6 第 10 章立了五型谱系与验证器数学，Book7 立了装配链，本章的问题因此很具体：**draft 怎么提、怎么验、错了怎么回滚，以及——在一台没有 CUDA 的 NPU 服务器上，这套东西哪几条真能跑。**本章产出三件：一套机制走查（2.2-2.4）、两组实测读数（实验 A 与 B，含 $\hat\alpha$ 对账）、一件大项目资产（两层的 drafter）。到站时的图景：两条实测路线全绿、加速比与接受率对上了 Book6 的理论账；同时会冒出新问题——草稿还要过文法约束（下一章）、集成服务怎么搭（第 12 章收）。

> **最小背景栏**：读本章只需要两笔旧账——Book6 第 10 章的投机解码理论（验证器数学式 10.1-10.3、$\alpha/\tau/c/\gamma$ 记号、五型谱系与「$\alpha$ 低于三成账面翻不正」的负结果母题）与 Book7 第 7 章 7.7 节的装配链一瞥（if-elif 接线层）。两边都忘了细节不妨事：用到时我们逐笔指回，不重教。

先把「哪几条真能跑」回答掉，因为它决定了全章的读法。v0.30.0 的配置层有一张 MRV2 白名单：`config/vllm.py#L2839-2849` 的 `_get_v2_model_runner_unsupported_features` 把白名单之外的 ngram、draft_model、suffix、medusa 全部登记为 V2 不支持——**本机仅有的两条可实测路线（ngram 与 draft_model），恰好都还是 MRV1-only**；draft_model 在 MRV2 侧的补齐晚至 v0.31。这不是随手排的：MRV2 重写了执行循环，speculator（投机器——MRV2 给 drafter 装配起的新名）被设计成 runner 内建的器官（2.3 的工厂），而 ngram 这类**跑在 CPU 上的 proposer** 与「外挂一个完整小模型」的 draft_model 都还没有搬进新组织方式——重写一次执行层的代价，就是每条特性都要重新搬家。实测证据同向：我们的配对冒烟日志里，装载 drafter 的是 `model_runner_v1.py#L4034`——vllm-ascend 自有的 MRV1 runner。

> **【版本差异框注】读的链与跑的链**：本章机制讲解一律锚 MRV2 路径（`vllm/v1/worker/gpu/spec_decode/` 一系——验证侧正身）；但 ngram/draft_model 两条实测路线在两轨都走 MRV1 装配链（`gpu_model_runner.py` 的 if-elif 段）。这不是矛盾而是分层：**验证的数学与采样协议在两代间同构，装配的组织方式在两代间重写**。运行栈 0.27.1 的对应行号漂移约 +45（差异表 #8 继承）。

于是本章的三段定位是：专题=投机解码；站段=8/12/13 三站；模块=`vllm/v1/spec_decode/`（提议侧）+`vllm/v1/worker/gpu/spec_decode/`（MRV2 验证侧）+vllm-ascend 的 `spec_decode/`（NPU 落地侧）。本机可测面定谳：**ngram（纯配置零权重）与 draft_model（自产 drafter）两条；eagle/eagle3 需专用 draft 权重产制、MTP 需模型自带 MTP 层——都是阅读面加云 GPU 选做**（已按作者裁定登记「选做不做」）。

## 2.2 一步的账：draft-propose-verify-accept/reject

两条路线定了，先看每一步怎么记账。结构账先于性能数字：投机解码把每个 decode 步从「一次前向出一个 token」改成「一次验证前向出一串 token」，这笔账由三方分头记账：

- **drafter 持草稿的写权**——它产出 $k$ 个候选 token（$k$=num_speculative_tokens），连同各自的预测概率；
- **rejection sampler（拒收采样验证器）持判决权**——用 target 模型在验证前向上的概率分布，逐位裁决草稿的生死，全中再从 target 分布采一个「彩头位」（bonus token）；
- **scheduler 持回滚的记账权**——判决结果落回请求状态，错了就回退账面。

回滚的账面动作，正身在调度器里（v0.30.0）：

```python
# vllm/v1/core/sched/scheduler.py::Scheduler.update_from_output #L1984-1996（骨架摘录）
# 【源码：阅读锚 v0.30.0】（中段以 … 略）
num_accepted = max(len(generated_token_ids) - num_sampled, 0)
…
request.num_computed_tokens -= num_rejected
```

用人话说：**拒绝不删草稿占过的 KV，只把「算到哪了」的账拨回验证起点，下一步重算**。两行小代码藏着两个大口径。其一，`num_sampled` 每步恒为 1（#L135-138 的 `num_sampled_tokens_per_step`），所以 **num_accepted=本步产出数−1：拒绝后从残差分布采出的那个修正 token 不算「接受」，全中时的 bonus 也不算**——它数的是「草稿里被点头的位」。其二，拒绝不是删除而是回退重算，KV 槽位由调度器的 lookahead（超前预留）兜底（站 8 的超前读正是为此：每请求多排 $k$ 个槽）。

验证前向的批形状因此有一个固定的形变家族。全序列视角：上下文长 $n$ 的 $B$ 条请求，草稿拼在末尾一次前向——$(B,n,d)\to(B,n{+}k,d)$；每步 query 视角：常规 decode 每请求只排 1 位，拼上草稿后是 $(B,1,d)\to(B,k{+}1,d)$——K/V 取自全序列、Q 只取这 $k{+}1$ 位，采样输出再收缩回 $(B,k{+}1,v)$。执行层的采样分岔就挂在这个形状上：无草稿走 `self.sampler(...)`，有草稿走 `self.rejection_sampler(spec_decode_metadata, draft_probs, logits, sampling_metadata)`——构造在 `gpu_model_runner.py#L701`（紧随 drafter 装配链），主调用点在 #L3681。

rejection sampler 本体，两代各有一份正身——MRV2 主读轨 `vllm/v1/worker/gpu/spec_decode/rejection_sampler.py::RejectionSampler`#L77（328 行）的构造函数：

```python

# 【源码：阅读锚 v0.30.0】（watermark 分支以 … 略、tensor 构造收尾以 … 略）
```

构造即见 v0.30.0 把验证策略参数化：`adaptive_verification`（按历史接受率调 $k$）、`synthetic`（合成接受率做实验对照）、`block`（块验证）。配套的 `acceptance_estimator.py`（501 行）与 `adaptive_verification.py`（504 行）是 v0.30.0 新增条目（差异 #12）——运行栈 0.27.1 没有这两件。MRV1 对照轨在 `vllm/v1/sample/rejection_sampler.py::RejectionSampler`#L45（1123 行的大家伙，核族从 #L407 的 `rejection_sample` 到 #L719 的 greedy 核）——两代同名同职责，但 MRV2 把它从「采样层的旁支」升格为「speculator 的器官」。

验证器的两分支与 Book6 式 (10.1) 的分布不变性两分支一一对应：贪心解码（target 与 drafter 都取 argmax）走 `rejection_greedy_sample_kernel`#L719——逐位比对两个 argmax，等则接受；随机采样走 `rejection_sample`#L407 的拒收采样核——按概率比裁决，从最小修改分布重采。我们的实验全用贪心（`--temperature 0`），一是贪心下「接受=逐位一致」读数最干净，二是验证器两分支共用同一套记账（上段的回滚账对两分支同构）。

草稿的产出怎么回到调度器？有一条专门的数据通道：`vllm/v1/outputs.py` 的 `DraftTokenIds`（调度器在 `scheduler.py#L69` import 它）——执行层把「本步为哪些请求提议了哪些草稿」打包成这个轻量结构，随 EngineCore outputs 回流，调度器据此更新 lookahead 账。说到 lookahead，这里有一处两轨演进的活标本：草稿槽数（`num_lookahead_tokens`）在运行栈 0.27.1 由 Scheduler 构造时**按方法自算**（eagle=k/draft=k/dflash=k+1/dspark=k——`R/vllm/v1/core/sched/scheduler.py#L247-270`）；v0.30.0 把它上移为配置层的 property（`config/vllm.py#L627`），docstring 明言「Consumers must read this property rather than re-deriving」——**同一笔账，两代把它的权威源从「消费者各自推导」收归「配置单点」**，这是引擎减少隐式耦合的一个小而典型的演进。

**例 2.1（draft-verify 一步的批形状与指标账）** 设 $B=2$（各 $n=10$）、$k=3$。①调度器为每请求排 1 真位+3 草稿位（lookahead 预留）；②验证前向 $(2,10,d)\to(2,13,d)$（全序列视角 $n{+}k$；每步 query 视角 $(2,1,d)\to(2,4,d)$）；③逐位裁决：请求 A 位 1-2 接受、位 3 拒→账面回退、从残差采修正 token；请求 B 三位全中+bonus，单轮封顶 $k{+}1=4$；④步末产出：A=3 个（2 接受+1 修正）、B=4 个（3+bonus）。**指标账**（按「产出−1」口径）：num_drafts=2、num_draft_tokens=6、num_accepted=$(3{-}1)+(4{-}1)=5$→平均接受长度 $=1+5/2=3.5$（含 bonus）、draft acceptance rate $=5/6\approx83.3\%$（分母是 token）、per-position 接受率 $=[1.0,1.0,0.5]$（位 3 上 A 拒 B 中）——三个口径一个例子全钉死（口径定义见 2.6）。

Book6 第 10 章的验证器数学（式 10.1 的分布不变性、式 10.2 的截顶几何期望、式 10.3 的 $\alpha$-$c$-$\gamma$ 加速比）在这里一律指回不重教；本章只补引擎侧的一句话：贪心解码下拒绝采样退化为逐位 argmax 比对，这正是我们实验全部用贪心的原因之一（另两个原因在 2.6 的三纪律里）。

## 2.3 proposer 家族：一个语法位，十一条分支

验证侧看完，换提议侧。Book7 7.7 说过「四型 proposer 统一成一个接口」——现在把「统一接口」摊开看。MRV1 的装配是一条 if-elif 链（`gpu_model_runner.py#L641-688`），实测分支序：custom_class→ngram→draft_model→ngram_gpu→gemma4→step3p5→dflash→suffix→eagle（eagle3 特判）→medusa→extract_hidden_states——**十一个分支共用同一个语法位**：装一个对象进 drafter 槽，每步拿上下文还 $k$ 个候选。链的头几行长这样：

## 2.4 NPU 侧：工厂全表与四条平台守卫

跨过设备边界，vllm-ascend 在 `spec_decode/__init__.py::get_spec_decode_method`#L36-61 自有一条工厂：ngram→`AscendNgramProposer`（直接继承**上游 CPU 版**，只把 `dummy_run` 改成 no-op）；ngram_gpu→`AscendNgramProposerNPU`；eagle/eagle3/mtp→`AscendEagleProposer`（双继承 EagleProposer+Ascend 基类；step3p5 变体另走 `AscendStep3p5MTPProposer`——2.3 的「mtp 走 EAGLE 形态」即此）；dspark 与 dflash(/2) 为 Ascend 特有/自动分流；draft_model→`AscendDraftModelProposer`；**gemma4 与 custom_class 无分支**——配了直接 `ValueError: Unknown speculative decoding method`（与上游的差异点，如实登记）。接线点在 `vllm_ascend/worker/model_runner_v1.py#L649-671`，而我们冒烟日志里的老朋友 `#L4034 Loading drafter model...` 就是这条链的入口日志。

ngram 那个 `dummy_run` no-op 值得停一拍：图捕获期 runner 会对每个组件做一次干跑以确定形状，而 ngram proposer 根本没有 NPU 模型可跑——上游 CPU 版的干跑在 NPU 栈上会碰设备初始化，NPU 版把它改成空操作。这个一行的补丁背后是移植的通用课题：**「无设备组件」怎么参与「有设备假设」的启动协议**。同理读者也能看懂为什么 ngram 能零成本继承上游：提议在主机侧的 numba 里跑（例 2.2），与设备后端无关——能继承的就不要重写，要改的只有设备假设的接口点。

平台层还有四条守卫（`platform.py`），每条都是「NPU 以收紧换稳定」哲学的实例：①spec 的量化强制继承主模型（#L724-732，告警明示）；②动态投机×DCP 拒绝（#L1531-1560 直接 ValueError）；③xlite 图模式×无投机互斥（#L1121-1131）；④**capture sizes 计入 spec tokens**（#L1430-1445：`decode_query_len += num_speculative_tokens`，上限 $\min(B\times(1{+}k),512)$）——第④条 Book7 例 7.4 已实测过代价：ngram $k{=}3$ 档图捕获表尾从 256 涨到 512、启动 84s→159s。

配置层的分工则要澄清一笔容易想当然的账。**MTP draft「加载为目标模型自身 MTP 层」的重映射正身在上游**：`vllm/config/speculative.py` 的 `hf_config_override`（按 model_type 把 DSV3/V4、GLM4-MoE、Qwen3-Next 等的 draft config 改写成 MTP 变体，两轨同在）；vllm-ascend 的 `patch_speculative_config.py` 实际装的是 **dspark 系规整四件**（k3_dspark 校验放行、legacy qwen3 DSpark 归一、dspark×DCP 临时关、ptd_token_id 兜底）——它的官方 docblock 自称「MTP draft 重映射」，与实码是脱节的。

## 2.5 大项目技术主场：给 207M 配一个两层的兄弟

理论账（Book6）说投机解码要赚，得有一个「小而准」的 drafter；装配链（2.2-2.4）说装 drafter 只是一行 config。中间缺的一环是：**drafter 从哪来**。这是本章大项目主场要补的环——也给「207M+投机解码服务」立技术地基。

**先算参数账，看看「小」的下限在哪。** 取 Book3 的 215M 定版架构只改层数（12→2，其余不动：hidden 1024、GQA 16:8、intermediate 2816、词表 32000）。

**例 2.3（drafter 的词表钉死账）** 三步账：①wte $32000\times1024=32{,}768{,}000$；②untied 的 lm_head 再一份同量——embedding 两块合计 **65,536,000**；③非 embedding=2 层×每层 11,798,528+终层 RMSNorm 1,024=**23,598,080**；总共 **89,134,080** 参数，是 target 的 $1/2.3$。推论：层数 12→2 省了 83% 的层参数，但词表的地皮一寸不让——**再深的层数削减也动不了这 65.5M**。Book6 选型结论说「drafter 取小两个数量级」（Book2 的 Scaling Laws 账），在 32k 词表面前撞墙；读者可心算任意层数的同族 drafter：参数 $\approx 65.5\text{M}+L\times 11.8\text{M}$。

**再定训练档——控制变量的口径比训得多久更重要。** 检查资产时我们发现一个此前从未明说的事实：207M target 的「Book3 终态」其实是 **integrated 1000 步档**（8.2M token，eval 5.83534——Book3 起全量长训就一直暂缓着）。这意味着 drafter 若按 Chinchilla 直觉训得更多，反而与弱训练的 target 分布失配、拉低接受率。正确口径是**同语料、同配方、同步数，唯层数不同**——一个「两层版的兄弟」。于是 drafter 用 Book3 训练管线的 NPU 启动器注入 $L{=}2$ 跑同款 integrated 档【本机实测（Atlas 910B3，CPU 侧训练件+单卡）：wall 1.6 分钟、稳态 0.016 s/step、final_eval 5.7789 全有限——底档 `log/book8-00/r7_draft_int.log` 与 `log/book3-ch10/train215_integrated_b8draft2Lint.json`】。兄弟俩的 eval 对照（2 层 5.78 vs 12 层 5.84）本身就是个教学点：**8.2M token 的欠数据区里，小模型先吃饱**——但别急着乐观：分布都平的时候重叠未必大，$\hat\alpha$ 是联合属性，这要等实验读数说话。

顺带交代注入手法——它是 Book6 以来的「**不改交付件**」手艺的一次完整展示：Book3 的 `train_215.py` 一字不动，NPU 启动器打三处补丁（mps 探测直通、autocast 重定向、`LLAMA_215M["num_hidden_layers"]=2` 的 dict 原地改——训练脚本与模型库共享同一个 config dict，改一处全链同步）；参数账断言里的字面量与路径锚则在**载入前替换源码文本**、从补丁件执行（磁盘原件零触碰）。想在自己项目里复用「别人的训练脚本+我的小改动」，这三层（探测补丁/行为补丁/源码字面量补丁）是一个够用的工具箱。

**资产链三件**（底档 `log/book8-00/`）：HF 五件套 `hf_draft2m/`（tokenizer 复用 hf207m 同源件——词表对齐判据落位；若异词表配对，接口预案是 2.3 的 `VocabMapping`）；真配对冒烟三判据全绿（双模型装载日志/贪心两轮一致/输出非空，底档 `r7c_draft_pairing.*`）；`speculative.py#L1157` 的 `Overriding draft model max model len from 2048 to 1024`——drafter 长度对齐 target 的第一道闸。

**例 2.4（从 $\tau$ 反解 $\hat\alpha$——对账预演）** 实测平均接受长度 $\tau_{obs}=2.0$、$k=3$：解 $\frac{1-\hat\alpha^{4}}{1-\hat\alpha}=2.0$。试 $\hat\alpha=0.5$：$1.875$ 不够；$\hat\alpha=0.55$：$2.019$ 过——$\hat\alpha\approx0.54$。再代 Book6 式 (10.3)：取 $c=0.2$ 粗估，理论加速 $2.0/(3\times0.2{+}1)=1.25\times$。拿真实的 k=3 体检档臂验一遍这条流水线：$\tau_{obs}=3.36$ 反解 $\hat\alpha=0.885$、$\hat c=(3.36/1.40{-}1)/3=0.47$——与实验 C 的逐臂对账表逐位吻合；预演里的 $c=0.2$ 是理想图模式时代的量级，本机 eager+小批量的 $\hat c\approx0.5$ 正是加速比只有 1.4× 而非文献 2-4×{厂商自报} 的主因。

## 2.6 观测与判读：$\hat\alpha$ 的三个口径与三条纪律

投机实验最容易读错的不是加速比，是接受率本身——三个口径差一个字就是一个数：

1. **平均接受长度** $\tau=1+\text{num\_accepted}/\text{num\_drafts}$——**+1 是惯例加彩头**（源码注释原话："Conventionally, mean acceptance length includes the bonus token"，`spec_decode/metrics.py#L113`，两轨同文）；
2. **draft acceptance rate** $=\text{num\_accepted}/\text{num\_draft\_tokens}\times100\%$——分母是 **token 数**不是提议次数；
3. **per-position 接受率** $=\Sigma_j \text{accepted\_per\_pos}[j]/\text{num\_drafts}$——「前 $j$ 位全对」的通过率剖面，教「第几位拖后腿」最直观（与 DeepSeek-V3 报告「位置越往后衰减越快」互证）。

用人话说：三个口径分别是「平均一步走多远」「草稿 token 的命中率」「每一位的及格率」——例 2.1 的三口径（3.5 / 83.3% / [1.0,1.0,0.5]）在此各归各位。同一份 `SpecDecodingStats` 有三个消费面：serve 周期日志行（格式串原文：`SpecDecoding metrics: Mean acceptance length: %.2f, Accepted throughput: ..., Per-position acceptance rate: %s, ...`）；`/metrics` 的三个 counter（`vllm:spec_decode_num_drafts/num_draft_tokens/num_accepted_tokens`——**只在 spec 配置非空时注册**，spec-off 臂没有这些行，本身就是开关旁证）；以及 inproc 钩子逐步剖面（须 `VLLM_ENABLE_V1_MULTIPROCESSING=0` 且 `disable_log_stats=False`——Book7 ch12 踩坑延续）。第三个消费面值得多说一句用法：inproc 模式下每步都能读 `make_stats().spec_decoding_stats`，per-position 向量逐步可取——**「第几位拖后腿」的画面只有这里看得见**（周期行是累积均值，会抹平步间波动）；它是运行栈没有 per-request 指标（下面的框注）时，最接近请求级剖面的替代口径。

> **【版本差异框注】** v0.30.0 另有 per-request spec 指标三件套（`--per-request-spec-decode-metrics` 三档开关、`RequestSpecDecodeMetrics`、`EngineCoreOutputs.spec_decode_metrics`）——**运行栈 0.27.1 全仓零命中**（差异 #14）。大项目观测只能走聚合面：周期行、counter、inproc 三选一。

**实验三纪律**（提炼自混淆源清单的前三条；全表在素材底单，动笔逐条过）：其一，**async scheduling 与 ngram 互斥且默认开**——spec 臂会被强制关掉 async 并告警（`Async scheduling not supported with ngram-based speculative decoding and will be disabled`），不显式统一 `--no-async-scheduling` 的话，on/off 两臂连调度器都不同（互斥守卫的机制层在 ch5 §5.2 展开——Book7 ch12:57 欠账的 `_spec_token_placeholders` 正身也归那里）；其二，**bench serve 不再默认贪心**——`--temperature 0` 必须显式；其三，**workload 要配得上 proposer**——随机数据集上 ngram 接受率天然趋零（实验 A 的 random 臂正是为这条预注册的负结果锚，虽然实测推翻了它——推翻本身成了更好的读数）。

八条清单里还有一条 NPU 特有的要害：**一臂一进程**——同进程起两个 LLM 实例必死（CANN 运行时在同一进程里只许初始化一次，第二次 aclInit 直接报 107001 冲突），所以扫描循环里每臂起停一次 serve 不是繁琐而是物理约束；连带的一条工程纪律是**判零之前先证有流量**——我们第一轮扫描就踩过：bench 命令的旗标拼错让请求一个都没发出去，serve 正常、metrics 全零，表面上像「spec 没生效」，实则是零流量（三个 0.27.1 bench 旗标陷阱与这次排障的完整过程件在 `log/book8-ch02/` 各臂日志可查——它们本身就是「观测口径先于结论」的活教材）。

最后一个接口预告：草稿也过文法约束（spec×结构化同开时，判废草稿**从 draft 分母剔除、不从 accepted 分子剔**——acceptance 读起来更「乐观」，口径差写脚注）——机制的完整展开是下一章的正菜。

## 2.7 本章小结

回扣开篇的三问：draft 怎么提——proposer 家族十一个分支共用一个语法位，NPU 侧工厂全表继承上游并补齐 dspark；怎么验——rejection sampler 逐位裁决、bonus 归属与回滚账面都在调度器的两行代码里定了口径；怎么回滚——`num_computed_tokens` 回退加 lookahead 预留，错了就重算。而「哪几条真能跑」的答案是两条：ngram 与 draft_model——恰好都是 MRV1-only，恰好都被我们跑绿了。实测的最终账：ngram $k{=}3$ 加速 1.40×（$\tau=3.36$、$\hat\alpha=0.885$、$\hat c=0.47$），drafter $k{=}3$ 加速 1.16×（$\tau=2.64$）——两条都赚，但赚法不同：一条吃的是模型输出的自重复结构（免费），一条吃的是同源分布的兄弟直觉（一次 integrated 档训练）；把它们放在同一张对账表上，$\alpha$-$c$-$\gamma$ 三元账从 Book6 的纸面走到了引擎的读数。

**带走的心智**：其一，**投机解码是一笔三方分账的生意**——drafter 出力、sampler 判卷、scheduler 记账，读任何实现先找这三个写权位；其二，**接受率是联合属性**——drafter 与 target 的分布重叠决定 $\hat\alpha$，「小而准」里「准」字指向的是与 target 的相似而非绝对质量（例 2.3 的词表地皮与例 2.4 的反解对账是这笔账的两个心算工具）；其三，**观测口径先于结论**——+1 惯例、token 分母、per-position 剖面三个口径不钉死，任何加速比都读不稳。

下一章换个约束方向：从「猜得准」到「格式对」——结构化输出把文法编译成每一步采样的硬约束，管线正身与 grammar 后端族在 `vllm/v1/structured_output/` 等着开箱。
