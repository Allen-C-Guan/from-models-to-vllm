# 第 6 章 分布式服务：TP/PP/EP/DP 与多卡边界

> 站段坐标：站 6-8（进程拓扑扩展）+站 11-12（多卡执行与通信）。B4-1（EP 工程）与 B7-7（多卡图模式同步边界）双钩并门；另收 Book6 ch12:3「多卡实测留 Book8 云档」的半句（作者已裁定选做不做，本机 TP 双卡实测兑现本地部分）。记号契约首现：**TP（tensor parallel，张量并行）/PP（pipeline parallel，流水线并行）/EP（expert parallel，专家并行）/DP（data parallel，数据并行）**——四词首现对照在此。

## 6.1 一张卡装不下，一张卡扛不住

单卡引擎的两类失败：「装不下」（模型权重+KV 超单卡 HBM）与「扛不住」（吞吐/延迟需求超单卡产能）。给读者一个读章锚：全章的核心对照物是**表 6.1 的通信账**与**例 6.2 的木桶账**——前者决定选哪把刀、后者决定 MoE 部署的额外工课。为什么需要四种刀而不是一种？因为**被切的对象性质不同**：张量是纯算术（切完拼回去就行）、层是串行依赖（切完要接力）、请求是独立的（切完互不影响）、专家是条件路由的（切完要看病跨卡）——对象性质决定通信模式（同步拼装/流水接力/零通信/动态路由）。四种刀法不是设计者的自由发挥，是**四个对象各被物理规律钉死了通信形状**。

四种切法是四类答案，共同骨架是「**切什么、怎么通信、代价多少**」的三联问（表 6.1 收拢答）：TP（tensor parallel，张量并行）把**每层的张量**切开——一个大 GEMM 变两个小 GEMM 各算半边，多卡合力算一层，层间 all-reduce 对齐——通信密、延迟低，装得下+单请求提速（大模型推理的主力切法）；PP（pipeline parallel，流水线并行）把**层堆**切开——卡 0 算 1-12 层、卡 1 算 13-24 层，token 像流水过两站——通信疏（只在 PP 边界传 hidden state）、但批不满时有流水线空泡（第 k 站在第 k-1 站出活前只能等——推理侧请求流不断时空泡可摊薄），装得下+吞吐型（训练侧的主流、推理侧的补充）；DP（data parallel，数据并行）把**请求**切开——每卡一个完整引擎副本各吃各的请求——零模型通信、纯吞吐型（**不解决装不下**——每卡都要装全模型）；EP（expert parallel，专家并行）把 **MoE 的专家**切开——每卡驻一部分专家、token 按路由表跨卡求医（all-to-all）——MoE 专属，非 MoE 模型用不了这把刀。真实部署的选刀实例一锤定音：70B 模型 4 卡推理最常见的是 TP=4（一刀四切——4 卡每层合力）；若 4 卡装不下 405B，就 TP=4+PP=2（共 8 卡，4 刀宽×2 站深——先切宽再切深，宽的通信密放层内、深的通信疏放层间）；若吞吐还不够，再叠 DP=2（共 16 卡，两台 8 卡机器各一个完整副本）。**三维组合的枚举不是自由配置题——每个维度有自己的通信代价，选组合=在「装得下」约束下最小化总通信**。

DP 值得多看一眼，因为它是四种里唯一**不需要引擎支持分布式**的：每个 DP 副本就是一个完整的 vLLM 实例（各自起 serve、各自有 EngineCore），调度层只需要在前端把请求分发到不同副本——vLLM 的 `dp_supervisor`（入口层的 DP 调度器）就是干这个的。**DP 的简单性来自「每份独立」**，但它的限制也来自这里：不共享 KV（每副本各自的 APC）、不共担权重内存（每副本各装一份）、副本间不通信（不存在跨副本的负载转移）。**DP 是「加机器」的最朴素形态**——引擎不用改、通信为零、代价是内存翻倍；TP/EP 是「改引擎」的复杂形态——通信有价、换来内存与计算的真正分摊。

三段定位：专题=分布式服务；站段=6-8+11-12；模块=`v1/executor/` 五件+`distributed/parallel_state.py`+vllm-ascend 的派发三路线。本章产出：executor 拓扑走查+进程公式实测（6.2）、通信正身与 NPU 派发三路线（6.3）、MoE 专家并行与 EPLB 的均衡账（6.4）、图模式的全组同步边界（6.5）、TP 双卡首跑 J1-J7 全绿读数（6.6）。

> **最小背景栏**：TP 的行切/列切数学与 all-reduce 通信账是 Book6 ch12 已教（式与图指回）；MoE 的专家路由是 Book4 ch07 已教。本章只讲「引擎怎么组织多卡」，并行数学与路由机制指回。读本章的方法论提示：分布式功能的官方文档通常只给「支持/不支持」的矩阵——**源码给出的是「为什么这个格子是 ✅/❌」的约束链**（通信原语的假设、时序对齐的要求、平台守卫的判定），这套约束链才是部署决策时真正需要的知识。

## 6.2 executor：拓扑的组织者

Book7 ch7 讲执行层时只到 uniproc+multiproc 一句点名——现在展开。executor 的角色一句话：**它是「进程拓扑的组织者」**——单卡时一切在一个进程里（uniproc 直调，Book7 的默认世界）；多卡时 executor 决定起几个进程、谁跟谁组通信组、消息怎么路由。`v1/executor/` 五件：abstract（抽象基类+`get_class`#L49 的分派——按 uni/mp/ray/类路径四路）、uniproc（单进程直调）、multiproc（本机多进程——EngineCore 与 Worker 同机但各为独立进程；通信走共享内存消息队列（`rpc_broadcast_mq`——广播一条消息多个 Worker 同时收到、比逐个 TCP 便直一个量级）+`worker_busy_loop` 三行式响应循环（收→算→回，Book7 ch7 的正身在多卡世界原样复用）、每 Worker 绑一张卡），ray（跨机 actor 化——**本机未装 ray，阅读面**；actor 化=每 worker 是一个可远程调用的对象，跨机部署的代价是每条消息多一跳序列化——但换来了跨机调度、容错重启、多租户共享这些单机多进程给不了的能力；vLLM 的 ray 路线是「推理上云」的拓扑基座）、外加 external_launcher（外部启动器——TP 环境由调用方拉起而非引擎自起，ch5 的死锁考据框提过它：external_launcher 模式下编译必须关异步（每 TP rank 各有调度器，异步迁移不同步会死锁）——vLLM 0.30.0 引入的外部编排接口，为 k8s 等调度器预留——「谁起进程」从引擎职责变为外部系统的可插拔选项）。executor 与 EngineCore 的关系一句钉死：EngineCore 是**逻辑**执行器（调度循环——不管几卡都是一个 EngineCore 实例）、executor 是**物理**执行器（进程组织——决定起几个 Worker 进程）；EngineCore 每步把 SchedulerOutput 交给 executor、executor 广播给各 Worker、各 Worker 各算各的份额再回传——**调度一次决策、执行多卡分治**。这层「逻辑-物理」分离让单卡与多卡共享全部调度代码——与 ch5 的「调度逻辑零改动只改时序」是同一设计哲学的两次应用（一次分空间、一次分时间）。

进程数公式（Book7 ch4 立的）：**A+DP+N(+1)**——A=API server、DP=数据并行副本数、N=每副本的 TP×PP worker 数、(+1)=离线模式无 A。

**例 6.1（TP2 的进程账）** 本机首跑实测：`ps` 表 4 行——API(1)+EngineCore(1)+`VLLM::Worker_TP0`+`VLLM::Worker_TP1`(2)；公式 $A{+}DP{+}N=1{+}1{+}2{=}4$ ✓（底档 `tp2_ps.txt` 原样）。换 PP=2 的世界：公式给 $1{+}1{+}2{=}4$ 同样 4 个进程，但进程名变 `Worker_PP0/PP1`——**TP 的两个 Worker 同一步算同一层的两半（横向并行）、PP 的两个 Worker 同一时刻算相邻层的不同批（纵向流水）**——进程数相同、时间关系完全不同。每 Worker 各持一张卡、各算半个张量——**TP 的「分布」从进程名就能看见**（Worker_TP0/TP1 的命名是 vLLM 的多进程拓扑自描述习惯，ps 表即拓扑图）。进程间的消息流也值得看一眼：API server 收 HTTP、EngineCore 做调度（ch4 的 busy loop）、Worker 们做前向——调度结果经共享内存广播（multiproc 的 `rpc_broadcast_mq`）同达两个 Worker、前向结果同路回来——**调度一次、广播两次、通信零跳**（EngineCore 与 Worker 同机进程间）。

## 6.3 通信正身与 NPU 派发

TP 的每层 all-reduce 走 `distributed/parallel_state.py::GroupCoordinator`#L422-446——官方 docstring 的 rank 表（TP/PP/DP/EP 各组的 rank 编号空间）；通信组的正身在 `distributed/parallel_state.py::GroupCoordinator`#L422-446——

```python
# vllm/distributed/parallel_state.py::GroupCoordinator#L422-446（骨架摘录）【源码：阅读锚 v0.30.0】
class GroupCoordinator:
    """General class for process group information for NCCL-like
    communication.
    ...
    - local_rank (int): rank of this process within this group on this node.
    - rank (int): global rank of this process.
    - world_size (int): world size of this group.
    ...
    """
```

指名看什么：docstring 把「一组通信参与者」的全部身份字段列清——rank（全局编号）、local_rank（本机编号）、world_size（组大小）——**每个进程在每个通信组里各有一套编号**（TP 组的 rank 0 与 EP 组的 rank 0 可能是不同进程），理解多卡日志的第一课是分清哪套 rank 在说话。HCCL 是 NPU 的通信后端（对应 CUDA 世界的 NCCL）。本机首跑的通信证据三行（底档 `tp2_evidence.txt`）：`world_size=2 rank=0/1 backend=hccl`（两个 worker 各一行——通信组建立的握手实物）+ HCCL 超时链值得三句展开：`The timeout interval of the HCCL operator is 1836s. Timeout in seconds for execute_model RPC calls in multiprocessing must be greater than 1836s, Set VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=3000`——CANN 的通信超时默认 1836 秒（约半小时），比 vLLM 的执行 RPC 默认超时长；如果 RPC 先超时而 HCCL 还在等，进程会被误杀——**引擎自动把 RPC 超时抬到 3000 秒兜底**。这不是 bug 修复而是防御性适配：NPU 通信栈的时间常数与 CUDA 世界不同（NCCL 默认 30 分钟级、CANN 1836s 是另一个数），**平台差异不止功能面，时序面也要适配**——这类适配无声无息地发生在启动日志里，运维读日志时值得多看一眼。

vllm-ascend 的 MoE 派发三路线（sources/01 §四）——每条路线是一种「token 与专家怎么见面」的答案：**MC2**（矩阵计算 2.0——华为的 MoE 通信库，专用全互联核），**AllGather**（TP 内先聚 token 再本地路由——通信模型简单、代价是每卡都看到全量 token），**All2AllV**（token 直送专家所在卡——通信量最小、代价是路由表的动态性）——按模型规模与 TP 度选路（小规模 AllGather 简单优先、大规模 All2All 省带宽、有 MC2 硬件加速时首选）。EPLB（expert parallel load balancer，专家并行负载均衡器——上节的例 6.2 立的「木桶效应」的解药）**双路互斥**：`EplbConfig`#L106 的两种实现（静态重排与动态迁移）不能同开——静态在启动时按历史统计重排一次、动态在运行中按观测周期迁移，各有代价与适用面；且上游 EPLB 是 CUDA-only——vllm-ascend 用 `_CudaAlikeEplbPlatformProxy` 代理绕行（「假装是 CUDA」的平台代理——上游按 `platform.is_cuda` 分派 CUDA 路径，NPU 没有 CUDA 标志，代理类把标志翻转给 EPLB 子系统看、底层算子实际走 NPU——**一处标志位的善意谎言**，ch10 平台章展开这个模式的得与失）。finegrained_tp 五字段四守卫（细粒度 TP——把 expert 的 TP 切得比 attention 更细的配置面）：MoE 模型的 expert 权重占大头而 attention 轻量，如果 attention 与 expert 同 TP 度，attention 侧被过度切分反而低效——finegrained 允许 expert 用更高的 TP 度、attention 用更低——**「一刀切」与「按密度切」的取舍在并行配置面重现**。四守卫各对应一条组合禁忌（与图模式/DCP/特定通信后端的互斥），配置面的复杂度来自「每种新自由度都要与旧自由度正交」的约束传播。

## 6.4 MoE 专家并行：EP 的账

MoE 的多卡问题有自己的形状：专家权重巨大（激活参数小、总参数大——Book4 ch07 的账）但每个 token 只用少数专家。规模感先立一档：DeepSeek-V3 级 MoE 总参 671B、每 token 激活 37B——单 bf16 副本要 1.3TB 权重（8 张 80G 卡的纯权重），而每 token 实际只碰 37B 的那一小撮专家。**「权重装满了每张卡、计算只发生在少数几张」**——这个不对称是 EP 一切设计的出发点。EP 的切法：每卡驻一部分专家，token 按路由表送到专家所在的卡。通信原语是 **all-to-all**（每卡发给每卡，但发的量由路由决定——与 all-reduce 的「大家发等量、聚成一个结果」不同，all-to-all 是「各发各的、各收各的」——**一对多的搬运而非归约**）；每 token 一来一回（发去算、算完回）。EP 与 TP 的根本区别值得先立：**TP 切的是「一层之内的张量」（每卡都看到每个 token）、EP 切的是「专家的集合」（每卡只看到路由到自己的 token）**——TP 的通信是对称 all-reduce（每卡发等量数据）、EP 的通信是 all-to-all（每卡发往不同卡的数据量取决于路由结果）——**路由的随机性直接变成通信的不均匀性**，这是 MoE 多卡的独特难题。

**例 6.2（8 专家 2 卡的账）** toy：8 专家均分到 2 卡（各 4 个）；一批 16 token、每 token 选 2 专家（top-2 路由）。理想均匀：每卡各收 16 个 token-专家对（32 对的一半）——all-to-all 发送 16、接收 16，两卡等速。**不均匀的坏情形**：热门专家全在卡 0——卡 0 收 30 对、卡 1 收 2 对，卡 0 成为瓶颈而卡 1 闲死——**整个集群的吞吐被路由分布钉死在慢卡上**（木桶效应的分布式版）。这就是 EPLB 存在的理由：**动态迁移专家让两卡负载均衡**——观测一段路由统计（哪些专家被高频选中）、把热门专家搬到闲卡、更新路由映射表（路由从「静态等分」变为「动态重排」）；迁移本身有通信成本（专家权重要跨卡搬），所以按周期批量做而非每步做——**攒批降频**的思想在引擎里到处都是（ch1 的 checkpoint 只存端点、ch5 的掩码批量填充、本处的专家批量迁移——同一工程直觉的三次落地）。上游的 EAGLE 组也有一个「每候选长度至多 drop 一块」的约束（ch1 提过），这两个「迁移/丢弃的粒度控制」都是同一个问题：**在粒度与频率之间找平衡**。EP 的部署还有一个细节值得点名：专家权重的**分卡装载**。MoE 检查点按「层→专家」组织（每层的专家堆在一起），但 EP 部署要求按「卡→专家」重新分配——装载器要把检查点里的专家权重按路由映射拆到各卡（这是 B7-9「expert 权重加载」的前半，ch8 量化章的后半讲这些权重的量化形态怎么过同一管道）。

`parallel_state.py#L2210-2245` 的 EP 组建档带着一条防死锁注释——大意：专家组的 all-to-all 与数据组的 all-reduce 如果交错发起（一个进程先做 A 再做 B、另一个先 B 再 A），两组通信互相等对方释放——经典分布式死锁；解法是**全局通信序**（所有进程按同一顺序进入通信），注释把这个约束显式写进了代码文档（并行正确性的冰山一角——冰山水面下是「每条通信路径都要可序化」的隐式合同）。

## 6.5 多卡图模式的同步边界

B7-7 的正身：**图捕获是全组协同的事**——单卡时图捕获是本地事务（捕获→重放闭环在自己卡上）；多卡时捕获区间内的通信算子（all-reduce 等）也要进图，而通信需要两卡同时到达——所以捕获必须在全组同步的窗口里做。上游机制=多卡图捕获的三层上下文（`graph_capture` 的组上下文——每卡在同一位置进入捕获、同一位置退出；通信算子嵌入图中要求两卡的前向步调一致到算子粒度）+custom_all_reduce 的 IPC 对账（通信算子进图前各卡要「对齐好握手」——自定义 all-reduce 走共享内存 IPC，两端的内存窗口要预先交换确认）。三层是：进入前对齐（确保全组站在同一位置）、捕获中同步（通信算子嵌入时的两侧握手）、退出后校验（确认全组同时离开捕获态）——**每层都是「让多台机器在做同一件事的确定性保证」**。NPU 侧的档位对齐条件（`platform.py#L1179-1199`）：TP>1 且图模式且（SP 或 shared_expert_dp 或 dsa_cp 任一开）时对齐行为有专门分支——**不是无条件 TP 约束，是特定组合下的协同边界**。这条条件句本身就是教材：多卡系统里没有「支持/不支持」的二值——每种特性组合（TP×图×SP）是一个格子，格子的可用性要单独验证，格子的数量是特性数的乘积——**这就是组合面测试债爆炸的数学根源**，也是平台层宁可禁用（ch5 的 ubatching）也不愿背矩阵债的原因。本机 TP2 的 eager 首跑不受此面影响（图模式多卡臂=阅读面+云档口径——作者已裁定选做不做，B7-7 的「TP>4」原始措辞按事实收窄为本节表述——上游机制本身是「TP>1 且特定组合」而非「TP>4」的硬边界）。另预告：ch8 量化章会看到多卡×量化的交叉（W4A16 权重的切分装载与 EP 的 expert 加载共用一段管道），多卡的边界到此还长着。

## 6.6 实验：TP 双卡首跑

## 6.7 本章小结

回扣开篇的两类失败：装不下→TP/PP 切模型（TP 通信密延迟低、PP 通信疏有空泡）、扛不住→DP 复制引擎（零通信）+EP 切专家（MoE 专属的 all-to-all）；进程公式 A+DP+N 在本机 TP2 上 4 进程实测兑现、HCCL 握手与超时链是 NPU 通信的实物证据；MoE 的负载不均催生 EPLB、图捕获的全组协同是多卡边界的最后一道。

**带走的心智**：其一，**四种切法对应四类「什么被切」**——张量/层/请求/专家——先问「我的瓶颈是什么、什么可以切」再选刀法，多数真实部署是混合切（TP×PP×DP 的三维组合）；其二，**通信是分布式的房租**——TP 每层付一次（all-reduce）、EP 每 token 付两次（来回收发）、DP 几乎不付——房租决定各切法的经济边界（大模型推理首选 TP 的原因不是它最好，而是它在「装得下」约束下通信最密而延迟最低）；其三，**多卡的正确性住在时序里**——组建立握手、捕获对齐、IPC 对账、防死锁注释——分布式 bug 多半不是算错而是「两边不在同一时刻做同一件事」；其四，**路由的随机性变成通信的不均匀性**——MoE 多卡的木桶效应催生 EPLB，「攒批降频」是这类动态再平衡的通用解法。

下一章把「装不下」推到极限形态：P 与 D 干脆分成两台机器——PD 分离与 KV 传输的 connector 生态。本章的 TP 是「计算切」（每层内切张量——空间维的并行）、下一章的 PD 是「阶段切」（prefill 与 decode 两阶段各归各的机器——时间维的分治）——同一组多卡、两种时间维度的切法；而 KV 传输正是 ch1 的块账在跨机场景的续篇（块怎么搬、怎么对齐、谁来记账），connector 生态的十七家厂商就是这笔账的十七种算盘。
