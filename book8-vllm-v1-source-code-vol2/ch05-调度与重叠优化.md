## 5.1 时间也是钱：重叠的机会成本账

Book6 的批处理五部曲教过「批」的经济学：请求凑批摊薄权重加载的固定成本。本章换一个轴：**时间轴上的重叠**——CPU 的调度决策与 NPU 的矩阵乘法是两台可以同时开动的机器，让一台等另一台就是白扔产能。Book7 走主链路时这个轴被有意按住（执行层章只到「采样分岔」为止，async 调度只点了半句名）；本章把它扶正，连同 B7-6 押来的另一半——ubatching——一起开箱。给读者一个自测锚：读完本章你应该能对着一张引擎的时间线图，指出哪几段是串行浪费、各段用什么方案能遮蔽、遮蔽的代价是什么——这三种判断力是「重叠优化」的全部。三段定位：专题=调度与执行的重叠；站段=站 8 内部+站 12 前缘；模块=`v1/core/sched/async_scheduler.py`（70 行，两轨逐字节同）+`v1/worker/` 的 ubatch 族（v0.30.0 新增件）。本章产出：async 机制正身与收益条件式（5.2+例 5.1）、ubatching 阅读面与平台禁用守卫（5.3+例 5.2）、重叠四代族谱（5.4+表 5.2）、on/off 对拍读数与负结果判读（5.5+表 5.1）。

> **最小背景栏**：Book6 ch06 的 overlap 概念（CPU 与设备并行的收益账）与 ch05 的调度决策循环是两笔旧账；Book7 ch12 的 async_scheduling 实验位（12.2 节的三分之一）已立观测方法。均指回不重教。

## 5.2 async scheduling：调度搬到执行旁

先看默认的世界：EngineCore 的 busy loop 每步先调 scheduler 做决策（哪些请求进批、各排几个 token）、再把决策交给 worker 执行——**决策与执行串行**。调度是纯 CPU 工作（扫队列、算预算、拼 SchedulerOutput），执行是 NPU 工作（前向+采样）——串行意味着 NPU 算的时候 CPU 闲、CPU 想的时候 NPU 闲。这笔浪费平时看不见，因为它藏在每一步的微观时序里——不画时间线就不知道钱漏在哪。而它的大小完全取决于两条线各多长：执行 60ms 时 2ms 调度无感（占 3%）；执行被图模式压到 9ms 时同样 2ms 就占 18%——**同一个浪费，在不同执行速度下从「可忽略」变成「第一优化目标」**，这是本章所有故事的起点。工业报告里 async 系优化动辄两位数百分比的吞吐提升{厂商自报}，全部来自「执行被压短后调度占比显形」的同一机制——读懂本章的条件式，就能分辨哪些报告的数字在你的负载上能否复现；反过来，如果你的引擎还跑在 eager+小批量上，先别碰 async——把执行压短（图模式）才是第一顺位。Book7 ch4 讲 busy loop 时说它是「有活绝不谦让的内循环」，本章补的是反面：**内循环里也有自己跟自己串行浪费的时刻**。

async scheduling 的答案朴素：**本步执行期间，CPU 预先做下一步的决策**——执行 N 步的时间线从「决策-执行-决策-执行」变成「决策₁-执行₁‖决策₂-执行₂‖决策₃…」，每步的决策藏在上一执行的影子里。落到 Book7 ch4 的 busy loop 五拍上：同步版每拍是「收消息→调度→执行→回消息→再循环」，async 版把「调度」挪到上一拍的「执行」期间做（预调度的输入是上一拍的输出快照+最新到达的请求）——**五拍的顺序没变，其中一拍的时间位置漂移了半拍**。Book7 说 busy loop 是「有活绝不谦让的内循环」，async 把「不谦让」推到了极限：连自己拍的间隙都不留。这个「半拍漂移」带来一个语义细节：预调度看到的请求状态比同步版旧一步，极端情况下新到达的请求要多等一步才进批——TTFT 的微增（5.5 实测 +68ms）部分来自这里。

**例 5.1（串行 vs 重叠的时间账）** toy 数字：设调度 2ms、执行 60ms。串行：每步 62ms、N 步 62N。重叠：首步 62ms、此后每步 max(2,60)=60ms、N 步 62+60(N−1)——省的是每步 2ms 的调度裸奔，N 步省 $2(N{-}1)$ms，占比 $ pprox 2/62 pprox3\%$。**把执行换成图模式的 8.9ms（ch4 M3 实测）**：串行每步 10.9ms、重叠后 8.9+2ms→占比涨到 $2/10.9 pprox18\%$——**执行越短、被遮蔽的调度占比越大**，这就是 async 的收益条件式。5.5 的实测负结果反过来验证了这个条件式（eager 的 60ms 执行把收益压到负）。

正身是 `v1/core/sched/async_scheduler.py` 的类声明——

```python
# vllm/v1/core/sched/async_scheduler.py#L12+#L16-27（骨架摘录）【源码：阅读锚 v0.30.0】
class AsyncScheduler(Scheduler):
    ...
        self._spec_token_placeholders: list[int] = [-1] * self.num_spec_tokens
        ...
    def _update_after_schedule(self, scheduler_output: SchedulerOutput) -> None:
        super()._update_after_schedule(scheduler_output)
        spec_decode_tokens = scheduler_output.scheduled_spec_decode_tokens
        # Use the latest num of scheduled draft tokens in next step as placeholder.
        self._spec_token_placeholders = [
            -1
        ] * scheduler_output.num_spec_tokens_to_schedule
```

指名看什么：类在 #L12 继承同步版；$-1$ 占位符的**生命周期**一眼可见——构造时初始化一列、每次 `_update_after_schedule` 用「最近一次实际排期的草稿数」重建——**占位符不是静态约定而是每步刷新的活账**，注释原话「Use the latest num ... in next step as placeholder」。它继承同步版、改写 `schedule()` 的调用时序（调度结果先存起来、下一步直接取用）；整个文件只有 70 行，因为机制的核心不在「怎么调度」而在「什么时候调度」——调度逻辑本身一字未改（两轨逐字节同，diff 零输出的正面清单又一枚）。这个 70 行是本章最美的工程细节之一：**把一个时序问题从算法问题里剥离出来**——同步版与异步版共享全部调度代码，差异只在调用时机，所以能保持逐字节同的继承而非复制粘贴的分叉。对照一下反面：如果调度逻辑里到处散布「if async: 提前算」的分支，两版会迅速漂移成两套代码——70 行的前提是**时序关注点的彻底分离**，这与软件工程里的关注点分离（separation of concerns）是同一课的引擎版。配套的握手协议是 `_spec_token_placeholders`（#L16/#L23/#L44）：投机请求的草稿槽位在异步模式下用 $-1$ 占位符顶替——**调度先于执行出结果，草稿还没回来，槽位数只能先按上界占住**；执行后草稿真回来时再替换占位符。这是 Book7 ch12:57 点名的那笔账的正身：$-1$ 是「这里将有一个数、但现在还没有」的时序标记——异步世界里数据结构的字段经常处于「上一步的值还没消费、下一步的值还没产出」的中间态，占位符就是给中间态的显式记号。全书至此出现两处 $-1$ 哨兵（ch3 例 3.4 的 draft 回填与本处的槽位占位）——**都在标记「投机数据的时间差」**：草稿从产出到验证有一步延迟，延迟期间数据结构里需要一个不与任何真 token 冲突的哨兵值；$-1$ 的选择不是审美而是语义（有效 token id 恒非负）。runner 侧的配对锚在 `gpu_model_runner.py#L3675-3679`（MRV1 面——本章实读的链；MRV2 镜像侧的 draft 回填路径在 `worker/gpu/` 一系，结构同构、行锚按主读轨纪律引用时标版本）。

> **【版本差异框注】async×spec 的互斥**——ngram 类投机与 async scheduling 不能同开：引擎自动关 async 并告警（`Async scheduling not supported with ngram-based speculative decoding and will be disabled`——ch2 实验 A 每个臂的 serve 日志里都有这行，底档在册）。机制层：ngram 提议在 CPU 上跑（ch2 例 2.2 已走查），与 async 的「CPU 预决策」抢同一台机器——两个「让 CPU 忙起来」的方案打架了。互斥的自动挡白名单在 `config/speculative.py`（v0.30.0 的 Literal 里 ngram_gpu 有特例、draft_model 在 v0.30.0 放行而 0.27.1 未放——差异续表 #26b）。ch2 实验 A 的三纪律第一条（两臂显式同置 `--no-async-scheduling`）防的就是这里：不显式关，spec 臂被自动关 async 而 off 臂开着——两臂调度器不同，测的就不是 spec 的净效应了；本章实验反过来利用了这面（无 spec 时 async 单开干净），一对实验互为反面。

## 5.3 ubatching：把一步切两半

async 重叠的是「调度与执行」；ubatching（微批切分）重叠的是「执行与执行」。机制：一个 decode 步的批切成两个微批（micro-batch），微批 A 在做注意力时微批 B 在做 FFN——像流水线上的两道工序。

**例 5.3（切分算法的 CPU dry 跑）** searchsorted 的三步走：①请求按累计 token 排序 [64, 128, 192, 256, ...]（各自的 prompt+输出预算）；②预算线画在 total/2 处（如 192）；③searchsorted 找插入位——第 3 条请求跨线，切点在第 2/3 条之间——微批 A=[req1, req2]（128 tok）、B=[req3, ...]（其余）。**边界情形**：一条请求就超预算线（超长 prompt 单发）→ 该请求独占一个微批（切不动就不切）；全部请求同长 → 完美对半。整条算法是纯 CPU 张量操作（微秒级）——切分本身的成本远小于切错的代价（不均匀=流水线空泡），所以算法宁可用保守的排序+二分也不用更聪明的贪心（聪明=难证不变量）。

**例 5.2（两道工序的流水线账）** toy：批 32 请求、单批执行 60ms（注意力 24ms+FFN 36ms，设两段可分离）。不切：每步 60ms。切两半（各 16 请求）：每微批注意力 12ms+FFN 18ms=30ms，两微批流水——理想重叠后每步 max(注意力段, FFN 段)=max(24, 36)=36ms（两微批的同类段错峰共用），**省 24ms/步≈40%**。但要付：切分计算（searchsorted 的 token 预算二分）、乒乓 buffer 的显存翻倍（两个 in-flight）、边界同步——收益条件=段间错峰的收益＞切分与同步的固定开销。正身在 v0.30.0 的 `v1/worker/` 新增件族：`ubatch_utils.py` 的切分算法（searchsorted 按 token 预算二分——把批内请求按累计 token 排序后从中间切一刀，两半的 token 量尽量均匀；**均匀是流水线收益的前提**，不均匀的微批会让快的那半等慢的那半）、乒乓不变量（两个 in-flight buffer 交替——本步的输出是下一步的输入，两套 buffer 轮转避免读写冲突——「乒乓」的名字来自一拍里 buffer 甲在写/乙在读、下一拍互换，像打乒乓球一样交替持拍）、DBO（dual-batch overlap）设计文档的四段结构（切分/执行/合并/同步——一段流水一段账）。这套件的行数不大但概念密度高：它是「把一步的原子性拆开」的完整工程化——前两章的所有结构（请求/批/块）都以「步」为原子单位，ubatch 是第一个把步内部再拆层的机制。上游设计文档给的位置也说明它的成熟度：仍带 experimental 标注（与 ch1 的 hybrid 文档同一档的成熟度信号——机制在、承诺未满）；NPU 侧的替代思路是**多流**（multistream——NPU 原生的多任务队列，让两个算子流在设备侧并行，不需要引擎层切批），这是 ch10 平台章的展开位。

**本机栈的现实**：vllm-ascend 平台层把 ubatching **显式禁用**：

```python
# vllm_ascend/platform.py#L856-867（骨架摘录）【源码：运行栈 vllm-ascend 0.27.1rc1】
        if getattr(vllm_config.parallel_config, "enable_dbo", False):
            logger.warning(
                "Parameter is currently ignored on Ascend. parameter=enable_dbo, action: resetting to False. "
            )
            vllm_config.parallel_config.enable_dbo = False

        ubatch_size = getattr(vllm_config.parallel_config, "ubatch_size", 0)
        if ubatch_size != 0:
            logger.warning(
                "Parameter is currently ignored on Ascend. parameter=ubatch_size, value=%d, action: resetting to 0. ",
                ubatch_size,
            )
            vllm_config.parallel_config.ubatch_size = 0
```

指名看什么：**两段守卫、一个句式**——`currently ignored on Ascend ... action: resetting to ...`（当前在昇腾上被忽略、正在重置为默认）；DBO 与 ubatch_size 两个参数各一段，先告警再改值、动作可观测；文案的坦率值得学——不说「不支持」而说「被忽略+已重置」，把动作与后果都交代了（上游的多流假设基于 CUDA stream 语义，NPU 的多流（multistream）调度行为未经组合验证）。守卫为什么选「忽略+重置」而不是直接报错？报错的成本是：带着 ubatch 参数的启动脚本（可能来自团队共享的部署模板）在 NPU 机器上直接死——但参数本身无害（重置后引擎完全正常），死的代价没有收益。**「参数无害但没实现」的场景，忽略+告警是正确档位**；对照 ch3 的混用后端（参数有害——行为会错，必须报错）：**守卫的档位跟着「重置后行为对不对」走**，这才是「报错优于静默」的完整版——不是一切都要报错，而是一切都要显式。这是「平台收紧上游自由度」家族的第三个成员（图模式默认档、结构化输出单后端之后）——NPU 的多流（multistream）语义与上游 ubatch 的 CUDA stream 假设不匹配，收紧换稳定。值得预告一句：ch8 量化章还会遇到第四个（某些量化格式进门即拒）——这个家族在 NPU 平台上比想象的大，ch10 收总账时会看到 vllm-ascend 的 patch 体系就是围绕这类「上游假设↔设备现实」的落差建的。

> **【考据框】平台收紧家族账（ch10 的前菜）**：①图模式默认档（vllm-ascend 平台设 FULL_AND_PIECEWISE 默认，Book7 ch8）；②结构化输出单后端（ch3 例 3.5——混用直接报错）；③ubatching 禁用（本节——置 0+告警）。三案一谱：**上游给自由度、平台按设备现实收窄**——读任何「vLLM 支持特性 X」的声明时，先查平台层的实际档位，特性矩阵的一行在具体设备上可能是三态（全开/受限/禁用）。

## 5.4 重叠族谱：四种「让机器忙起来」的方案

把视野拉远，vLLM 生态里的重叠方案有四代：①**overlap scheduler**（SGLang 的成名作——调度与执行重叠，vLLM V1 的 async scheduling 同思路；Book7 ch1 的对照表里点过名，这里的补充是：两家实现同思路不同挂点——SGLang 挂在调度器内部、vLLM 的 async 挂在 EngineCore 的 busy loop 层，挂点差异决定了与 spec/图模式的互斥面不同）；②**async scheduling**（本章正身——EngineCore 内部的时序重排）；③**ubatching/DBO**（执行内部的流水线化——5.3 阅读面）；④**CPU-GPU 重叠的 mm encoder**（ch4 的 encoder cache——视觉编码与语言解码的异步）。收成一张速查表：

**表 5.2 重叠四代族谱**（切位/资源关系/本机状态）

| 方案 | 切在哪 | 两条线的资源 | 本机状态 |
|---|---|---|---|
| overlap scheduler（SGLang） | 调度/执行边界 | CPU↔设备（零冲突） | 同思路=async |
| async scheduling（vLLM V1） | busy loop 内 | CPU↔设备（零冲突） | **实测（5.5）** |
| ubatching/DBO | 执行内部 | 设备内部（访存↔算力互补） | 平台禁用（5.3） |
| mm encoder 异步 | 模态边界 | encoder↔decoder | 观测级（ch4 J4） |

四案的共同骨架：**找到两条不抢同一资源的流水线，让它们时间上并行**；差异在切的位置（调度/执行边界 vs 执行内部 vs 模态之间）。资源维度判别法：async 重叠的两条线一台纯 CPU 一台纯 NPU（零资源冲突——所以只要时序允许就能赚）；ubatch 的两条线都在 NPU 上（抢算力——收益靠「注意力访存受限 vs FFN 算力受限」的**资源类型互补**，访存段与算力段错峰）；mm encoder 的两条线一个在 encoder 一个在 decoder（模型结构天然分界——而且多数时间里 decoder 在跑、encoder 在等下一张图，重叠窗口天然存在；ch4 实验①的同图二发 180ms 里，processor 缓存热后 encoder 段近乎归零，说明这条重叠线在 mm 高并发下的可压缩空间）。**切在哪由「哪两条线资源互补」决定**——这是比「四种方案」更本质的记法。评一句生态位：四代方案里最老思想（SGLang 的 overlap）与最新机制（vLLM 的 ubatch）在同一引擎里并存——**重叠优化没有「终局方案」，只有不断被新硬件特性重新定价的旧账**；异构算力（如 NPU 的 AI Core 与 Vector Core）会开出新的互补线，族谱还会长。判别一个重叠方案值不值，Book6 的账式仍然管用：重叠收益=被遮蔽的那段较短流水线的时长−同步开销。这个式子在本章被三次使用：例 5.1 算 async（$2/(2{+}60)$ 的占比）、例 5.2 算 ubatch（错峰省 24ms 对切分开销）、5.5 的负结果回解释（开销>收益）——**一个式子贯穿三种方案的正反判断**，这是「账式比方案长寿」的活例。

## 5.5 实验：async on/off 对拍

本节实验件在 `code/Book8-vLLM源码剖析下/ch05/async_ab.sh`（判据 J1-J5 预注册于设计书，含结果分支）。

【本机实测（Atlas 910B3，CANN 9.1.0，运行栈 0.27.1+vllm-ascend 0.27.1rc1）：底档 `log/book8-ch05/async_{off,on}.*`+`async_ab_summary.json`】——Qwen3-0.6B、eager、无 spec（隔离 async 单因子——有 spec 会被 5.2 框注的互斥自动关掉 async，双因子纠缠）、32 请求×64 token echo workload、请求率 8/s（高于 ch2 的 4/s——压出调度开销的可见度）；扫掠件 `code/Book8-vLLM源码剖析下/ch05/async_ab.sh`（沿 ch2 模板+ch4 的端口清场教训）。实验设计的一句话版：**同一 workload、同一卡、唯一变量是 async 开关**——ch2 的 a_sweep 模板直接复用（端口清场与离线变量已在脚本里固化，那些教训如今是模板的一部分）；请求率 8/s 是要让请求排队（4/s 时调度器每次只批几条、决策亚毫秒级，8/s 强制批满后调度决策的复杂度才上来）。

**表 5.1 async on/off 对拍读数**（32 请求×64 token、率 8/s、eager、无 spec）

| 臂 | 吞吐（req/s） | ITL（ms） | TTFT（ms） | config 证据 |
|---|---|---|---|---|
| async_off | 1.67 | 59.2 | 116 | `async_scheduling: False` |
| async_on | 1.58 | 63.7 | 184 | `async_scheduling: True` |
| 比值 | **0.946×** | 1.076× | 1.59× | — |

比值 **0.946×，async 反而慢 5%**（底档 `async_ab_summary.json`）。J1-J5 逐项：J1 两臂起服 ✓（config 行实证：on 臂 `async_scheduling: True`、off 臂 `False`——装配证据在档；这也是 J5 的完成态）；J2 on 臂无互斥告警 ✓（无 spec 的干净面）；**J3 落在预注册的「平/负」分支**——eager 模式+小批量（32 请求）下调度决策只占步时的很小份额，被遮蔽的收益＜async 自身的开销（占位符协议+时序重排的固定成本）；J4 ITL 对照同向（63.7 vs 59.2ms，+7.6%——decode 步变慢的方向与吞吐一致，佐证这是机制开销而非测量噪声）；J5 调度证据行两臂各有 config 实物（on 臂启动行 `async_scheduling: True`——配置层的装配证据；off 臂 `False` 对照）。除此外两臂 serve 日志的 spec 相关行均为零（无 spec 干净面确认）。**这 negative 读数本身就是账**：例 5.1 的条件式给出解释——$\text{收益} \approx \frac{t_{sched}}{t_{sched}+t_{exec}}$，本实验 $2/62\approx3\%$ 的理论上限被 async 自身开销（占位符协议+时序重排+TTFT 涨 68ms 的调度提前成本）反超成 −5%。收益条件=调度占比大（大批量/复杂调度策略/图模式把执行压得极短）——本机 eager 口径下执行太慢（60ms/步），遮不住反而更慢；把 M3（图模式，ITL 8.9ms）与 async 组合才是它的主场（步时被图模式压短 7 倍后，调度占比从 ~1% 涨到 ~7%——收益空间打开但未达临界；ch4 的 M3 未开 async 是矩阵的单因子纪律，图×async 的双因子臂留给读者的组合矩阵当扩展位）。**负结果+条件式+收益方向的三件套**，比一个孤立的正读数更接近「可迁移的判断力」——读者在自己的部署里量出 $t_{sched}$ 与 $t_{exec}$ 的比值，就能预判 async 值不值。

## 5.6 本章小结

回扣开篇的机会成本账：async scheduling 把调度搬进执行的影子里（70 行的时序重排、调度逻辑零改动——实测负结果+条件式完整解释了它的收益边界）、ubatching 把执行切成流水线（v0.30.0 新增件、NPU 平台显式禁用——「忽略+重置」档守卫的档位选择本身是课）——两种重叠在时间轴上省的是同一笔钱：**串行等待的空转**；四代族谱与资源判别法（零冲突/互补/结构分界三种切法）给了读者面对新重叠方案时的归类本能。四代重叠方案的族谱给了判别框架，互斥守卫给了边界：不是所有「忙起来」都能叠加。

本章与 ch4 合读还有一层：ch4 的组合矩阵是「空间维」（哪些开关能同开），本章是「时间维」（哪些时序能重叠）——生产调优是两个维度的张量积，每个格子都要实测或至少条件式预判。

**带走的心智**（五条，比惯常多一条——本章的判断力密度配得上）：其一，**重叠的收益=被遮蔽流水线的时长**——先量出两条流水线各多长、再算值不值，这个 Book6 的账式在源码时代原样管用；其二，**特性矩阵是三态的**——「支持」在具体设备上可能是全开/受限/禁用，平台层守卫才是真身（三案一谱）；其三，**两个 CPU 优化会打架**——ngram（CPU 提议）与 async（CPU 预决策）互斥的教训：优化方案不独立，组合前先查资源竞争；其四，**负结果+条件式＞孤立正读数**——async 在 eager 小批量下慢 5% 的实测配上 $t_{sched}/(t_{sched}+t_{exec})$ 的收益式，读者在任何部署里都能预判值不值——这是本书反复示范的「可迁移判断力」的又一次落地；其五，**占位符是异步世界的语法**——$-1$ 哨兵、预存槽位、「上一步值还没消费」的中间态，读异步代码先找占位符的生命周期（谁初始化、谁刷新、谁消费），占位符的轨迹就是异步时序的轨迹。

下一章把单卡引擎摊开成多卡：TP/PP/EP/DP 四种切法与通信账——「一张卡装不下」与「一张卡扛不住」的两类答案。本章的重叠与下一章的切分在生产部署里又是一对乘法：多卡的通信段（all-reduce 的等待）是最典型的「可遮蔽流水线」——TP 的通信与计算重叠正是 overlap 思想在分布式尺度的重演。
