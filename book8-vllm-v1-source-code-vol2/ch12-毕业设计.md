## 12.2 全链走查：一条请求穿越八册

收官主线：**一条请求**（`"Generate a sonnet about attention"`）从进引擎到出 token，每一步对应一册的知识——

1. **Book1**：请求里的「attention」这个词的向量表示，最终要过一个 $\text{Attention}(Q,K,V)=\text{softmax}(QK^T/\sqrt{d_k})V$——原典公式（2017）是这一切的起点。
2. **Book2-3**：模型是 GPT-2→LLaMA 式的 decoder-only 架构——预训练学会了语言统计、组件改装（RMSNorm/SwiGLU/RoPE/GQA）让 207M 的底子跑得更快。
3. **Book4-5**：如果换成 MoE 或混合架构——专家路由把前向拆到多张算力卡（ch6 的 EP）、混合层的 KV 形态变（ch1 的 hybrid 组）。
4. **Book6**：请求进引擎前，调度器要决定批型（continuous batching）、KV 预算（分页+前缀缓存）、投机与否（α 收益账）——推理物理学的全部决策在这几百毫秒内完成。
5. **Book7**：请求穿过 17 站——入口（站 1-6）→EngineCore（站 7-8）→KV 管理（站 9）→执行（站 10-12）→采样（站 13）→输出（站 14-17）——每一站的模块在 Book7 各章精读过。
6. **Book8**：在 17 站的骨架上长出的九个专题——本章的请求如果带 json_schema 就过文法约束（ch3）、如果 drafter 开着就带着 3 个草稿位一起走（ch2 的 k+1 批形状）、如果部署在 4 卡上就每层 all-reduce（ch6）……

**走查的要害**：这不是知识点的罗列——是**同一条请求在八册知识中的投影**。读者应该在脑中放出这部电影：一句话进去、一串 token 出来、中间每一步都有八册中的某一页在照亮它。图 12.1（八册×17 站总地图——ch13 图 13.1 的底图）是这部电影的单帧截取。

## 12.3 源码新芽导读：引擎的下一站

大项目走完，引擎还在长——**六个 A 档新芽**（notes/02 子交付①，v0.30.0 里已发芽但未成熟的模块）：

1. **hisparse**（HiSparse 三态 KV——Source/Hot/Resident 分区——ch1 的稀疏双 spec 长出来的完整子系统，大上下文稀疏注意力的引擎侧正身）。
2. **watermarking**（水印——LLM 生成内容的水印嵌入与检测，生产合规的前置件）。
3. **fault_tolerance**（引擎级容错——worker 故障恢复/checkpoint 恢复，从「崩了重启」到「崩了续跑」的进化）。
4. **ec_transfer**（EngineCore 传输——PD 分离的进阶形态，EngineCore 进程本身跨机迁移）。
5. **weight_transfer**（6753 行——权重传输子系统，PD 分离的启动加速：D 侧从 P 侧拉模型而非各自下载）。
6. **`vllm/models/` 硬件隔离新包**（kimi_k3 11093 行等——每硬件家族一个子包，模型代码从 `model_executor/models/` 迁出——硬件适配从 patch 升级为目录级隔离）。

**例 12.1（全链走查的一步）** 以 drafter 的一个草稿 token 为例追踪它在八册中的投影：这个 token 是 drafter 的 forward 输出（Book1 的 attention 矩阵乘出来的）→ 通过 RoPE 位置编码获得了位置信息（Book3 的组件改装）→ 它的生成概率分布来自一个 2 层 89M 的小模型（Book2 的预训练让它学会了语言统计的近似）→ 它作为三个草稿之一被送入 target 的验证前向（Book6 的投机解码理论说它有 α 的概率被接受、Book7 的 17 站走查画出了它从 drafter 到 rejection sampler 的路径、本册 ch2 的源码精读给了装配链每一行的锚点）→ 如果被接受它就成为了输出的一部分、如果被拒绝就触发 num_computed_tokens 的回滚（ch2 §2.2 的回滚账面）→ 最终出现在用户的屏幕上（ch7 的输出链——EngineCore→detokenizer→SSE）。**一个 token 的一生，就是八册书的全息图**。

**导读的意义**：这六个芽告诉读者「这套书的方法论怎么自己读新东西」——先看它在 17 站的哪几站上（地界定位）→再看它付的是哪笔账（ch1 的「每笔账有家」心法）→最后看它的配置面怎么用（引擎的统一学习路径）。**毕业设计的真正交付不是那个 207M 服务，是「能独立读懂引擎任何一个新子系统」的能力**。

### 12.3.1 全链走查的展开

例 12.1 给了一个 drafter token 的投影——全链走查还有更宏观的读法：**把一条请求的完整旅程按时间轴展开**。

**T=0ms**：用户发送 HTTP POST——请求进入 vLLM 的 API server（Book7 ch3 的入口层精读——FastAPI 的 uvicorn worker 收包）。**T=1ms**：请求被解析（chat 模板应用——Book7 ch11 的 chat template 走查）；如果带图（ch4 的五步管线在此启动——PIL 造图→processor resize→ViT encode→投影→拼接）；如果带 schema（ch3 的 grammar_init 在此异步启动——schema 编译进 EngineCore 线程池）。**T=5ms**：EngineCore 的调度器决定本步排谁进批（Book7 ch5 的决策循环——token 预算/KV 余量/抢占判定三查；如果 drafter 开着，调度器多排 k 个草稿位——ch2 的 lookahead 预留）。**T=10ms**：执行层的前向开始——28 层依次算过（每一层内部：RoPE 位置编码→attention（NPU 走 ACLGraph 捕获的 fused 核——Book7 ch8/ch9 的图执行与 attention 后端）→RMSNorm→SwiGLU MLP；如果 MoE 在此层有专家，all-to-all 通信把 token 送到专家所在的卡——ch6 的 EP 路由）。**T=50ms**：前向完成——logits 出来，sampler 采样（无约束走 Book7 ch11 的九步采样；有文法约束走 ch3 的 bitmask 施用——禁位设 $-\infty$ 后 softmax；有 spec 走 ch2 的 rejection sampler 逐位裁决）。**T=51ms**：采出的 token 经 detokenizer 增量解码（Book7 ch11 的 incremental detokenization）、经 SSE 流推给用户。**T=52ms**：如果 drafter 在跑，下一个循环开始——drafter 出下一轮草稿、调度器排下一批。

**这条时间线的每一毫秒都是八册书的一页**——读者如果能在脑中按毫秒级放出这部电影，就真正读穿了这套丛书。

### 12.4 全链走查的八册投影（展开版）

12.3.1 的毫秒时间线是从引擎视角看的——现在从**八册知识视角**看同一条请求。**Book1 的投影**：请求里的每个 token 的 embedding 向量、每层 attention 的 $QK^T/\sqrt{d_k}$ 缩放点积——原典公式的每一步都在 28 层中各执行一次。**Book2 的投影**：这个 207M 模型的权重是预训练的产物——它学到的语言统计让它在 prompt「one two three four five six seven」后自然接「eight nine ten」。**Book3 的投影**：模型不是原始 Transformer——RMSNorm 替了 LayerNorm、SwiGLU 替了 FFN、RoPE 给了位置信息、GQA 把 KV 头从 16 压到 8（KV 存储减半的直接原因）。**Book4 的投影**：如果这是 MoE 模型，每层的前向会多一步路由——top-k 专家选择+all-to-all 通信（ch6 的 EP 专题）。**Book5 的投影**：如果这层是滑窗注意力，KV 只存最近 W 个 token（ch1 的混合组管理）。**Book6 的投影**：调度器在排队论意义上是一个 $M/G/c$ 系统——Little 定律 $C=\lambda\times T$ 给出并发数与延迟的关系，容量规划的根基。**Book7 的投影**：请求从 HTTP 进来到 SSE 出去穿越的 17 站——每一站的模块在那一册精读过。**Book8 的投影**：drafter 的草稿、文法的掩码、adapter 的旁路、图模式的重放、多卡的 all-reduce、KV 的传输带、量化的反量化、指标的上报——九个专题在 17 站的骨架上各自生长。

**八册投影的含义**：同一条请求在八册书的每一册中都有一个截面——截面各不同但请求是同一条。**把八个截面对齐，就是「从模型到服务」的完整知识图谱**。

### 12.5 源码新芽导读的完整版

六个 A 档新芽各给一段「是什么/为何前瞻/入口锚」——**hisparse**：HiSparse 三态 KV（Source/Hot/Resident 分区）——大上下文稀疏注意力的引擎侧正身；ch1 的稀疏双 spec 在这里长成完整子系统——入口 `vllm/v1/kv_cache_interface.py` 的 HiSparse 族。**watermarking**：LLM 生成内容的水印嵌入与检测——生产合规的前置件（AI 生成内容的溯源）；入口 `vllm/watermarking/`。**fault_tolerance**：引擎级容错——从「崩了重启」到「崩了续跑」的进化；入口 `vllm/v1/engine/fault_tolerance/`。**ec_transfer**：EngineCore 传输——PD 分离的进阶形态，EngineCore 进程本身跨机迁移；入口 `vllm/distributed/ec_transfer/`。**weight_transfer**：6753 行——PD 分离的启动加速：D 侧从 P 侧拉模型而非各自下载；入口 `vllm/distributed/weight_transfer/`。**硬件隔离新包**：`vllm/models/` 新顶层（kimi_k3 11093 行等）——每硬件家族一个子包，模型代码从 model_executor/ 迁出——硬件适配从 patch 升级为目录级隔离。**六芽的共同信号**：引擎正在从「单机服务」向「分布式+合规+容错」的生产形态全面进化。

### 12.8 源码新芽导读的方法论深化

12.5 给了六芽各一段——现在深化**怎么读**的方法论。三步法的完整版——**第一步地界定位**：`ls vllm/新芽名/` + `wc -l vllm/新芽名/*.py`——文件数和行数告诉你体量级（<1000 行=小件、1000-5000=中件、>5000=大件）；再 `grep -rn "class.*:" vllm/新芽名/ | head -10`——类名告诉你它怎么组织（一个基类+多个实现？还是平铺的函数族？）。**第二步付的账**：读每个文件的 docstring 首段——`"""Save KV layer for async copying during execution."""` 一句话告诉你它做什么；再 grep 它在引擎主链路的调用点——`grep -rn "from vllm.新芽名" vllm/` 告诉你谁在用它（如果零调用说明它是独立子系统、有调用说明它是嵌在主链路的）。**第三步配置面**：`grep -rn "VLLM_" vllm/新芽名/` + `grep -rn "新芽名" vllm/config/`——环境变量和 config 字段告诉你用户接口在哪里、怎么开怎么关。**三步的工具是 Unix 原生的**——不需要 IDE 不需要文档工具，一个终端读完任何新子系统。这套丛书从 Book1 的第一个 toy attention 到本册的最后一个 connector 用的都是这三步的变体。

### 12.9 全书的暗线：从公式到生产

### 12.11 毕业设计的完整时间线走查（终版浓缩）
