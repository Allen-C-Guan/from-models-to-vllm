## 3.1 开篇：把「请输出 JSON」变成每一步的硬约束

Book6 讲采样与 logits 处理器时留下半句分野：「另一族『硬约束截断』（语法/格式的强制掩码）是结构化输出的地界 → Book8 第 3 章」【Book6 ch09-采样与logits处理器.md#L31】——软变换（top-p/惩罚项改分布的形状）Book6 已教，硬约束（把非法 token 的概率直接钉死为零）是本章的正菜。Book7 第 11 章在协议面做了两层实证（官方 UT 7/7+激活探针双钩子；guided_json 请求的 happy path），并把机制层留在这里：「结构化输出管线（xgrammar/guidance 机制层）→ Book8 第 3 章」【Book7 ch11-OpenAI兼容层.md#L155，B7-4】；Responses 面的那句定位也一并到期——「三扇门共享同一个引擎出口，机制层归 Book8 第 3 章」【同文件#L128】。

本章的问题：**一句「请输出 JSON」，是怎么变成采样器里每一步的硬约束的？** 三段定位：专题=结构化输出；站段=站 3+8+12/13；模块=`vllm/v1/structured_output/`（8 文件 2556 行——Manager 正身在 EngineCore 侧，机制主体不在 worker 镜像里；MRV2 的掩码上卡件在 `worker/gpu/structured_outputs.py` 点名）。产出：管线正身（图 3.1）、四后端对照与两轨口径（表 3.1）、四件实验读数（编译账/稳态开销/正确性/单后端 patch——表 3.2）、论文链的口径课。

> **最小背景栏**：上下文无关文法（context-free grammar，CFG）的最小概念——产生式规则递归定义语言（JSON/SQL 是 CFG 的经典语言、正则是其真子集），本章用到「文法处于某状态时哪些 token 合法」这一句即可；约束解码（constrained decoding）与结构化输出（structured output）互训。软/硬 logits 处理器分野=Book6 ch09；OpenAI 协议三扇门=Book7 ch11。

```python
# vllm/v1/core/sched/scheduler.py#L2979-2988【源码：阅读锚 v0.30.0（ced6857）；运行栈同文】
        if request.status == RequestStatus.WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR:
            structured_output_req = request.structured_output_request
            if not structured_output_req or structured_output_req.grammar is None:
                return False
            if isinstance(structured_output_req.grammar, Exception):
                self.grammar_compile_error_reqs.add(request.request_id)
                return False
            request.status = RequestStatus.WAITING
            return True
```

指名看什么：**三分支**——grammar 槽位还是 None（编译在途）→`return False` 本轮不调度；grammar 槽位是 **Exception**（编译失败）→`grammar_compile_error_reqs` 记账后返回（**单请求失败、不炸引擎**——错误隔离的调度器侧正身）；否则转 WAITING 放行。编译的成品或异常都从同一个槽位读出——「一个字段两种命运」的枚举式错误处理。

## 3.3 编译期账：异步、等待态与 512MB 缓存

编译发生在 EngineCore 进程、**异步**（线程池 `max_workers=(cpu+1)//2`，`__init__.py#L76-78`；`executor.submit(self._create_grammar, request)`）——但有一种部署形态必须关掉异步：

```python
# vllm/v1/structured_output/__init__.py#L47-56【源码：阅读锚 v0.30.0（ced6857）】
        # When in external_launcher mode, async grammar compilation causes deadlocks
        # due to external_launcher mode having a scheduler for each TP rank.
        # Async grammar compilation causes the
        # WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR → WAITING transition to
        # happen at different times on different TP ranks,
        # breaking the determinism assumption that external_launcher relies on.
        self._use_async_grammar_compilation = (
            vllm_config.parallel_config.distributed_executor_backend
            != "external_launcher"
        )
```

指名看什么：`external_launcher`（torchrun 式外部启动，每 TP rank 一个 scheduler）下异步编译会使「等待态→WAITING 的迁移时刻」各 rank 不一致——**一个兼容性开关背后是一段确定性论证**（谁在什么前提下才许异步）。异步的代价去哪了？用人话说：**把编译挪出调度的关键路径、用一个等待态换不阻塞**——引擎不等编译，编译好了再进队。账面落点：**编译等待落 request_queue_time 账**，闭环三锚：等待态期间不被调度（scheduler#L2979-2988）→`queued_time = scheduled_ts - queued_ts`（`metrics/stats.py#L543`）→直方图 `vllm:request_queue_time_seconds`（loggers.py 注册/observe）。一句话：**编译慢不慢，前端 queue 直方图先看见**——无需任何侵入观测即可读编译账，这正是实验②TTFT 差分法的理论根据。实操一面：`vllm:request_queue_time_seconds` 是标准 Prometheus 直方图（ch9 的指标字典会给它的 bucket 与标签面），serve 场景抓一次 `/metrics` 就能看分布——**结构化请求占比高的服务，queue 直方图的右尾就是编译账的形状**；如果右尾随时间不降，先查是不是「每请求唯一 schema」击穿了缓存（例 3.5 的击穿模式）。这也给了一个无需改代码的巡检判据：同 schema 稳态服务的 queue 右尾应当收敛到毫秒级。

缓存把编译摊掉：`XgrammarBackend` 构造 `xgr.GrammarCompiler(cache_limit_bytes=VLLM_XGRAMMAR_CACHE_MB*1024*1024)`（`backend_xgrammar.py#L66-70`），默认 **512MB**（envs.py，两轨同值），缓存键=`get_structured_output_key`。消歧一句：grammar cache（编译缓存）≠ APC（前缀缓存，Book7 ch06）——前者摊「文法编译」的一次性成本、后者摊 prefill 的计算成本，两本账互不遮挡（一个服务可以两个都吃满）。推论立成纪律：**「首请求（miss）」与「缓存命中（hit）」是两种工况，报告必须分开**；测纯编译开销用逐请求唯一 schema 强制 miss。

**例 3.1（512MB 缓存的 LRU 账）** 构造：单文法的自适应掩码缓存约 0.46MB（论文 Llama-3.1+JSON 单文法读数——3.8 节；用作每份体积是数量级估算口径）；toy 缩小池=1.0MB（≈2 份）。输入四步访问序列 A,B,C,A：第 4 步 A 已被 LRU 逐出→重编一次。输出读数：真机 512MB÷0.46MB≈**1,113 份编译产物常驻**——「缓存为什么够用」的数量级直觉：一个服务的 schema 集合（几十到几百个 API 的返回格式）远小于千份量级，miss 在稳态服务里是稀有事件；会击穿缓存的只有「每请求唯一 schema」的模式（动态生成 schema 的网关型负载——那时编译账回到每请求一次，schema 型格式天然复用、罕见逐请求唯一；动态 regex 才是击穿工况的常态载荷——且 obj_basic 的 24ms 半是预热账（表 3.2 ①），真实每请求账以 str_pattern 的 14ms 为准）。（位置：cache_limit_bytes 构造正身同上；0.46MB=论文 p.5-6。）

**例 3.2（编译期 vs 执行期：一条请求的时间线两工况）** 构造（toy 假设值，实测由 3.7 实验①回填）：请求 t=0 到达，编译 220ms、调度等待 90ms、出首 token。输入两工况：①首请求（miss）——queue=310ms（等待态吞掉编译+调度）；②同 schema 第二请求（hit）——queue=90ms；差分 310−90=220ms 恰是编译账。输出读法：**编译是一次性成本、缓存把它摊掉；每步掩码的执行期开销不在 queue 里、在 ITL 里**——两个账本分开读，混读会把一次性成本报成稳态税。（位置：实测=3.7 表 3.2 的 miss/hit 两行；queue 口径三锚同上。）

## 3.4 掩码怎么施：每步只开少数几扇门

掩码的本体制只有一个直觉：**在文法的每个状态下，词表里只有极少数 token 是合法后继**。用 toy 词表走一遍：

**例 3.3（mini 词表上的掩码演化）** 构造：toy 词表 8 个 token——`{`、`"`、`a`、`:`、`1`、`2`、`}`、`x`（id 0-7）；schema 等价文法 S→`{` `"` a `"` `:` N `}`、N→`1`|`2`。输入四步（每步=已生成前缀→8 维掩码向量）：
①前缀空：{0:1}（只 `{` 开门）；
②已生成 `{`：{1:1}（只 `"`）；
③已生成 `{"a":`：{4:1, 5:1}（N 展开两通道）；
④已生成 `{"a":1`：{6:1}（只 `}`）。
输出读法：四步的开通道数=1,1,2,1——**硬约束=把 softmax 的整个词表前景裁成窄门**；token `x` 四步全关。全词表 151k 的真机同理，只是掩码从 8 维变成 $(B_s,\lceil V/32\rceil)$ 的位打包矩阵。（位置：fill_bitmask 正身=`__init__.py#L202`；并行阈值 128/批 16 见 3.2。）

施用侧三件小事：其一，`_fill_bitmasks` 对大批量并行填（大于 128 个结构化请求时线程池分批 16 并行——**每步的掩码构造是 CPU 活**：文法状态机的推进与位打包都在主机侧，批大了会顶到调度延迟；阈值 128 与批 16 的量级感——量级感上单请求掩码构造应远小于毫秒、128 个以下串行的总开销预计低于线程池派生的固定成本，过了才值得开池——此账未实测，如实登记）；其二，`apply_grammar_bitmask` 在采样前把 logits 的非法位置 $-\infty$（utils.py#L100；MRV2 的上卡核版本在 worker 镜像——位打包矩阵整块上卡、核内按位展开，避免逐 token 的主机往返）；其三，掩码只对「批内带结构化约束的请求」行生效——$B_s$ 是子批，普通请求同行 logits 不动（**混合批是常态**：约束请求与自由请求同批调度，掩码按行选择性施用）。走查一遍这个混合批：8 请求里 3 条带 schema——掩码矩阵就是 3 行而非 8 行，构造与施用两侧都按行索引跳过自由请求；这解释了为什么约束开销随「批内占比」而非「批大小」缩放——生产负载里结构化请求占比两三成时，约束税相应只打在那两三成上。

一笔账把 3.3/3.4 连起来：**约束的总成本=一次性编译（miss 时毫秒级，缓存摊掉）+每步掩码构造（CPU 微秒级×并行）+每步施用（GPU 一条掩蔽核）**——三笔账住在三个层（编译器/主机 CPU/设备），观测口径也分三个面（queue 直方图/调度延迟/ITL）。读任何约束系统的性能声明，先问它报的是哪一笔。

读法两句话：正向读——四后端共享 Backend/Grammar 抽象双件套，「换后端」=换编译器与缓存策略，掩码施用链不变；反向读——**三种缓存策略（内存/无缓存/磁盘）是同一问题的三个工程答案**，读后端族的钥匙是「编译产物住在哪、活多久」：xgrammar 把编译产物养在进程内 512MB（命中即免编）、guidance 每请求现构造 LLMatcher（无缓存但构造轻）、outlines 落盘跨重启——「贵的产物值得缓存，便宜的产物现做现扔」，这个取舍读任何编译器族都通用。四后端的依赖**本机全在装**（xgrammar 0.2.8/llguidance 1.7.6/outlines_core 0.2.14/lm-format-enforcer——实测 import 全通），「auto 解析到异后端」因此是真实的运行时分支而非纸面配置。记号消歧随表立死：结构化输出的 **backend** 与 attention/量化 backend 同名不同物（connector=KV 传输器/backend=后端/adapter=LoRA 件——三物对照第三次）。

协议面的两代行为是本章最好的一堂「同名 API」课：

> **【考据框】guided_json 的两代死法**。0.27.1（运行栈）：请求体带 `guided_json` 字段——pydantic 模型里没这个字段、extra=allow **静默丢弃**，模型裸奔输出散文（体检 11 号实物：同 prompt 下输出 "Sure! Here are three common fruits:..." 散文、completion_tokens=27）；0.30.0（阅读锚）：guided 族六字段**整体移除+显式 warning**（`protocol.py#L20-34` 的 `_REMOVED_GUIDED_FIELDS`，注释原话点名 #53975——「requests still using them get HTTP 200 with unconstrained output and no visible signal. Warn instead of burying the only breadcrumb at DEBUG level.」）。正身入口是 `response_format`（json_schema 型）：12 号实物——同 prompt 输出 `{ "fruits": ["Apple","Banana","Orange"] }`（合法 JSON）【本机实测底档 `log/env-audit-20261011/{11,12}_guided.json`】。两代对照的教训：**静默丢字段比报错危险一个数量级**——上游修的正是运行栈踩过的坑（与 Book7 logprobs 两代语义是姊妹案例）。

请求体的正身形态（12 号模板——`response_format` 的 json_schema 型，本章实验的母版）：

```json
// log/env-audit-20261011/12_guided_smoke.sh#L29（请求体模板原文）
"response_format": {"type": "json_schema", "json_schema": {"name": "fruits",
  "schema": {"type": "object", "properties": {"fruits": {"type": "array",
  "items": {"type": "string"}}}, "required": ["fruits"]}}}
```

入口链两行：前端 `extract_structured_outputs`（运行栈 `chat_completion/protocol.py#L641`——把请求约束归一为 StructuredOutputsParams）→引擎侧 `structured_outputs_from_response_format`（`openai/engine/protocol.py#L179`）——**三扇门（chat/completion/responses）在此汇成同一个内部参数对象**，Book7 那句「共享同一个引擎出口」的落点。

NPU 侧还有一件平台收紧件（Book7 ch11 的两级实证在此进机制层）：`patch_structured_output.py`（134 行）——`_raise_mixed_backend`#L46-50 在引擎已初始化后端后再遇异后端请求时抛 `VLLMValidationError`，把上游「同引擎可换后端」的自由度收紧为**单引擎单后端**：

**例 3.4（auto 混用后端的三步走查）** 构造：①serve 以 `backend='auto'` 起（启动行 config 实物：`StructuredOutputsConfig(backend='auto', disable_any_whitespace=False, …)`——12 号 serve 日志#L45）；②首请求（json schema）→auto 解析为 xgrammar 并**记到 config**（Book7 激活探针读数 `cfg_backend_recorded_by_patch`——引用 Book7 底档不重跑：UT 7/7+双钩子在位）；③第二请求显式要求 guidance→`VLLMValidationError: The engine is already using 'xgrammar', but …`。输出读法：**报错优于静默**——与考据框的 guided_json 静默丢恰成对偶（同册两个「静默 vs 显式」案例）；解法=启动时显式配 `structured_outputs_config.backend`。（位置：本机四后端依赖虽全在装，但「auto 首请求解析+异后端混用」的行为级证据仍引 Book7 底档（UT 7/7+激活探针双钩子——引用不重跑）；此为平台收紧第二案例，与 ch2 的 ngram×async 互斥同族，总账在 ch10。）

## 3.6 spec×grammar 交叉：最长合法前缀与 −1 哨兵

结构化输出与投机解码（上一章）共享一条采样路径，交叉点的正身是 `validate_tokens` 三件套（v0.30.0 的 #15 重构）：draft 块进 Manager 后，`strip_speculative_padding`（utils.py#L48-61——docstring 自述：ngram 等投机后端用 **−1 哨兵**填拒绝位，剥离要「before tokens reach any backend, rather than inside a single backend」——从后端内部**上提到管理器**统一处理，这就是重构方向本身）→`_get_constraint_start`→`grammar.validate_tokens`（`__init__.py#L294`，docstring 原语 "Return the longest unconstrained or grammar-valid prefix"——**draft 验证=最长文法合法前缀**，与 ch2 的贪心前缀同构）。（位置：validate_tokens=`vllm/v1/structured_output/__init__.py#L294`+`vllm/v1/core/sched/scheduler.py` 回填段 #L2443-2458；分母剔除=scheduler.py#L2811-2812。）

**例 3.5（最长合法前缀与 −1 哨兵）** 构造：文法 S→`a` `b` `c`；draft 块 spec_tokens=[a, b, x]（k=3，第三位 x 非法）。输入五步：①draft 块进 manager；②`strip_speculative_padding` 查 −1（本例无 padding，原样过）；③constraint_start=0（无推理窗）；④`validate_tokens` 走栈——a 合法推进、b 合法推进、x 非法停住→返回 [a,b]；⑤scheduler 回填 `[-1]` 补长→[a,b,−1]，`num_invalid_spec_tokens=1`。输出读法：acceptance 口径里**分母 3−1=2**（grammar 判废草稿从 draft 分母剔除、不从 accepted 分子剔——`make_spec_decoding_stats` 的剔除账，scheduler.py#L2811-2812）——spec+结构化同开时 acceptance 读数偏「乐观」的机制根，ch2 脚注在此兑现。

> **【版本差异框注】拒绝语义两轨不同**：阅读锚侧 draft 被文法拒绝→log error+标 failed 继续（`__init__.py#L398-412`，"Unexpected: grammar terminated or rejected draft token …"）；运行栈侧同场景直接 `raise AssertionError`（运行栈 `__init__.py#L329`，grammar_bitmask 内联循环内）——0.27.1 的行为是「崩线程」、v0.30.0 演化为「记错误继续」，spec×grammar 组合在生产上的成熟度代际差，读旧栈日志时先认这个语义——实例：0.27.1 上同开 spec+grammar 偶见的 EngineCore 崩溃栈若落在 `grammar_bitmask` 内联循环（#L329 一带），十有八九就是这条拒绝语义而非「模型输出坏 token」。

实验③的失败分支值得多看一眼（预注册的「区分 schema 过严/模型能力与引擎约束失效」分支）：失败模式是 **parse_ok=false**（截断）而非 schema_ok 单独失败；归因不止于症状推理——**定谳探针**已干预验证：同卡同 seed 给 obj_nested 的 tags 加 `maxItems:4` 重跑，输出即完整合法（底档 `log/book8-ch03/exp3_attribution.md`）——归因从「症状指向」升为「干预定谳」——如果引擎约束失效，症状应是「parse 通过但字段类型错」；实际症状指向 token 预算。修复有二：schema 加 `maxItems`（约束面收口）或加 max_tokens（预算面放宽）——**同一故障的两个修法住在不同的层**，这正是「schema 即接口」的教学点。

顺着「schema 即接口」再补一张严格度的地图（启动行 config 里的开关与 schema 字段就是几个旋钮）：`required`（schema 层——哪些字段必须出现；引擎把它编译成文法的必经分支）、`additionalProperties: false`（schema 层——禁止多余字段；引擎侧另有总开关 `disable_additional_properties`——置 True 时给 schema 统一补这行收紧，默认 False=按 schema 原样尊重作者选择）、`disable_any_whitespace`（引擎层——是否容忍 token 化产生的跨结构空白）。三个旋钮各住一层（文法必经性/字段封闭性/词面容忍度），组合出「严格度光谱」：最松（无 required 约束的开放 object）到最严（全封闭+无空白）——**严格度每拧一格，模型在窄门里的出错率与输出长度分布都跟着变**。实验③的 maxItems 教训在此一般化：schema 不是「描述格式」的文档，是**参与采样与预算的运行时接口**。

## 3.8 论文链：一个摘要里的两个口径

机制的正身之外，这条线的论文值得一段考据——不为掉书袋，为**读数字的口径纪律**。xgrammar（2411.15100，MLSys'25）摘要同句住着两个口径：「up to 100x speedup over existing solutions」（**编译/掩码构造口径**，对比既有效果引导方案）与「near-zero overhead in end-to-end serving」（**端到端口径**）——三个数字并排先对口径：SGLang v0.4 博客的「up to 10x faster than other open-source solutions for JSON decoding」是端到端 JSON 口径{厂商自报}。本章实验②的 +13.4% 就是端到端口径的本机读数——与「near-zero」不矛盾（百分比级 vs 数量级加速的陈述面不同），但**引用时必须声明口径**。机制数字两条（论文 §3）：context-dependent token 只占**不足 1%（1134/128k，Llama-3.1+JSON 文法）**——这个数字的直觉值得展开：JSON 文法里，`{`、`"`、`:`、`,`、数字与字母这些 token 的后继集合**几乎总是确定的**（`:` 后面必是值、`,` 后面必是键），真正依赖上下文的只有少数「多岔口」token（比如一个值可以是数字或字符串或嵌套的开头——后继开哪些门要看前文走到哪了）。所以掩码不必逐请求重算全套：**绝大多数 token 的门是常开的（或常关的），可以预检预存**——这就是自适应掩码（adaptive token mask）的根，也是例 3.1 里那 1,1,2,1 的窄门在 15 万词表上的推广；实现上用持久栈（persistent stack）做多请求共享的文法状态（考据框级一句点到）。第二条：自适应存储把掩码缓存从 160MB 压到 **0.46MB（0.2%）**——压缩的两级：预检的常开/常关 token 不占存储、只有 context-dependent 的 1134 个 token 才按状态存门【官方论文 PDF 直读】。续作 XGrammar-2（2601.04426，ACM CAIS'26：TagDispatch+跨文法缓存，over 6× 编译加速）**未进 v0.30.0**（`backend_xgrammar.py` import 的是 xgrammar 1 系 API）——论文跑在引擎冻结前面，作 ch12 新芽候选登记——它的 TagDispatch（按工具调用的 schema 结构分派）与跨文法缓存正对着「每请求唯一 schema」这个 xgrammar 的残余软肋（例 3.1 的击穿工况），值得留档观察。

## 3.9 本章小结

回扣开篇：「请输出 JSON」的旅程=站 3 进协议参数→站 7/8 异步编译与等待态（queue_time 落账、512MB 缓存摊一次性成本——例 3.2 的 310−90=220ms 分账）→站 8 每步位打包掩码（例 3.3 的 1,1,2,1 窄门）→站 12 施于 logits、站 13 回灌推进文法；四后端共享抽象双件套、三种缓存策略三种工程答案（表 3.1）；实测四件把账配齐——miss/hit 两个数量级、稳态 +13.4%、正确性 24/32（maxItems 教训）、单后端收紧（例 3.4）。spec×grammar 的交叉账（例 3.3 的 −1 哨兵与乐观口径）把上一章的脚注兑现。

**带走的心智**：两幅画。**其一，文法状态机就住在采样器隔壁**——每一步生成前，词表被裁成窄门（1,1,2,1）；读任何约束系统的行为，先问「门谁开的、开多大、开多久」。**其二，一次性账与稳态账分开读**——编译 miss/hit 差两个数量级（缓存摊掉）、每步掩码 +13.4%（稳态税）；加上「读论文先对口径」（100×是编译、10×是端到端）——**三层账本意识是结构化输出的全部经济学**。

镜头拉回全书：本章把「输出的形」钉进了采样器；下一章转向「输入的胖」（多模态请求与 LoRA 外挂——图片进请求后哪几站要改账、外挂权重怎么不重载地改行为）。而本章的约束开销读数与后端支持面，将在 ch11 的选型决策表里作为服务能力维度回收（合规维度一行）——约束引擎的账，最终要进服务选型的总账。
