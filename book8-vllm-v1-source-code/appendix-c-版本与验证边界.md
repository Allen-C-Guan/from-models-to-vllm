# 附录 C 阅读版本、后续变化与验证边界

## C.1 固定版本是一份可复查的阅读坐标

本书上游阅读锚为 **vLLM v0.30.0 / `ced6857afa0ea7b2e3f0846a62e1394e90f15607`**，Ascend 分支为 **v0.30.0 / `c09d3e20b9c45c80b34ae3781440d90904a44023`**。正文中的教学源码保留固定提交原文，只插入可剥离的中文注释。在线链接固定到提交，不指向持续变化的 main。

本次运行环境也已升级到 0.30.0。旧材料所说的“0.30 源码与 0.27 运行栈对照”不适用于本书新记录。版本号一致仍不能替代实现核对：平台插件可能选择不同 Worker、Runner、Attention 和调度器；探针因此同时记录实际类、方法位置与文件哈希。

本机使用 Ascend 910B2、CANN 9.2.1、torch 2.10.0、torch-npu 2.10.0.post7。基础模型是 Qwen3-0.6B 的固定快照，具体参数见[基础实践](实践与证据.md)。TP/PP 使用两张设备，其他端到端案例使用单设备；CPU 契约实验不加载模型到 NPU。

## C.2 后续版本改变什么，如何回查

2026-11-02 定向核对了官方 v0.31.0、v0.32.0 发布说明，并沿用本次架构调研保存的八个 v0.32.0 核心文件快照进行结构对照。本书继续固定 v0.30.0，既没有升级实验环境，也没有把后来增加的能力写成旧版已经具备。

| 后续变化 | 对本书阅读的影响 | 依据与核验深度 |
|---|---|---|
| v0.31 调整等待队列，并增加活跃请求约束 | 第5章的具体队列与条件属于固定版本；迁移时重新核对 schedule | [v0.31 发布说明](https://github.com/vllm-project/vllm/releases/tag/v0.31.0)，Scheduler 项及其 PR |
| MRV2 的能力继续扩展；v0.32 调整 ROCm 默认选择 | GPU、ROCm、Ascend 的默认实现必须分别核对，不能由一方推断另一方 | [v0.32 发布说明](https://github.com/vllm-project/vllm/releases/tag/v0.32.0)，Model Runner V2 项 |
| v0.32 调整上下文长度与 max_tokens 的处理 | 输入校验与有效 token 预算需要重读；不沿用旧版具体异常条件 | [v0.32 Breaking Changes](https://github.com/vllm-project/vllm/releases/tag/v0.32.0)，PR #57035 |
| v0.32 移除部分编译优化和 cascade attention | 第11、14章的可用路径、模式与回退需要在新版本重新检查 | 同一发布说明，PR #60517、#61126 |
| v0.32 快照中两代 GPU Model Runner 入口仍存在 | 不把“预计删除 MRV1”当作已发生事实；文件存在也不证明默认启用 | 八个文件的路径和顶层类定向检查；不等于全分支行为审计 |

这些是迁移阅读提醒，不是完整更新日志，更不是新版性能结论。需要升级时，先比较数据契约、状态字段与装配条件，再比较方法名和行号。一个类名仍在，但其默认路径或结果提交时点已经变化，同样会影响本书中的调用树。

历史设计材料也有边界。V1 发布博客帮助解释降低 CPU 开销、简化执行与统一调度的动机；Hybrid KV 文档使用较早源码快照解释分组思想。本文引用其设计背景，但具体方法、分组条件和状态路径以 v0.30.0 源码为准。[V1 设计背景](https://vllm.ai/blog/2025-01-27-v1-alpha-release)；[固定版 Hybrid KV 文档](https://docs.vllm.ai/en/v0.30.0/design/hybrid_kv_cache_manager/)。

## C.3 哪些结论有哪一级验证

| 证据 | 本书实际覆盖 | 不能据此推出 |
|---|---|---|
| 固定源码核对 | 摘录、关系、调用位置、状态分支、配置条件 | 所有模型与平台组合都成功运行 |
| NPU 真实运行 | A/B、分块与 C 加入、Runner 张量、AsyncLLM 流式与取消、TP2 与 PP2 | CUDA 路径、HTTP 全链、生产吞吐和长时稳定性 |
| CPU 调用真实对象／方法 | KV、DP 路由、语法、多模态缓存、LoRA 映射、混合 spec、Connector、指标等 | 相应完整模型或跨机服务已验证 |
| 固定源码 AST 函数体 | 专家映射、n-gram、FP8 编码及部分模式判断 | 装饰器、编译器、设备 kernel 和完整依赖栈行为 |
| 源码构造例 | 投机拒绝后的进度回退、共同状态恢复边界等 | 某次硬件运行真的发生了这些数值 |

特别是异步前端实验使用异步交付，但核心调度仍按记录配置关闭异步；不能拿它验证 CPU 与设备计算重叠。Connector CPU 往返保存了真实张量，却没有验证网络、NIXL、DMA 或 PD 服务。FP8 编码展示舍入与 scale，却没有验证 NPU FP8 GEMM 和模型精度。

若希望把这些范围向外扩展，先选一个具体模型、平台与配置，在同一边界增加观测，再补正确性对照与性能测量。先把“验证了什么”说清楚，新的证据才能与已有内容可靠衔接。
