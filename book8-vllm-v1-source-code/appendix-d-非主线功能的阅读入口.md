# 附录 D 非主线功能：沿契约继续阅读

正文选择生成请求作为主线，但一个推理系统还需要服务不同任务、部署形态和模型家族。本附录给出固定版本中的继续阅读入口。它不是功能兼容矩阵，也不声称以下所有分支已经端到端实测。

## D.1 不以逐 token 文本结束的任务

Pooling 请求将模型表示交给汇聚或任务头，结果可以是向量、分数或其他非生成产物。第12章已经说明它和采样返回的区别。继续阅读时，先看 `pooling_params.py` 与 `entrypoints/pooling/` 怎样表达任务，再看 `v1/worker/gpu/pool/pooling_runner.py` 怎样消费模型输出，最后回到输出侧核对结果类型。不要默认每个请求都经过 sampler 和反分词。

同一原则适用于 rerank、embedding 与 classification：用户协议相近，不意味着输出张量语义相同。检查输入如何配对、模型头产生什么形状、结果如何对应原样本，再考虑共享调度与批次的部分。

## D.2 Beam search、工具调用与推理文本解析

Beam search 需要保存多个候选及其累计分数，不能直接套用“A每轮只有一个当前分支”的直觉。固定版入口在 `entrypoints/generate/beam_search/`，区分 offline 与 online。先读候选扩展和保留规则，再查引擎怎样接收这些工作；不要未经核对就推断它必定是核心 Scheduler 内的一个开关。

工具调用和推理文本解析位于用户协议与生成结果之间。它们可能消费模型特定的标记与增量文本，改变客户端看到的消息形态；这与第21章在 logits 上限制合法 token 的语法约束是不同层次。入口为 `tool_parsers/`、`reasoning/` 及在线 serving 代码。沿“原始模型输出→增量解析状态→协议消息”阅读，重点检查跨输出块的标记、未完成片段和结束行为。

## D.3 更多模型与 Attention 变体

第10章选择 Qwen3 使权重与形状容易对应；第18、22、25章分别打开专家、多模态与混合状态。阅读 MLA、稀疏 Attention 或其他模型时，可以复用同一顺序：模型注册与配置→层结构→KV spec→backend metadata→实际算子。

不要先假定所有模型都保留形状相同的K/V张量，再把压缩状态硬塞进满注意力公式。模型特定状态影响分配页大小、读取位置和前缀复用条件；第11、25章的接口问题仍然适用，但具体字段需要重新核对。相关入口在 `model_executor/models/`、`v1/attention/` 和 `v1/kv_cache_interface.py`。

## D.4 Ray、多节点与更多并行组合

第16章实测 TP2 和 PP2，第17章拆开副本路由，第18章说明专家归属。继续看 Ray 或多节点时，先确定每个 rank 的设备与节点，再看启动、消息传输、进程组和故障传播。`v1/executor/ray_executor.py` 与 `distributed/parallel_state.py` 提供入口。

换了执行器不等于调度器重新定义了 token 进度，但启动、错误交付和清理成本会改变。两个单独成功的 TP、PP 实验也不能替代 TP×PP 联合验证。上下文并行、专家并行和数据并行的具体组合，需要同时检查模型、backend 和进程组支持条件。

## D.5 模型注册实践放在读完主干之后

若要把前几册的教学模型接入 vLLM，先以一个已有的相近模型实现为对照，列出三个契约：配置与注册、参数装载、forward 与输出。随后检查 Attention、KV spec 和任务接口。注册成功只能证明模型被识别；权重映射正确、生成正确、批次变化正确要分别验证。

建议先完成一条短请求的数值对照，再加入 A/B 异长批次、分块、结束清理和恢复。每次只增加一个变化维度，保存输入、有效配置和关键产物。完整训练与注册工程属于选读实践，不是理解本书的前置条件；旧实验资产保留作历史材料，使用前必须重新核对版本与运行环境。

## D.6 通用的继续阅读顺序

先把新功能放回全局地图，说明它改变请求契约、状态表示、执行实现还是部署组织。然后找一对生产者与消费者，跟踪一个最小产物；再补正常结束、取消、失败与恢复。最后才决定是否深入某个 kernel。

如果无法确定具体平台是否支持某组合，结论就保留为未知，并查该版本官方支持说明与配置检查。看到接口存在、类可导入或某条测试用例通过，都不能代替目标组合的验证。
