## 事实依据与解释边界

主干职责复核[官方 v0.30.0 架构说明](https://docs.vllm.ai/en/v0.30.0/design/arch_overview/)，具体关系回查本地固定源码；UML 记法参考 [OMG UML 2.5.1 规范入口](https://www.omg.org/spec/UML/2.5.1/About-UML)。所有图由本书选取成员、简化重绘，不冒充官方原图。DTO、协调对象等是本书对源码角色的解释，不声称维护者给实现正式命名了某个设计模式。

| 关系或路径 | 核验依据 | 避免的误读 |
|---|---|---|
| LLMEngine 持有处理器和核心客户端 | `engine/llm_engine.py` 构造函数中的三个属性赋值 | `engine.engine_core` 不直接等于核心对象 |
| InputProcessor 创建请求描述；OutputProcessor 索引交付状态 | `input_processor.py::process_inputs`；`output_processor.py::add_request` | 创建依赖与长期关联不同；保存引用不自动证明 UML 强组合 |
| InprocClient 继承 EngineCoreClient | `core_client.py` 类定义与构造函数 | 类型继承不表示新增进程 |
| EngineCore 持有 SchedulerInterface 与 Executor 的实现 | `core.py` 构造函数；`sched/interface.py`；`executor/abstract.py` | 参数注入、配置选类分别说明，不把全部系统说成纯依赖注入容器 |
| Scheduler 与 UniProcExecutor 的泛化 | 各自类定义的基类 | 不把“协调者调用协作者”误画成继承 |
| Scheduler 持有 Request、KVCacheManager，创建 SchedulerOutput | `scheduler.py` 初始化、schedule；`sched/output.py` 数据定义 | 持久请求状态和当步传输数据不是一类对象 |
| NewRequestData 的列表与 CachedRequestData 的单个批量容器 | `SchedulerOutput` 的类型标注 | 一个容器对象不代表一条请求 |
| 接纳、step 与 KV 停点路径 | 调用树涉及方法的实际调用位置 | 兄弟调用并非同时在栈；跨进程消息不形成连续 Python 调用栈 |

补充 SchedulerInterface 后，来源索引扩大至 31 个文件；见[来源索引](../source-index.json)。关键关系与调用位置通过 AST 检查，结果含文件与行号，见 [architecture-validation.json](architecture-validation.json)。AST 能确认静态调用位置，不能证明每个分支实际执行；本轮未采集运行时调用栈。此前日志与本轮源码推导继续分开标识。

## 注释与图示审校

注释来自独立 [source_notes.py](../../../../../code/source_notes.py)，构建器只在指定原始行前插入解释。检查先确认新增内容被 Python tokenizer 识别为注释，避免误插到多行字符串；再移除新增注释，逐字比较固定源码。原始注释、变量、条件与顺序保留；网页将教学注释用不同颜色标示。

逐张查看新增与修改的地图／类图，核对箭头方向、空心三角、类别、数量标记与文本容纳。保留原时序图、部署图与状态图，各图说明其简化边界。没有将静态类框解释成进程，没有仅因属性存在就画强组合，也没有通过装饰性的设计模式标签替代源码解释。

本轮修正调用树中一处容易写错的条件：LLMEngine.step 本身会调用客户端 abort_requests，空请求列表在 InprocClient 内不继续触发核心中止，不能将前端的这个调用写成“有请求才发生”。
