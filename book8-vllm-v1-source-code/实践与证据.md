## 怎样复现

代码入口：[observe_requests.py](code/observe_requests.py)。脚本使用工作区现有本地模型，不下载或重装运行栈。它要求该模型快照存在；迁移到其他机器时，先准备对应模型和匹配环境，并调整脚本顶部的模型路径。

在工作区根目录先运行 `npu-smi info`，确认空闲卡，再设置设备编号。下面卡 0 仅是本次选择，不保证复现时仍空闲。

```bash
export ASCEND_RT_VISIBLE_DEVICES=0
source ./env.sh
python code/Book8-vLLM源码剖析/observe_requests.py --case baseline --out log/book8-source-rewrite/my-baseline
```

另开 shell 时重新设置设备并 source 环境。将 `--case baseline` 改为 `--case chunked` 运行分块案例；使用 `--deployment mp` 运行基础多进程对照；使用 `--plain` 运行不包装内部方法的对照。每次指定不同的 `--out` 目录，脚本拒绝覆盖已有目录。

脚本保持 `spawn`，有 `if __name__ == '__main__'` 守卫。`inproc` 关闭的是前端与 EngineCore 之间的多进程边界，不能将其解释成修改了 NPU 的进程启动纪律。InprocClient 中直接驱动真实 `LLMEngine`，未自行模拟 Scheduler 或替换模型计算。

首次暖机可能长于后续运行，初始化也占用时间。`result.json` 中的 wall_seconds 包含启动到结果完成，但不包含 finally 中完整关闭耗时；带探针运行会有额外序列化开销。这些数字只供安排复现实验，不是吞吐或延迟基准。

## 怎样理解字段投影

包装器在方法边界立即提取字段，防止随后对象发生变化而污染早先快照。它不遍历整个引擎内部对象图。小张量会记录内容，其他张量记录类型、形状与设备；本轮主要观察 Python 消息和列表。

正文 JSON 保留被选字段的原始值；对象投影中取值为全限定类名的 `type` 是探针添加的类型标识，不是声称原类里有一个同名字段；渲染输入字典原有的 `type="token"` 则属于真实输入格式。集合排序后输出为数组，tuple/list 也以 JSON 数组显示，枚举显示其名称。JSON 展示形式不等于进程线上编码。

实际运行类为 Ascend BalanceScheduler，均衡功能关闭，`schedule` 分支委托上游实现；实际 Runner 是 Ascend MRV2。主案例的方法来源与哈希都保存在 manifest。上游与安装包的对应源码逐文件比较见[源码核验索引](provenance/research/Book8-源码重写/2026-11-02/source-index.json)。这不代表所有 CUDA 算子和上游 GPU Runner 都已在本机运行。

初轮观测发现 `ConstantList` 只被打印出类型，未包含 token 内容，随后改进序列字段的序列化并重跑两组案例。正文使用重跑记录；初轮材料保留在工作区 `log/book8-source-rewrite/preliminary-*`，不混入正文。最终探针版本与四次正式运行的脚本哈希一致，检查记录见审校报告。
